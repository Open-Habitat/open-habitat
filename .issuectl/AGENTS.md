# Issue tracker policy

Work in this repository is tracked as issues under `issues/<slug>/` and
managed with `issuectl`. This file carries what an agent touching the tracker
could not learn from the tool itself: why the tracker is shaped the way it is
here and what the repository has decided about it. The `/issue` skill and
`issuectl <command> --help --json` describe the commands, and the session
skills say how the DAG drives a work session; neither is repeated here. The block between the sentinels at the bottom is generated
from `issues/.schema.yaml` and `.issuectl/transitions.yaml` by
`issuectl doctor --fix`, so a change to the rules belongs in those two files
and the block follows.

## Why writes go through the tool

Several workers write to `issues/` at the same time from separate worktrees.
`issuectl` takes the repository write lock, validates every field against the
schema and returns a version token that can be passed back as
`--expected-version` to detect a concurrent edit. A hand edit to `item.md`
frontmatter has none of that: it can land a value the schema rejects or
overwrite another worker's change, and the failure surfaces later as a
`doctor` finding in someone else's gate run. The body is ordinary Markdown,
but `issuectl note` (Comments, Decisions, Agent Runs) and `issuectl check`
(checklist items) append or toggle without disturbing the surrounding text or
racing another writer, and `issuectl apply` or `update --patch-file` bundle
several changes into one transaction.

## The schedule

There is no backlog. An open non-epic issue is either scheduled by its `lane`,
ordered within the lane by `blocked_by`, then priority, then `lane_seq`, and
across lanes by `blocked_by`, or it is an anomaly that `/wrap-up` reports.
Labels classify content, not lifecycle: a `deferred` label once meant "not
now", it has been retired in favour of the `deferred` status with
`deferred_until`, and `doctor --fix` removes the label if it reappears.

## Status transitions

`.issuectl/transitions.yaml` lists the allowed transitions and its comments
give the reason for each: `untriaged` is unreachable from in-flight work
because that would silently un-work an issue, and the completion statuses
`fixed` and `done` come only from the development flow so that an untriaged
report cannot quietly become `fixed`. When the tool rejects a transition, the
error names the rule, and the answer is usually a different disposition
through `issuectl intake` rather than the same transition again.

## Commits and results

Commits carry a `Refs-Issue: @<slug>` trailer, or `Fixes-Issue:` when the
commit completes the issue. `issuectl sync-commits` and `changelog` read these
from history, so the trailer is the link that survives; `update --add-commit`
records the same commit on the issue side immediately. An issue is done when
its result is real and landed and its `result.md` says what was verified and
what was not. Plans, experiments and evidence live in the issue directory
beside `item.md` while the issue is in use. A closed issue's directory goes
to git history once no open issue or other living document names it
(`scripts/prune-closed.py`, root `AGENTS.md`); the trailer is what still
leads from the code to it there.

## Doctor

`issuectl doctor` runs inside the green gate (`scripts/ci-local.sh`) with a
pinned issuectl that may be older than the one installed on the machine. A
critical finding therefore fails everyone's gate, not only the run that caused
it, which is why it is worth fixing as soon as it appears. Doctor also
maintains the block below; `agents_md_drift` in its report means the schema or
the transition rules changed and the block is stale.

- `assessment_classification` (optional, scalar)
- `assessment_outcome` (optional, scalar)

- `blocked_by` (optional, list)

- `disposition_note` (optional, scalar)
- `disposition_reason` (optional, scalar) — allowed: by-design, out-of-scope, wontfix, withdrawn, superseded
- `duplicate_of` (optional, scalar)
- `epic` (optional, scalar)
- `labels` (optional, list)
- `lane` (optional, scalar)
- `originating_run` (optional, scalar)
- `originating_run_kind` (optional, scalar)
- `owner` (optional, scalar)
- `preparation` (optional, scalar) — allowed: pending, reviewing, ready
- `priority` (required, scalar) — allowed: low, normal, high
- `provenance` (optional, scalar)
- `provenance_detail` (optional, scalar)

- `review_confidence` (optional, scalar)

- `scheduling_reason` (optional, scalar)

- `source_ref` (optional, scalar)
- `status` (required, scalar) — allowed: open, in-progress, testing, untriaged, deferred, needs-info, done, fixed, wontfix, duplicate, cannot-reproduce, obsolete
- `type` (required, scalar) — allowed: bug, task, feature, improvement, chore, epic
- `updated` (optional, scalar)

### Required body sections by issue type

_No per-type body-section requirements declared._

### Status-transition rules

- **→ cannot-reproduce**
  - allowed from: untriaged, needs-info, deferred, open
- **→ deferred**
  - allowed from: untriaged, needs-info, open
- **→ done**
  - allowed from: open, in-progress, testing
- **→ duplicate**
  - allowed from: untriaged, needs-info, deferred, open
- **→ fixed**
  - allowed from: open, in-progress, testing
- **→ in-progress**
  - allowed from: open, testing
- **→ needs-info**
  - allowed from: untriaged, deferred, open
- **→ obsolete**
  - allowed from: untriaged, needs-info, deferred, open
- **→ testing**
  - allowed from: in-progress
- **→ untriaged**
  - allowed from: needs-info, fixed, done, wontfix, duplicate, cannot-reproduce, obsolete
- **→ wontfix**
  - allowed from: untriaged, needs-info, deferred, open, in-progress, testing
