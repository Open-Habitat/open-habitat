# ADR 0008: Keep recent conversation windows in the browser

**Status:** Proposed — Jari's architecture decision pending at @design-snappy-conversation-switching

**Date:** 2026-10-02

## Context

Switching to a recently viewed conversation in the current tab should render without waiting for a server round trip, within one display frame (~16 ms). Cold conversations (including after reload) and deep scroll may wait. Today `App.tsx` keys `BrowserConversation` by conversation id, remounting it; `useConversation` clears its history and live state, fetches status and the oldest 25 history entries in parallel, and creates a new EventSource for the *same user-wide* journal. Outside a controlled conversation `App.tsx` instead owns a catalog-only EventSource, which also changes ownership on route transitions. On a native entry it rereads the first page and walks up to 16 pages forward. The separate read-only `HistoryView` also remounts and fetches on every switch. `incremental-history-during-turn` is covered here.

Pi JSONL files remain the only history truth. The daemon validates ownership, orders and replays a per-UID global journal, resolves history, and admits writes. The gateway routes a session to its Unix user; it must not mix one UID's journal with another's. The snapshot's `live_tail` is provisional and atomically coupled with its journal cursor. The current history API starts at the *oldest* entry, not the newest, and its `after` cursor only moves forward. `status.native_revision` is a stat-based hint; the history page's `native_revision` is a content hash, so they must not be compared for equality. See [panel](../issues/design-snappy-conversation-switching/panel.md), [measurements](../issues/design-snappy-conversation-switching/measurements.md) and [simulation](../issues/design-snappy-conversation-switching/simulation-output.txt).

## Recommendation for Jari's approval

Use **A, with D as cold/recovery fallback**. One EventSource per tab and authenticated identity owns the global cursor; it is not tied to route changes. A disposable, in-memory, identity/daemon-instance-scoped LRU holds the most recent **five opened conversations**, each with at most **50 native entries**, a capped provisional turn (existing 128 frames / 128 KiB), presentation status, workspace id, paging boundary, and reading anchor. Target a **4 MiB aggregate serialized-entry budget**, evict oldest unselected windows by count or bytes (drop deep pages first). These are initial limits to tune with profiling; never keep mounted DOM trees for all windows. Keep selected and warm windows current by dispatching every validated, contiguous event in global sequence, but do not render background frames. Validate frames even for unvisited conversations; do not allocate a window for them. Data in a long-unvisited or evicted conversation is fetched on open, not prefetched. Read-only native conversations should use the same window mechanism, not a separate always-cold `HistoryView` path.

A bounded `history.entry` frame is daemon-produced from checked native history. On a contiguous stream and a known compatible window, append or deduplicate by native key into the browser projection without another history GET; never append provisional text to settled text or match by content. The saved assistant entry replaces the provisional turn as a unit. A repeated key with different content, unknown prefix/order, missing payload, oversized entry/ring truncation or changed native revision invalidates the affected history window and starts native reconciliation. A separate `assistant.delta`/`tool.*` frame stays provisional, bounded and separate from native entries. Keep provisional state for an opened background turn only within its cap, or mark its live section stale and fetch the daemon snapshot tail on selection; do not silently display an incomplete assistant answer. A global `snapshot.invalidated`, gap, 409 or instance change never turns cached entries into write authority. The history page's native revision scopes paging and content chunks; a changed revision demands a fresh tail and discards old deep-page cursors. No comparison of the unrelated status revision hint with the history hash.

Extend the history read contract to request a **tail-first bounded page** (at most 50 entries and existing byte cap) with a **backward** cursor for older entries, a stable native revision on every page, and explicit stale-precondition on a changed file. The daemon still reads/validates the selected Pi file; no daemon history index or materialized copy. The first page must cover the newest entries without walking every older page over HTTP. A page obtained while SSE runs is not assumed atomic with the stream: buffer concurrent relevant events, compare native keys/revision, then replay events after the load fence; if ambiguous, retry/resnapshot rather than lose a turn. Deep pages are temporary UI state and can be dropped on switch or memory pressure; scroll position is best effort if its anchor is evicted.

An in-memory window is **not a parallel history store**: it is a bounded view of entries this tab read or received from the mapped daemon, cannot authorize sends or continuation, has no durable browser storage or cache-service persistence, can be discarded without losing any user work, and is reconstructed from Pi. The measured need is that the current warm SPA switch still waits on a history request (100–117 ms in the synthetic read-only sample); a zero-RTT switch cannot be delivered by the current fetch-on-open path. Explicit budgets and invalidation make this a UI projection, not a competing history authority. Drafts and uncertain-send markers remain their current identity-scoped sessionStorage, separate from native history; no entry content is persisted there.

## Interaction sequence and latency budget

| Interaction | Sequence (owner → effect) | First meaningful paint budget |
| --- | --- | --- |
| Page load/reload | Gateway authenticates; daemon snapshot supplies identity, instance, cursor, agent list and provisional tails; browser creates empty LRU and one SSE from cursor. Selected conversation loads tail history + status in parallel; replay events arriving during load before marking it clean. | Cold spinner allowed; lab controlled **full reload 187 ms**, not a production percentile. |
| Warm switch | Route selects an already opened window synchronously; render bounded entries/anchor without fetch or remount; background windows did not render. Continue global stream. | **≤16 ms to paint**, zero request on click; target to test on instrumented implementation, not yet measured. |
| Active turn / send | Local draft/send observation persists as today; actual POST and receipt stay daemon-authoritative; journal dispatches provisional deltas, tool state and saved entry keys. `history.entry` replaces provisional turn; command/queue/question/settled event triggers *coalesced* status fetch when those authoritative fields matter, not history page-1 traversal. | Send feedback before network response (target ≤16 ms); accepted/rejected outcome waits for POST/status. Delta paint target next animation frame, throttle visible updates. |
| Reconnect/offline | Preserve the currently displayed window, mark it stale/offline and disable writes/continuation; resume the single global cursor. If sequence continuous, apply backlog and clear stale only after reconciliation; if 409/gap/instance mismatch, close stream, resnapshot, invalidate all windows, reconcile selected from native, then restart stream. | Old text may render immediately **with stale indicator**; proof/controls wait on native recovery. |
| Scoped or user invalidation | Agent-scoped invalidation marks its window dirty; user-scoped source change marks **all** windows dirty. Keep old text visibly stale, but do not claim it is current. Reconcile selected tail/status; warm dirty windows reconcile when selected or opportunistically within bounded work. | Stale display immediate; clean state may wait. |
| Deep scroll | Read older page with backward cursor + history revision; merge at anchor if revision matches, otherwise discard deep pages and restart. | Spinner for older page permitted; no blocking of current tail. |
| Cold open / eviction | Show skeleton; fetch tail history + status in parallel, validate workspace and identity; buffer/replay concurrent journal events, reveal only once coherent. | Spinner permitted; budget = max(status RTT, tail-history RTT) + parse/render, to measure on actual host. |
| Identity change / 401/logout | Synchronously close EventSource and discard all windows, live tails, old response generations and drafts under the old identity before rendering new identity. An in-flight response may not repopulate old data. | Never show old person's text under new identity. |
| Same user in multiple tabs/devices | Each tab independently authenticates, owns one stream and its own disposable windows; daemon's UID-local ordering/ownership is shared; a command from another tab arrives via journal. No BroadcastChannel/SharedWorker or cross-tab cache. | One SSE per active tab; no guarantee on offline tab freshness. |

A warm **dirty** window may render old text instantly with an explicit stale indicator, not as if verified. For command admission, cached status is only display data: fresh daemon checks, existing CSRF and continuation proof remain mandatory. On a daemon restart drop all windows (not just cursors) after detecting the instance change. A lost browser session may keep an admitted SSE open until its existing 10-minute deadline; no cache design can make revocation retract already-rendered bytes, but on 401/replacement the tab clears memory immediately.

## Costs and rejected options

`simulate.py` gives a deliberately heavy eight-writer scenario: **116.6 KiB/s per tab / 409.8 MiB/hour**, ~168 parsed frames/s, **1.14 MiB/s fan-out for ten tabs**, and ~16.8 ms CPU *per second* under an assumed 0.1 ms/frame. Typical one writer is **2.6 KiB/s / 9.2 MiB/hour**; idle heartbeat is negligible (~0.65 B/s). At eight writers ×20 deltas/s the daemon's 128-frame replay ring can expire in <1 second on a paused tab: recovery is essential. Five ×50 median-sized entries cost roughly **1.87 MiB heap** under the 3× scenario factor, before provisional state/DOM; hard byte bounds must enforce the actual cap. These are modeled payload and CPU costs, **not measured network p95 or a demonstrated 16 ms render**. Existing unified SSE already sends all users' *own* agents' frames; this design changes client retention/connection lifetime more than wire volume. Ten tabs mean ten SSE connections, not one shared global connection. Daemon/gateway fan-out is O(tabs × events), not O(conversations × events), with no new per-conversation stream.

- **B: IndexedDB on top of A** could show data after reload or days away, but reload is allowed to wait. It cannot synchronously serve the current-tab memory target, persists sensitive Pi/tool text across logout under a shared browser origin, and introduces schema/eviction/atomic cursor reconciliation. No measured need for this exception to the no parallel-store rule; rejected.
- **C: push recent tails for every conversation** could make never-opened conversations feel warm, but is speculative prefetch, not the stated recent-opened requirement. Snapshot already carries bounded provisional `live_tail` for agents; adding native tails for all 100 at 50 entries each would be ~15 MiB wire at the simulated median and adds snapshot cost without learning which conversation will open. Pushing 100 maximum-size provisional tails alone could reach 12.5 MiB. Rejected; current stream carries all relevant changes without requiring a browser window for each.
- **D: tail-first fetch, keep-alive/keep mounted only** improves cold path, and tail-first is necessary, but a request on every switch cannot guarantee zero network wait. Keeping five whole mounted trees adds DOM/side-effect lifecycle cost; retain data, not components. D remains the fallback rather than the warm path.
- **Extra browser journal ring / cross-tab worker** was proposed in the panel: adds replay/leader state while eagerly updated windows and daemon journal already cover the stated use case. Revisit only on demonstrated multi-tab resource pressure.

## Remove or change from the current model

Consolidate both the catalog-only EventSource in `App.tsx` and per-conversation EventSource, cursor/reconnect handling and offline polling in `useConversation` into the single tab-wide stream; remove keyed remount for route changes and `setEntries([])/setOpened(false)` on a warm switch. Replace the full-history read from page 1 on every `history.entry`, its 16-page walk and `pendingNativeEntry` single-key retry with bounded direct event projection plus revision/fence-based reconciliation. Replace separate read-only always-cold history state with the shared bounded window. Retain explicit status reads for fields the journal does not carry (including fresh continuation proofs), send receipts and uncertainty markers; do **not** treat the snapshot's provisional tail as settled history. Change history paging from oldest/forward-only to tail-first/backward for display, preserving a native read path for recovery. The daemon journal stays one per UID; gateway/Unix authority does not move.

Profile worst-case 50-entry render and large native output in synthetic browser, test overlapping fetch/event races, external file rewrite, two identities, multi-tab updates, gap/daemon restart and memory eviction before claiming the ≤16 ms target.
