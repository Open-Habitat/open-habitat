# ADR 0006: Local gateway subject revocation

**Status:** Accepted (Jari approved the direction in @revoke-subject-sessions, 2026-09-29)

The gateway owns browser sessions, OAuth states and conversation authorization. A root operator needs to remove one person's gateway access without restarting the shared gateway or changing the broker's identity ledger. An OAuth state has no subject until the callback exchanges its code; removing it from the map by subject at the moment of revocation is impossible.

Use a dedicated systemd-created Unix socket at `/run/native-agent-host/revoke.sock`, root-only mode 0600, passed as a single inherited descriptor to the unprivileged gateway. The authenticated gateway refuses startup without this descriptor. The control protocol accepts only one canonical positive numeric GitHub subject. The gateway checks kernel peer UID 0 and asks the broker to authorize the subject and return a valid binding before mutation. There is no HTTP route, browser cookie, UID, email or candidate login in this authority path. Root and the broker's allowlist are the operator authority; a compromised root operator already controls the machine. Fleetrepo must activate the socket with the service as one installation change; the package template alone does not change the live host.

Under the gateway session mutex, revoke removes that subject's sessions and per-session conversation permissions and sets a cutoff at the latest OAuth start serial. At callback, after provider identity resolution, an older flow for that subject is denied both before native token handoff and at the final locked session insertion. Other subjects' anonymous pending flows remain valid; they cannot be classified before the provider returns an ID. A callback already in handoff when revocation occurs may install a native credential, but cannot issue a session. A new login flow started after the cutoff is permitted; an operator who wants a clean personal workspace must independently isolate ingress during the reset. Restart loses all in-memory flows and sessions; no persistence or separate credential store is introduced.

Already-running requests and native daemon processes are not terminated. Broker checks still occur on each request, but a request that already passed authentication cannot be undone. Provider grants, device codes, Pi history, gh credentials, daemon handles and binding ledger are outside this action. A live reset still needs a reviewed operator and separate scoped daemon drain, inventory and provider-side checks. Do not interpret this as approval for guest deletion.
