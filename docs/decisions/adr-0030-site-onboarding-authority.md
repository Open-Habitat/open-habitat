# ADR 0030: Site onboarding, runtime admission and the site AI key

**Status:** Accepted 2026-10-24 (Jari), with all six recommendations of the proposal. The reasoning, the option tables and the current-code constraints are in `issues/plan-site-onboarding-authority/plan.md` (git history once removed). The product design is the prototype `proto-admin-server-onboarding`, rounds 1–6. The commands and operations named here are work to implement.

## Problem

An administrator sets up how a new person joins (Settings › *Käyttöönotto*: repositories, integrations, AI account) and who may join (Settings › *Käyttäjät ja pääsy*: allowed GitHub accounts, no invitations). Each of these needs an owner among the gateway, the broker and the person's daemon. Today admission comes only from root's `site.json`. The host holds no credentials, and the daemon trusts no input from the browser.

## Decision

**The onboarding configuration is gateway administration state.** `onboarding = {repositories: {mode: preselected|auto|skip, defaults[]}, integrations: [{provider, required}], ai_account: {offer}}` lives beside the server name and default quota, with the same writer lock, version and validation from the browser and from root's `open-habitat admin onboarding` CLI. `host apply` never touches it. It is never world-readable. A daemon receives only what a request needs, inside requests the gateway builds itself: the repository plan in the first-login handoff and the filtered defaults on the repository-list request. Integration and AI steps are presentation the browser reads from the gateway. `required` only removes the skip action and gates no access. The daemon may act on this input because it can only select among the person's own native actions (own `gh`, own `~/src`, `owner/repo` grammar, at most 20 defaults, own quota). A configuration change never affects people who have finished onboarding.

**Admission has two sources, both owned by the broker.** The `operator` source is `site.json` through `host apply`, as today. The `site_admin` source is runtime entries written only by new gateway-socket operations `admit` and `withdraw`; effective admission is their union, and a read-only list operation returns both. `site.json` gains `identities.runtime_admission` (default `false`). While it is false the broker refuses `admit`, and `withdraw` still works. The gateway resolves a login to its numeric GitHub id with the public users API (as the OAuth app, never with a person's token), and the browser shows a change as in effect only after the broker's reply. An uncertain reply is shown as uncertain and nothing retries automatically. Anyone the `operator` source admits, administrators included, cannot be withdrawn from the browser, and the browser's administrator-role write is removed. Administrators come only from `site.json`. Withdrawal runs in a fixed order so that every crash point stays closed: the gateway durably records a per-subject deny, removes the subject's sessions while the broker still authorizes them, then sends `withdraw`. Withdrawal ends web access only; the Unix account, home, credentials, SSH and processes stay (account removal is ADR 0007). Restore removes leftover sessions, sends `admit` for the still-committed binding and only then clears the deny, so the person returns to the same Unix account. With `admission: "any"` the access tab is read-only.

**The gateway holds one persistent provider credential, the site AI key.** It is stored in a separate gateway-UID `0600` file, outside administration state. It is written by a browser administrator or root's CLI and never read back beyond provider and a four-character suffix. `offer` is `site_key` exactly while a key is stored. The key is seeded once, in the handoff of the login in which the broker created the binding (`ensure` replies `created: true`), by a daemon write-if-absent operation under Pi's own file lock, so it never overwrites a key the person has. Later logins never seed. Whether the AI step shows is decided by native Pi credential status. Replacing or removing the key changes future seeds only. This is the single named exception to "the host keeps no credential store": the gateway never proxies use, issues per-person tokens or recalls a copy. Seeding already-joined people (`admin ai-key seed`) is later, separate work.

**Default repositories are imported once, by the person's daemon.** In the binding-creating login the gateway uses the person's transient GitHub token for one read-only access check per default. A default the person cannot read (`no_access`, `check_failed`) never enters their UID. The daemon enqueues ordinary clone jobs (ADR 0024) for the rest, skipping existing workspaces. `skip` with defaults imports without a chooser; `auto` shows them as locked chooser rows; `preselected` only preselects. Nothing re-imports on a later login.

**The administrator sees a sign-in receipt.** The gateway stores, per subject, a fixed-shape result about the site's own defaults only: `no_access | check_failed` from its own check, `queued | already_present` from the handoff reply (`unknown` when that reply is missing), and `ai_key: seeded | not_offered | failed`. The user list shows it as "Käyttöönotto 24.10.: 2/3 oletusrepoa · ei pääsyä: X". It is a snapshot that says a clone started, not that it finished.

## Authority and trust changes

- The gateway's administrator check can make the broker admit a new GitHub id and so cause an account to be created at that person's login. A compromised gateway already acts as every bound person through their daemons; what it gains is minting accounts that outlive the compromise. The bounds are root's `runtime_admission` switch, a cap on runtime entries (256) and runtime entries with actor and time visible in `host plan` and `admin access list`. Account creation, the UID pool, quota and home isolation stay with the broker.
- The gateway becomes the persistent holder of the site AI key. Every seeded person and their agents can read their copy, and only revocation at the provider stops its use.
- The gateway uses a person's sign-in token for one more purpose, the read-only default-repository checks inside the same transient window. It still never persists, logs or returns the token.
- The gateway gains a per-subject onboarding receipt and a per-subject deny, both in administration state.
- The broker gains `admit`, `withdraw`, the admission list and `created` in the `ensure` reply. It gains no network access, credentials or home writes.

## Rejected alternatives

The onboarding configuration was not put in `site.json`, either alone or as a seed for runtime state, because the browser is its editing surface and either `apply` overwrites the browser or there are two truths. The broker does not ask the gateway for all admission, since that gives up root's own boundary, and a root-only queue of browser requests would leave every admission waiting for a human operator. The site key does not live in a root site input (not settable in the browser) or in the broker (credential and home-write authority). A shared group-readable key would expose the live key to everyone and change joined people. An LLM proxy with per-person tokens is the credential broker the rules forbid. The daemon does not check default-repository access itself, because the full default list would then enter each person's UID. The admin view does not query each person's daemon live (a new principal and N×M GitHub calls) or read homes.

## Rules for `internal/AGENTS.md` when the implementation lands

The onboarding configuration reaches a daemon only inside gateway-built requests and only selects among the person's native actions. The broker owns both admission sources, and the gateway may only `admit` and `withdraw` runtime entries. Withdrawal denies in the gateway and removes sessions before the broker withdraws, and restore removes leftover sessions before it readmits. The site AI key is the gateway's only persistent provider credential, seeded once, never over the person's key. Inaccessible defaults never enter the person's UID. The receipt is the only cross-user onboarding fact, and it comes from the handoff reply.
