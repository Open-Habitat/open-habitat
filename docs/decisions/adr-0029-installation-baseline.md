# ADR 0029: A release-contained operator converges one declared site

**Status:** Accepted for Jari's settled baseline and conductor-delegated delivery details, 2026-10-22. **Configuration mechanism: product CLI primary, for Jari's review**, not a claim that he chose against Ansible. His settled points are recorded in @decide-installation-baseline: Ubuntu 24.04 amd64/systemd, release-pinned runtime dependencies, a separate `/home` volume with quotas, and agent-operated maintenance. This record specifies work to implement, not commands available in today's release.

## Context

Two customer pilots need the same installable product that could later run on hundreds of independent servers. Today the archive has binary/UI/templates, while the concrete test installation supplies initialization, boot policy and native runtimes. Neither an agent guessing from source nor copying the maintainer's deployment is a supported installation interface. The assessment in `issues/prepare-independent-installation/result.md` identifies those gaps; the later Jari decision supersedes its optional-volume recommendation.

The hard parts are crash-safe broker initialization, enforced quotas, boot restoration, process isolation and adoption of approved bytes by every component. Those rules must have one implementation whichever fleet tool invokes it. The operator runs as root during deliberate maintenance, not as a new privileged service accessible to the browser.

## Decision

### 1. Supported host and ownership

Support Ubuntu 24.04 LTS, amd64, systemd and a dedicated, separately mounted **ext4 `/home` filesystem with journaled user quotas enforced**. Ext4 narrows the implementation of Jari's storage decision; other filesystems, shared home mounts and existing-account migrations are outside the first supported path. The customer supplies an identified volume mounted at `/home` by UUID, capacity and retention policy. The product never creates a cloud volume, formats a disk or silently migrates homes. Retaining a volume is not a backup.

The customer owns OS installation/security updates, SSH, firewall, DNS, verified HTTPS ingress and certificate renewal, OAuth registrations, secret delivery, volume attachment and approved maintenance times. The product owns its release/runtime bytes, trusted path layout, configuration rendering, account pool checks, quota/boot/process gates and activation. OS kernel/systemd/libc remain the supported OS platform, not bundled replacements. The customer must coordinate updates to the release-pinned tool package set with product release qualification; ordinary OS security updates outside that set remain customer-owned. Record their observed versions and required capabilities in check results; reject unsupported capability drift.

No authority moves between runtime components. The gateway still authenticates and maps identity, cannot read homes or execute agents, and receives no installer API. The per-user daemon acts only as its UID. The broker alone creates first-login identities and publishes bindings. The offline root operator may initialize an empty broker and install policy; later quota/role changes use existing product administrative operations. Admission reconciliation needs a product-owned root writer using the provisioning package's transaction and trust checks; it is not an existing admin command. The operator never edits committed identity bindings or resets the broker head after initialization. No root command hook, templated shell, provider SDK, privileged network listener or new credential broker is introduced.

### 2. Primary delivery interface — for Jari's review

Recommend **`open-habitat host` subcommands in the released Go binary**, reading one versioned declarative site file. The resource has enough structured fields, and repeated convergence is a real requirement (canon §6), to warrant `apply`. This is a bounded local installer, not a general configuration-management engine. All transports and fleet scheduling stay outside it.

| Interface considered | Judgment |
|---|---|
| Product `host check/plan/apply/prepare/upgrade` | Primary recommendation. Same release carries the policy and its parser/tests; typed failures and safe recovery can be tested against the actual broker. Root need not install Python/Ansible to run it. Cost: we own a small reconciler and its crash tests. |
| Ansible collection/role | Good fleet orchestration, inventory, secret delivery and batching. As primary implementation it would put product-specific transactional rules in tasks/plugins separate from the Go authorities, or require a product helper anyway. Check mode is module-dependent, not proof of quota enforcement or ledger transaction safety. A later thin role may invoke the same plan/apply and interpret JSON; do not build a second reconciler now. An existing customer Ansible controller may invoke the CLI immediately. |
| Signed `.deb` / apt repository with config or debconf | Strong familiar distribution and update transport. Maintainer scripts still need idempotency and error recovery; package installation must not silently change quota mounts, restart sessions or reseed a broker. Defer repository/signing infrastructure and a thin package wrapper; do not put site activation in `postinst`. Package metadata does not replace site planning or actual daemon-adoption checks. |
| cloud-init / prebuilt image | Useful to supply the OS, SSH and mount, or invoke the verified operator once. First-boot/instance detection is not ongoing convergence or upgrade recovery. Images risk capturing site identities/secrets and do not solve maintenance on installed hosts. Neither is primary; any later image is site-neutral and still runs the same operator. |

Hundreds of instances do not require a product fleet database: each machine retains its site declaration and local operation receipt. A customer controller stores inventory, invokes checks, canaries one server, and bounds upgrade concurrency. It may use Ansible, SSH or another scheduler. No auto-updater or implied fleet-wide maintenance permission ships in the pilot.

### 3. Site declaration and native-state boundaries

Use a strict JSON document, `schema_version: 1`, selected with `--site-file` (default `/etc/open-habitat/site.json`). Ship its JSON Schema, a neutral example and machine-readable help. Reject unknown/duplicate keys, invalid ranges and unsupported schema before mutation; no arbitrary includes, scripts, executable secret resolvers or environment substitution. Schema fields are:

| Group | Desired inputs |
|---|---|
| `site_id`, `release` | Stable non-secret site identifier; exact release version and authenticated manifest digest. No `latest` or floating tool versions. |
| `gateway` | Dedicated gateway numeric UID/GID and listen address; HTTPS app origin, exact OAuth callback/client ID; references to OAuth secret, TLS cert/key and optional trusted origin-hop CA. No copied test IDs. |
| `identities` | Exclusive numeric UID/GID pool bounds (1000–60000, at most 4096), numeric GitHub admission IDs and desired administrator subjects. Gateway/proc groups must be outside that pool. The administrator set grants no admission by itself. |
| `storage` | `/home` mount UUID, `ext4`, required user quota enforcement, nonzero default byte limit (1 MiB–1 PiB, 1024-byte aligned). No device formatting directive. |
| `profiles` | Required `core`, plus explicit `editor`, provider integration selections, and named agent-tool profiles. Profile names resolve only to the release's pinned catalog. |
| `editor` | Same-site per-identity HTTPS origin template, only when selected; names/DNS/TLS prerequisites validated independently of installing code-server. |
| `integrations` | Only selected provider app settings and protected file references; tool paths are generated from the release, never customer-controlled commands. No user tokens or account connection list. |

Site file and parents are root-owned, non-user-writable; file mode 0600. Secret references are absolute local regular files supplied by the customer's secret system, with root-authenticated non-writable parents, no symlink traversal and the minimum required reader permissions. The operator reads them directly, never from argv or environment. It renders separate least-readable gateway and integration configurations; the site's references do **not** imply that existing integration app credentials are hidden from mapped users where the native tool requires them. Never put secret values or hashes of secret-bearing files into plans, receipts, diagnostics or provenance.

The file is authoritative for the **listed site-managed sets** (admission, administrator subjects, selected profiles and default quota). Plan exposes additions/removals; a changed default is prospective and never silently rewrites existing users' limits. Admission changes run under the broker state-directory flock, reject pending/drifted state, atomically advance the allowlist epoch, and require the broker to observe the new epoch/high-water before reporting completion. Reuse provisioning transaction code rather than invent a second ledger writer. For removals close entry points, revoke live sessions **while the old admission still authorizes the subject**, then publish the reduced allowlist, verify denial and reopen; the existing revoke command cannot authorize an already removed subject. Interruptions keep maintenance closed until reobserved completion. Removing admission never deletes Unix accounts/homes. Desired administrator grants for unbound subjects are explicitly `deferred_until_bound`: apply reports the outstanding grant with exit 0, without claiming it was granted, and a later apply reobserves and grants after the person first signs in. A confirmed unbound subject differs from a failed broker lookup, which remains an error. Removals of roles need no binding. Removing a profile stops offering it and manages its services/config only; it never deletes native credentials, histories or cloud files. UID pool, gateway IDs and mount UUID become immutable after initialization; a requested change is unsupported migration, not convergence. Workspaces, bindings, native credentials, user tools/settings, per-user quota overrides and active conversations are observed, never declared resources or reset to match an old receipt.

The site file is the desired-state source, not a parallel ledger. Rendered files and a sanitized operation receipt are necessary install outputs. Live broker/native/systemd state is always reobserved. Per-key configuration provenance remains inspectable through `config path/show --json`; any persistent flag/env override exposed follows canon §8, replaces lists/maps, and is resolved into the plan. Do not expose secret-valued argv/env overrides. Execution pins the effective configuration so a hidden environment change cannot alter an approved operation.

### 4. Named release and pinned profiles

Deliver one authenticated manifest for `linux-amd64`, with the core archive and optional profile archives all addressable by digest. The release publisher signs the manifest; the operator verifies it using a release key already trusted by the operator/customer, or an explicitly independently approved manifest digest for the pilot. Downloading a checksum beside an archive is integrity checking, not approval. Key trust cannot be bootstrapped by an unverified downloaded script. The customer verifies the initial operator binary through this independent trust path before running it as root.

Logical installed layout under `/opt/open-habitat/releases/<version>-<digest>/`:

- `bin/open-habitat`, `web/`, and a relative `open-habitat -> bin/open-habitat` bridge required by the current units;
- `runtime/` containing Node/Pi, locked npm dependencies and selected packages; `tools/` for selected native executables and wrappers;
- `systemd/` including nested host drop-ins, `sysusers.d/`, `tmpfiles.d/`, site schema, operator skill/guide, license/SBOM inventory, runtime lock and compatibility metadata;
- a manifest covering all installed files, safe link targets, executable modes and each profile artifact's digest. Release verification must expand today's allowlist deliberately, reject traversal/foreign links and verify exact inventory before privileged extraction.

`current` selects immutable root-owned, non-user-writable bytes. Runtime selectors reference explicit release paths; activation treats selectors, generated config and units as one recoverable generation, not independent symlink edits. Native Pi/agent wrappers follow the selected approved generation. Fixed `/usr/bin/git` and `/usr/bin/gh` host actions remain fixed; a release-qualified offline set of exact Ubuntu package artifacts supplies those paths and required ACL/quota/account utilities. Resolve and record the complete package closure with digests and licenses at release build time, including tool-private shared libraries and transitive npm packages. The closure explicitly records platform ABI dependencies (kernel/systemd/libc and their baseline OS dependencies) as platform requirements rather than bundling or exact-pinning the whole operating system. Installation never resolves `apt latest`, `npm latest`, `npx` downloads or a network dependency solver. Reject conflicting host packages rather than silently downgrading them. Security fixes to bundled tools, including the exact pinned `/usr/bin` tool-package closure, require a new qualified runtime lock/release. This intentionally does not promise arbitrary OS updates preserve runtime pins: if customer security maintenance replaces a pinned package, check reports `runtime_package_drift` and upgrades/convergence block until a qualified lock is selected; it never downgrades the security update or installs apt holds automatically. Plan lists the package ownership boundary so the customer can coordinate its updater. Unrelated platform updates are capability-checked, not exact-digest pinned. This constraint is the operational cost of Jari's all-runtime-pinned decision, not a recommendation to weaken it to minimum versions.

Core includes Node 22.21.1 and Pi 1.3.0 (the current executable requirements), git, gh, tmux and account/ACL/quota utilities. Initial optional pins from the inspected working materials are processes core 0.10.9 with parser override 0.3.4 and Claude bridge 0.9.3; code-server 4.141.0; Himalaya 2.2.1; rclone 1.71.2; gog 0.39.1; Softeria 0.170.1. Taskfleet/workmux and other engineering tools belong in a selectable release-locked agent profile, not a personal-machine snapshot. Package extensions load only the qualified entry points, not every shipped extension. Exact OS package and additional engineering-tool versions are release-build lock outputs, not guessed in this ADR. A release cannot claim a profile until its closure is pinned and tested as mapped users with minimal HOME/PATH.

The parallel inventory in `issues/inventory-agent-software/result.md` landed during review and was read in full. Include its common shell/scripting/search/archive capabilities in the release catalog: bash/Unix utilities, Python+venv, curl/CAs/SSH, jq, rg/fd (explicit `fdfind`/`fd` naming), tar/xz/unzip/patch. The selectable coding/workflow profile includes Taskfleet 0.16.0 with a qualified workmux pairing, issuectl 0.21.0, consult-llm 3.0.38, git-surgeon 0.1.17, uv 0.12.13 and version-matched portable skills; these observed versions are candidate pins pending compatibility and redistribution checks. Offer language/build stacks and Shipshape/project-canon/glasspad separately. Do not distribute the observed unlicensed parser 0.2.2: use the licensed 0.3.4 graph. Resolve unverified upstream licenses before advertising a profile. Inventory candidates do not override the product Node/Pi pins or authorize copying personal skills/settings/routing. Customer-specific selection is per machine, including the fuller requested agent environment, and profile acceptance includes a disposable native worker flow without replacing a running orchestrator. Optional absence is explicit in checks; required absence blocks activation. Tools being installed proves neither provider consent nor account authorization.

### 5. Check, preparation, installation and convergence

These names describe domain transitions/observations, not aliases for setting a field (canon §7). All run locally; root is required for full privileged observations and mutation, with insufficient visibility reported as unavailable rather than pass.

- **`host check --json`** is read-only: desired/observed release/profile versions, host capabilities, trusted paths, mounts, quota status, pool collisions, effective units/ACLs/proc policy, pending state, service adoption and ingress prerequisites. No account creation, EDQUOT write test, remount, service start or consent automation hides in a check. Readiness/health is only one observation.
- **`host plan --json`** and every mutation's **`--dry-run`** return the complete versioned planning envelope without writing host state. Actions have stable IDs, reasons, before/after non-secret state, required maintenance/disruption, unknowns and blockers. They name destructive or unprovable work, never pretend that a read proved enforcement. Plan identity binds site/release/effective-input identity, machine installation identity and relevant observed preconditions; secret identities are tracked privately, never exposed as hashes. Execution revalidates all inputs under lock and refuses stale approval.
- **`host prepare`** is a separate explicit maintenance operation, taking the approved plan ID and explicit disruption approval. It installs the selected boot/quota/ACL/proc policy, applies planned logind/polkit restarts, enables quotas on an already suitable filesystem and runs a bounded disposable-UID EDQUOT probe with cleanup evidence. It may require a customer-performed offline ext4 quota-feature step and reboot; report that requirement and stop, never convert a mounted filesystem. It does not format storage or initialize a populated home. A receipt records reboot-required and probe results, not permanent permission to skip later checks.
- **`host apply`** performs fresh install or idempotent site convergence, but cannot smuggle disruptive preparation or a release upgrade into ordinary apply. It stages verified bytes, accounts and trusted parents, reserves/checks the exclusive empty UID/GID pool against NSS/groups/homes/units, and initializes the empty broker in one durable locked transaction. Existing matching initialization is a no-op; foreign or incomplete state is not an invitation to reseed. Before exposing admission, verify boot gates, then activate the broker, both listeners and gateway **behind closed entry points**. Set the nonzero default through the running gateway's `admin settings update`, verify readback, and only then expose sign-in. The current gateway also rejects callback provisioning with `quota_default_missing` before a default exists; do not replace that safeguard by writing its state files as root. Existing-install quota/role changes use the product admin APIs, and admission uses the locked root writer described above, with observed postconditions. Render the sysusers declaration from the declared numeric gateway UID/GID plus the empty proc group; never install the dynamic gateway allocation template verbatim alongside a fixed allocation. A changed release returns `upgrade_required`.
- **`host upgrade`** explicitly authorizes the release transition and maintenance interruptions, as below. Preparing an unsuitable host remains a separate approval.

Boot gates must verify the actual `/home` UUID/mount and effective enforced quota configuration before broker or user socket activation. Missing mount must never fall through to root-filesystem homes. Recreate `/run` and committed users' named ACLs after every boot; refuse revoked/foreign/pending bindings, restore **both** daemon and agent listeners before a daemon starts, leave their instances broker-controlled. Verify host-wide `/proc hidepid`, empty exemption group except narrow logind/polkit service membership, trusted selectors and user manager/linger readiness. The broker retains its existing authority to enable linger, not a new installer-owned list of people.

### 6. Interrupted state and failed upgrades

One root-owned operation lock serializes product host operations; broker/admin locks still govern their own writes. Use the broker lock during initialization, keep publication closed until commit, and never infer an empty host from missing files alone. A minimal durable local operation record stores phase, input identities, previous/target generation and non-secret postconditions, with atomic writes and fsync before crossing irreversible boundaries. It is a recovery journal, not a second identity or workspace store. `host operation show <id> --json` reobserves phase and actual state after caller disconnect or reboot.

For any interrupted mutation, the same invocation recognizes a completed postcondition and reports no-op/completed, resumes only verified safe steps of that exact operation, or returns `recovery_required` with the conflicting phase. It must not allocate another gateway, rerun admission side effects blindly, reseed counters, overwrite foreign files or delete pending evidence. Ambiguous broker state is a blocker for diagnosis, not automated repair. Dry-run cannot reserve the host against external edits; apply rechecks and refuses drift.

Run upgrade from the **verified successor binary at its explicit immutable staged path**, not through `current`; this operator owns the transition and recovery journal. The journal carries a schema version and owning generation. The target operator must be qualified to run on the predecessor host before transition. Resume and reverify that same explicit binary after interruption/reboot; predecessor operation inspection at minimum reports the owning path/version and an unsupported journal without interpreting or rewriting it. The release compatibility check must verify operator/journal handoff as well as data/runtime formats. Upgrade stages and verifies the exact supported successor plus predecessor compatibility metadata, then checks host/config/pinned-runtime/state compatibility before stopping services. Explicit maintenance stops new public/own-UID entry points and relevant socket activation; enumerate running daemons, Pi turns, editors and persistent user services. There is no claimed drain in today's maintenance marker. Refuse busy/unobservable work unless this invocation explicitly authorizes interruption. Daemon stop can interrupt turns; never retry their prompts. Pinned user-manager tmux may survive, while editor/integration services using replaced runtimes must deliberately restart and be verified. Do not kill unrelated native sessions.

After quiescence, publish the staged config/unit/runtime generation and `current` selection with journaled recovery, restore boot gates/listeners, start components and verify **actual running** gateway/broker/daemon/runtime bytes and cold requests on both sockets. Build qualification must assert runtime-lock Node/Pi pins match the executable's required versions. Installed acceptance must exercise the production mapped-UID daemon startup path, which already validates Node/Pi before publishing handlers (`internal/daemon/handoff_linux.go`, `pi.validate`). Verify that path rather than adding a second validator or starting a model conversation. Keep admission closed until structural/security acceptance passes. Preserve homes, UID/GID bindings, admission/admin/session data, native credentials and histories. Post-upgrade human/provider tests are reported separately; they cannot be turned into synthetic passes.

**Rollback policy:** before activation, failed staging leaves the predecessor serving and removes only verified operation-owned temporary bytes. Once services stop or the generation switch begins, failure leaves the host in closed maintenance with inspectable evidence; do **not** automatically switch binaries back or restore data. The first supported path is fix-forward/re-run of the same qualified target after diagnosis. Retain the predecessor generation during the operation for comparison, but make no downgrade guarantee. Any future binary rollback needs explicit bidirectional format/runtime compatibility and restored running-byte checks; restoring an old broker ledger is never rollback. This deliberately trades availability for unambiguous identity/state safety and matches the existing upgrade issue's no-automatic-rollback scope. A separate `/home` volume is no justification for stale identity restoration. No backup/restore stack, arbitrary legacy migration or user deprovisioner is added here.

### 7. Agent contract and limits of language-model assistance

Short reads/plan use the existing `{schema_version,data,warnings}` envelope and stable check/action/reason codes. Failures are structured on stderr: exit 1 for actionable invalid input/conflict/failed policy, 2 for I/O/dependency/internal failures, 130/143 for cancellation. Observation unavailable is never empty, unlimited or healthy. No-change convergence exits 0 with `changed:false`; a plan can contain needed work without failing, but blockers fail explicitly with the available structured assessment. Logs never include secrets, raw provider output or home content.

Long prepare/apply/upgrade use explicit `--output=jsonl`: sequenced schema-versioned progress and exactly one result/error/cancelled terminal event when possible. They reject single-document `--json` in favor of the stream and `host operation show --json`; missing terminal output means unknown outcome requiring observation, not automatic replay. Fatal stream error carries the error class; stderr retains the structured fatal diagnostic. No TTY detection, prompts or spinners. Expose dry-run, structured drill-down help, effective config provenance, version/build SHA, bundled operator skill and per-check remediation. Test injected clocks/IDs and canonical site formatting without falsifying live receipt provenance (canon §§19–21); retain the Go CLI/domain split, not a new language runtime. Update CONFORMANCE.md honestly when implemented, not to claim these planned capabilities already pass.

An LLM may explain a blocked plan, diagnose sanitized observations, propose a site change, choose a maintenance window with its owner, or recommend fix-forward steps. Deterministic code must authenticate releases, validate inputs, resolve profiles, enforce authority/quotas/permissions, decide safe resumability, apply operations and classify observed results. No model-generated shell is executed as part of apply. Neither mail/repository text nor an LLM's confidence grants root approval or human OAuth consent. Agents operate many hosts by invoking this contract, not by replacing it.

## Delivery and acceptance

The four existing issues carry this decision without creating a second installer:

| Issue | Contract it implements |
|---|---|
| @deliver-install-initialization | Site schema/config/provenance and host check/plan/apply foundation, immutable generation, crash-safe empty initialization and idempotent site convergence; integration with the preparation gate. |
| @deliver-install-host-preparation | Separate ext4 `/home` UUID/quota baseline, explicit prepare, EDQUOT, host-wide proc policy, fail-closed cold-boot/ACL/both-socket gates and user-manager checks. |
| @deliver-install-runtime-profile | Authenticated release/profile manifest and complete pinned closure, bootstrap verification/materials, selectors/wrappers, optional tools and inventory-fed engineering profile; correct obsolete Pi instructions. |
| @deliver-independent-upgrade | Named successor staging/quiescence/adoption, operation recovery, failure-closed fix-forward policy and preserved native state; no automatic rollback or watcher. |

Initialization supplies shared operation/plan primitives; the other slices extend them rather than inventing their own state or output formats. Before either pilot is offered as a supported multi-user host, use only shipped materials on a fresh customer VM: independently verify bytes and effective isolation/quota, real consenting first use, distinct-user isolation, cold reboot, then a second named release with interruption/failure-injection and actual adoption checks. Repeat on the second server without importing the first agent's workaround transcript. The existing independent-installation experiment owns that evidence. This ADR neither provisions those machines nor claims their tests have passed.

## Evidence and rejected scope

Repository sources inspected: root/internal/docs AGENTS.md; `docs/operations.md`; `CONFORMANCE.md` and AI-first CLI canon v4 §§1–24; `scripts/package-release.sh`, `scripts/prepare-test-release.sh`, `scripts/verify-release.sh`; all shipped `systemd/`, `sysusers.d/` and `tmpfiles.d/` templates; the full independent-installation assessment and the four delivery issues. Current packaging verifies a deliberately narrow inventory and ships no native runtime or initializer; templates expressly leave boot ACL/quota preparation to the installation. These are gaps to implement, not hidden prerequisites to outsource to an agent.

Primary documentation consulted 2026-10-22:

- [Ansible check/diff semantics](https://github.com/ansible/ansible-documentation/blob/devel/docs/docsite/rst/playbook_guide/playbooks_checkmode.rst): unsupported modules do nothing/report nothing in check mode; sensitive diffs need explicit suppression. This limits a claim of dry-run safety, not Ansible's usefulness as a controller.
- [Debian Policy, maintainer scripts](https://www.debian.org/doc/debian-policy/ch-maintainerscripts.html): scripts must be idempotent and handle failure/unwind paths. Apt does not remove the need for our transaction design.
- [cloud-init first-boot determination](https://github.com/canonical/cloud-init/blob/main/doc/rtd/explanation/first_boot.rst): per-instance/per-boot distinction and cached identity explain why image bootstrap is not installed-host reconciliation.
- [ext4 filesystem options](https://man7.org/linux/man-pages/man5/ext4.5.html): quota feature/mount requirements justify a narrow checked baseline and explicit offline preparation rather than an inferred mounted conversion.

We reject a fleet service, bespoke storage layer, automatic cloud provisioning, copied personal workstation settings, platform-wide sandbox claims and automatic state rollback. None is needed to deliver the two pilots through an interface that another fleet controller can reuse.
