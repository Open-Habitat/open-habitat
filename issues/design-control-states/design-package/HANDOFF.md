## Adopted as design direction

- The returned control sheet covers the applicable rest, hover, press, focus, current/selected, disabled, pending and error presentations by family, in both themes and at desktop/touch widths. It replaces the old universal 18 × 10 table. Selected location uses a neutral surface; focus is visible; hover/press deepen a variant rather than turning it into a selection; pending retains contrast and conveys progress in text when motion is reduced.
- Navigation and agent presentation use separate channels for activity, new attention, browser capability and operation/transport result. A visited waiting agent remains waiting; a visited error remains on the row without staying in the attention section. Read-only is a dashed tag rather than the waiting ring. An unknown process is not a closed or crashed agent.
- The returned navigation/settings composition remains the target from the previous handoff. Its revised state examples replace the previous examples; earlier draft versions remain in Git history. [Visual pairs and limits](comparison/NOTES.md) record the changes.

## Reconciled with the existing design

The response says every disabled control shows a reason below it and proposes making every disabled button focusable with `aria-disabled`. The existing design avoids button instruction text, while an unexplained blocked action is not usable on touch or with a keyboard. **Agreed resolution:** show a concise reason next to a blocked action when the reason is not evident from its context (connection loss, read-only, pending receipt); do not add repetitive text for an empty composer. Expose that reason to assistive technology. Choose focusability and event suppression for the actual React Aria control rather than a universal `aria-disabled` rule. The new control sheet's explanation and empty-send example were corrected accordingly; example rows for non-obvious blocks retain their visible reason.

The response proposes removing pending/acknowledged sentences. The design keeps its quiet acknowledgement rule, but only where the result is actually confirmed and visible in the conversation; a pending command, unconfirmed interrupt or lost send acknowledgement must still be intelligible and must not appear as success. Any shortcut that drops the only status feedback is rejected. Its `checking` state is conditional on the separate @recover-sends-after-disconnection work and does not authorize resend.

## What the returned prototype cannot establish

- `confirmed_exited` does not prove intentional closure; the `valmis` example requires a positive closure fact. Shared per-conversation visited-event attention is not yet available. A terminal agent's last assistant message alone is not proof of waiting. A provider-error tag requires a reported failure. The `Hostin faktat` switch is a synthetic illustration, not proof that the present host can produce every row it draws. Product mapping must fall back to unknown or omit unsupported attention/operation facts.
- The proposed `AgentPresentation` shape, four status components, tokens, CSS replacement and disabled-button event API are **implementation suggestions**, not accepted signatures. `web/src/components/` and shared tokens remain unchanged by this handoff; @apply-control-state-design owns implementation, story/lab coverage and a draft-vs-production comparison. Its start needs a separately prepared next action under the work-session gate.
- The response's colour-ratio table is a useful design calculation, not an independent accessibility or 200% zoom test. The proposed field border is under the 3:1 non-text threshold; verify that the field boundary and focus/label treatment remain perceivable in implementation. No lab path exists yet for all attention combinations or interaction states; the original 24 state / 96 presentation gaps are not retroactively closed by a design prototype.

There is no independent new product promise to file from this package. The positive closure fact and shared attention marker are prerequisites of the already planned presentation mapping, Pi questions belong to @show-pi-dialogs, and send reconciliation belongs to @recover-sends-after-disconnection. If implementation finds they require separate work, scope it explicitly before claiming these states shipped.
