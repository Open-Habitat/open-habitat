# Conversation v2 slice — result

The v2 conversation presentation now uses the shared frame, sizing, button, SVG and status-mark primitives. Speaker labels have quiet icon-only copy controls with accessible names; the header's details button is quieter; the working composer exposes Keskeytä, Ohjaa and Lähetä directly while Enter retains the last selected queue mode. Rejected text remains in the editor, unknown queue status remains inspectable, and the return-to-latest control appears when the reader moves away from the bottom. The interrupt confirmation is next to the composer and receives focus. The app still owns native control, receipt handling and reading position.

## Deviations from the handoff and host requests

- Keep the long-title disclosure: `production-v1.md` promises access to the full 160-character title by keyboard, not only hover/title attribute. Keep explicit control/activity states in the header as required by `docs/ui.md`, rather than hiding the ordinary status. Keep Enter's selected steer/follow-up mode, despite removing the visual radio group; removing this tab-level choice would change keyboard behavior. Keep one app-level disconnection banner and the existing explicit status/reconcile action. Do not auto-scroll an active reader on open.
- The native history entry has no confirmed turn-completion boundary or time. A completed assistant message is **not** a confirmed completed turn (an intermediate tool-use message may precede the answer). The component has a `streamState="complete"` story for the intended success marker, but the host-backed view deliberately does not fabricate “✓ Vuoro valmis … · odottaa viestiäsi”. Request for the daemon/adapter: expose a proven turn-settled marker and timestamp in the browser's validated conversation view model; coordinate with the separate agent-control work before wiring this to history. No `internal/` or `contracts/` changes here.
- The currently supported browser conversation view does not expose a structured incoming question/request ID or response capability. The `SupportedQuestion` production component has a story, but the host-backed synthetic lab cannot produce this state; request a validated question view model and supported reply capability when the agent-control contract is ready. Likewise the read-only history has no verified `create` capability on that resource; show the honest read-only reason, not a synthetic “Uusi keskustelu” action. No fake question or control was added to production.
- The current ambiguous-send flow has only a tab-local uncertain marker and explanatory notice: it does not have a verified command-ID/result/reconcile view model to safely attach a message-level uncertainty bubble. Keep the disabled draft and existing explicit status check. Request the verified acceptance/result plus command ID from the conversation controller before placing a per-message card; never infer acceptance from a crash or retry automatically.

## Synthetic evidence

Paired `.png` and offline `.html` snapshots in this folder: `empty`, `working`, `completed`, `rejected`, `uncertain`, `disconnected`, and `read-only`, each in `light`/`dark` at 1440 and 390 px. Captured using `web/lab/session.mjs` against the isolated fake OAuth/Pi lab; the text, agent IDs and identities are invented. `completed` means observed idle after a fake-Pi answer, **not** proof of a per-turn completion boundary. Incoming-question evidence cannot be captured until the lab/controller produces a validated question. No real account, profile or native home was used.

The component stories in `web/src/components/ConversationStates.stories.tsx` cover empty, working, read-only, interruption, completed marker, incoming question, rejected and uncertain sends; Storybook's theme toolbar renders each in either theme. The lab metrics assert speaker text size, copy glyph, tool border and details icon in addition to the foundation's rail/column/padding/focus metrics in both themes and widths.
