## Provision stage and branch assessment

`internal/gateway/auth.go` has **two** `broker_denied` callback branches. First, `Exchange(ensure)` returns an error or a reply failing `brokerIdentity` (missing route, zero counters, invalid UID/name/socket). Second, after a successful ensure **and** successful token delivery to the native sink and generation of session/CSRF secrets, `Exchange(authorize)` errors, has an invalid reply, changes epoch/binding or regresses generation. Only then is a session cookie issued. The gateway logs the same reason for both branches, and does not record broker operation, transport outcome or reply failure class. Worse, `internal/cli/cli.go`'s `gatewayBroker.Exchange` currently collapses a valid `state_unavailable` reply **and** transport errors to `ErrBrokerUnavailable`, and other failure replies (including `denied`, `name_collision`, `drift`) to `ErrTransport`; the gateway cannot recover the original broker failure enum from its present interface. The observed event alone cannot identify which branch ran.

**Strong inference, not a proven branch:** the *first* (`ensure`) branch is consistent with the unchanged generation 1 and zero bindings. In the normal `Writer.Handle` path (`internal/provision/writer_linux.go`), a successful first ensure must durably publish a binding (incrementing generation) before socket readiness, reauthorization and a routable response; the second gateway branch would require such a route and a successful token delivery first. No published binding or JIT account is present after the attempt. Therefore the second branch conflicts with the observed state **unless** state was subsequently replaced/rolled back outside the writer, evidence came from a different attempt/installation, or the deployed behavior differs from the inspected source. No transaction-correlated broker record or independently attested continuous state history excludes those alternatives. Do not claim a proven exact branch or an observed host guard failure.

The first branch itself covers distinct failures:

- **Transport/admission:** `internal/provision/transport_linux.go` validates a root-owned Unix socket and server peer UID, frames and strict request/reply protocol; the server silently closes for wrong gateway peer UID, malformed frame, capacity admission, deadline or cancellation. Client maps dial/peer/framing/parse failures to `ErrTransport`. A running broker/socket at later inspection does not rule out an earlier admission or connection failure. Broker service start/stop activity in the broad window makes temporal correlation important, but is not evidence of causation.
- **Broker policy or candidate refusal:** `Writer.handleLocked` rejects missing allowlist identity (`denied`), unreadable/unstable state or markers (`state_unavailable`), unsafe/colliding Unix name (`name_collision`), and availability/host drift (`drift` or `name_collision`). `githubLogin` accepts some provider handles that `username` rejects; an operator-approved alternate is required in that case. The matching ID and marker-free later state weaken simple allowlist/mid-publication explanations; they do not test the specific provider candidate, concurrent state or host occupancy at the request time. No name or provider identity is published here.
- **Host-side pre-publish checks:** the executor's `Available` inspects NSS name/UID, supplementary groups, home/config/socket vacancies, parent ownership/ACL and inactive instance units **before** `pending.json` is written. A refusal here can leave the precise empty snapshot seen. Once `pending.json` is written, failed subsequent steps normally leave a pending marker; after publication, readiness failure normally leaves a binding. Absence of both makes pre-reservation refusal or no admitted ensure more consistent than a late host step, but does not choose between them.

`Store.Evaluate` is explicitly a legacy policy-only probe, not the production broker handler and not a safe substitute for diagnosing a live ensure. No broker `ensure` or `authorize` was sent during this investigation.

First preserve the validated reply failure enum (or a safe typed classification) across `internal/cli/cli.go`'s gateway adapter; the current collapsed errors cannot distinguish transport from policy refusal. Distinguish `transport`, `invalid_route`, `reply_denied`, `reply_state_unavailable`, `reply_name_collision`, `reply_drift` and `binding_changed` without changing the fail-closed response or session semantics. Use only the already server-generated attempt ID at the gateway; never log subject, candidate, UID, route, socket, raw errors, response frames or token. Preserve the generic browser failure.
