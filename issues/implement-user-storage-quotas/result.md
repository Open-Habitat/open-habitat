## Product implementation

The broker selects a committed bound UID and applies the gateway-supplied default hard limit before publishing a new account, journals incomplete provisioning, and fails closed when kernel quotas or an existing bound limit become unreadable. Bound-account quota read/set remains possible after admission revocation without readmitting that account. The broker uses `quotactl_fd` on host-selected `/home` with an O_PATH descriptor, compatible with `PrivateDevices=yes`, and requires both quota **accounting and enforcement** (`Q_XGETQSTATV` flags) at startup, before account mutation and on native reads/sets. Native kernel quota state is the only usage/limit record.

Gateway and root CLI share the durable default and per-bound-user limit writer. Administrators see limits, usage, filesystem capacity/free space and overcommit; people see only their own quota. Browser and root CLI use strict versioned storage contracts, aligned 1 MiB–1 PiB byte limits and GiB input. Daemon clone admission checks its own effective UID, native hard limit, usage and filesystem free blocks, with no legacy `~/src` source image or 20 GiB cutoff. Remote clone size cannot be known before download; kernel EDQUOT is final. A confirmed full quota has a distinct clone error and browser explanation. Product commit sequence on the rebased branch: `b939b7c`, `e196897`, `2c0c62f`, `fa3a628`, `f65539c`, `371e295`, `dff4c30`, `9cca124`, `f601a87`, `5ce90ff`, `eadac53`, `543f5cf` (with earlier issue progress `0a7a915`). Fleetrepo fix `49312717` excluded exactly that guest-owned unit from product stop/start, retained refusal of unrelated enabled units, passed 185 tests, and was pushed. A fresh pinned-root official preflight still refused. Read-only diagnosis showed that the fresh-install receipt pins the original six-file JIT policy digest `bb0d048b27b11d984fd35acc221e1344fe9b7753902aac7b97767b21f7770054`, while all six installed policy files match current pushed Fleetrepo main at digest `5deaa615c922ab5ce31f8b7d2da9b17c3fc28815b5e08bed57fbb5895540fac8`. Earlier gate-helper path repairs legitimately changed those bytes *after* fresh select without a successor-recognized policy transition. The old receipt must not be silently rewritten or the check bypassed. The latest guest inventory and evidence were pushed to Fleetrepo main (`dd969071`).

**Recommendation needing trust-chain agreement:** implement an explicit root-only, read-only-preflighted policy-transition receipt linking the original fresh receipt digest to the reviewed pushed-Fleetrepo policy bytes, with no branching or acceptance of unknown installed content. Only then retry the official successor chain. A clean OS rebuild is the simpler trust model but here would entail another offline quota setup and an origin CA/Alder shared-ingress change, outside this run's no-shared-service-edit constraint. Do not disable the quota enforcement unit to satisfy the successor.
