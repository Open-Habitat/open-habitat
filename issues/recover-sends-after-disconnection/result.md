# Result — recover sends after disconnection

Implemented on the committed tree `282ba49e323271a6c72c3e6a5980b9321f6ce798` (2026-10-05). HTTP snapshot failure disables new conversation sends while preserving the view and draft. SSE failure alone leaves HTTP writes available. Outstanding commands retain their original ID; a successful HTTP snapshot checks the original daemon status/receipt without waiting for a conversation event or reposting the message. Accepted and rejected receipts settle the send; pending remains pending; an absent receipt or lost daemon controller remains unknown, not rejected. An edited draft is never cleared by a later acceptance. The current behavior is documented in `docs/architecture/events-and-recovery.md`.

## Limits and failures resolved

The first clean gate stopped at an outdated implementation-plan validation rule. The next reached 128/129 browser passes but exposed a layout-test race: it measured the feed before the editor was ready. A repeated focused run passed 3/3 after the wait correction. The third clean gate passed browser, Go, contract and packaging checks but failed final issue doctor because CI pinned issuectl 0.18.4, which could not parse the current schema; pinning the verified 0.19.0 release made the final clean gate pass. Earlier focused checks initially failed on assertions that assumed the empty draft enabled Send or an empty feed list was visible; those test assumptions were corrected and retested. Model-performance corpus logging was attempted but SSH-to-self on alder rejected the key (permission denied); this advisory logging failure did not affect review evidence or product validation.

The browser scenarios use synthetic host routes, not a live daemon restart or real account credentials; the gate's same-UID browser host does not prove distinct-Linux-UID isolation. No new daemon or gateway authority was introduced. A missing receipt intentionally leaves the original command unresolved rather than authorizing a silent replay.
