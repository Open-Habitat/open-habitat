# Native gh JIT handoff — implementation receipt

**Clean product revision:** `2b6a97c04fc305f57a6979671c5dc78885f244cd` (committed tree, no tracked or untracked changes at the gate). This is app-level integration with dynamic gateway route from `7018ee9`, not host activation.

The gateway already obtains a broker `ensure` route after GitHub `/user`, sends the OAuth token only once over the mapped daemon UDS and rechecks `authorize` before issuing a session. Its session-backed requests reauthorize on every use. The sink validates the mapped socket pathname and kernel peer UID (systemd-owned root socket), while the daemon checks gateway kernel peer UID. This issue adds daemon-side reread of the root-owned `0640` per-UID numeric binding file before each handoff, with fixed path, `O_NOFOLLOW`, root owner/group and complete strict config equality. The broker executor now emits that binding path; legacy static handoffs without the new field retain their prior contract. The native gh adapter serializes installations and disconnects for a daemon UID, refuses to overwrite a preexisting status-success gh account unless numeric API identity, HTTPS helper and storage all verify, and reobserves rather than installing twice. Unknown/partial identity denies session and leaves reconciliation to the operator. Neither the root broker nor browser cookie, argv, environment, log or retry queue receives the token.

## Security review and assessment

The first claim proposed automatically replacing a partial gh login; this contradicts the fail-closed reconciliation requirement. ## Limits / later gates

No Fleetrepo write, host activation, fixture listener, live credentials, real-person OAuth, private UID pool, new two-UID JIT guest, ingress or deployed version proof. A fresh OAuth flow after a failed handoff still requires explicit inspection/reconciliation of any partial native credential; do not retry the same token. A legacy *broker-created JIT* config from an older build would not match the new serialization and requires an operator-reviewed migration if such a binding is later discovered. Fleetrepo private declaration/UID pool and guest/pilot consent remain separate prerequisites. Existing Unix users and running agents were not touched.
