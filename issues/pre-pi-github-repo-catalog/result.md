# Pre-Pi GitHub repository catalog

The authenticated gateway now has exactly one read-only pre-Pi listing route: `GET /api/v1/onboarding/github/repos?page=1..100&limit=1..50`. It rechecks the broker, dials the mapped daemon socket and reconstructs a validated allowlisted response. The daemon checks its trusted peer and immutable subject binding, runs `gh api --method GET /user` to bind installed native authorization to that subject, then queries `/user/repos` with owner, collaborator and organization_member affiliations. It neither accepts a browser token/owner nor reads workspaces or Pi history. Existing snapshot/history/conversation mounts stay behind their Pi gate. Commands inherit no secrets, have bounded stdout and deadline, discard stderr and kill child process groups on cancellation. Responses are no-store; native failures return fixed errors.

Evidence (this branch, before clean CI): focused `go test ./internal/gateway ./internal/daemon -run 'TestGatewayRepoCatalog|TestRepoCatalog' -v`, scoped `go vet`, and contract fixture validation passed. Synthetic gateway sockets tested distinct mapped identities, forged routing headers, malformed daemon output and the Pi-gated snapshot. Daemon tests covered private organization/collaborator projections, malformed JSON, rejected missing auth and two separate disposable credential homes invoking a real fake-gh subprocess. Those homes run under one unprivileged test UID, **not two kernel UIDs**. The gateway and subprocess tests are separate synthetic layers, not a single real gateway→mapped-UID daemon→gh guest. No real GitHub account, live host, browser flow, release or deployment was exercised. A full cross-UID guest proof remains needed for the broader @github-repos-first-onboarding acceptance.
