# Worktree agents in the browser — proposal for Jari, not an accepted decision

3 October 2026. Scope: the browser journey and the launch/control boundary for [this decision](item.md), feeding [manage-agent-worktrees](../manage-agent-worktrees/item.md). No host or Taskfleet integration was changed here.

## What exists and what it implies

The host discovers immediate directories under `~/src`, including recognizable linked Git worktrees; it does not register workspaces or follow worktrees elsewhere. Pi history is indexed by its native session ID and exact header `cwd`; the browser lists histories in their discovered workspace. A browser-owned conversation is a Pi child started by the per-user daemon in RPC mode, with an ownership lock and in-memory handle. Only that child accepts browser sends, steering, questions and aborts. A terminal Pi file can be read but cannot be attached to in RPC mode. After a daemon restart the handle is gone; even an ended conversation is continued only when the browser-origin lock, workspace and unique native history prove it safe. Seeing a terminal process or a matching branch is not a control proof.

Taskfleet 0.11.6, as installed, creates a run with a full run ID and node ID, a worktree/branch, a supervisor and a worker. `run create` requires a kind and title and either `--task` or `--prompt-file`; a profile is optional (without one, Taskfleet uses its selected harness). A browser journey would fix the kind to `spinoff`, supply a title and task, and preflight the actual create inputs with `--dry-run`. `--interactive` changes supervision semantics but does **not** make a worker browser-controllable. `run show`, `run list`, `node list/show` and the event log expose native state. `status` is progress; `lifecycle` is fixed `autonomous` or `interactive`, not progress. `run merge` is Taskfleet's successful merge/report/teardown path; `cancel`, `salvage` and `discard` have different effects, with retained work requiring deliberate disposal. The CLI offers `--dry-run` and `--idempotency-key`, but no documented create-without-worker or placement flag. Workmux's **default** directory is the sibling `<project>__worktrees`, with run checkouts one level inside; for a parent at `~/src/foo`, these are not immediate `~/src` workspaces and their Pi history will not appear in the current snapshot. Workmux documents a configurable `worktree_dir` (relative to repo root or absolute): a configuration such as `..` could place a checkout directly under `~/src`, subject to verification and collisions. This repository's `.workmux.yaml` does not set placement; a user's effective global configuration was not inspected. These are capability observations, not a claim that Taskfleet's current CLI supports the proposed design.

Evidence: `docs/architecture/{identity-and-trust,workspaces,conversations,http-api}.md`, `docs/decisions/adr-0001-unix-native-agent-host.md`, `internal/daemon/{discovery_linux.go,snapshot_linux.go,history_linux.go,conversation_linux.go,pi_rpc_linux.go}`, `web/src/app/{WorkspaceRailView,BrowserConversation,HistoryView,ConversationActions}.tsx`, `web/src/components/Navigation.tsx`; installed `taskfleet --help`, `taskfleet run --help`, `taskfleet run create/list/show/merge/cancel/salvage/discard --help`, `taskfleet node list/show --help`, and `taskfleet-overview` v0.11.6; `workmux config reference`, `.workmux.yaml`, and `systemd/native-agent-host-daemon@.service`. CLI help and source were read, not a live personal run or real session.

## Journey to implement after the boundary is agreed

- From a **Git parent workspace** choose “New worktree agent”, provide a task and required human-friendly title. Explain that Taskfleet selects the final branch/worktree name; do not promise a chosen final branch. Show why creation cannot start (not Git, Taskfleet missing/incompatible, destination not safely discoverable, run capacity, etc.) before offering the action. Submit once, then show “creating / outcome uncertain” until a fresh native observation ties the full run ID + node ID to a worktree. An interrupted browser request is **not** permission to create another run automatically. Recover by listing runs and worktrees with the exact returned ID or a proven idempotency-key retry/lookup (key semantics need synthetic verification); otherwise ask the person to inspect the ambiguous creation rather than guessing by branch suffix. Taskfleet's `run show --current` resolves exact canonical worktree-path and branch ownership inside an owned worker worktree; verify its applicability from the daemon's checked directory instead of building a second ownership database.
- In navigation, put the worktree agent **under the parent Git workspace** (not as an unrelated top-level project), with a link to the worktree's own workspace context. A badge “Worktree · branch …” and a small parent breadcrumb make the relationship visible in both places. The worktree has a separate cwd, Pi session and history; it is not the parent's conversation. With the default workmux sibling layout, **no** Taskfleet-created checkout of a parent immediately under `~/src` becomes a discoverable worktree workspace: the `<project>__worktrees` container can instead appear as an ordinary directory. Show the run in a parent run list with “worktree outside accessible workspaces”; neither its terminal Pi history nor the worktree conversation is currently available there. This placement gap must be resolved in implementation, not by inventing a workspace registry.
- Opening the row goes to the ordinary conversation layout and history. State is a **combination of separate facts**: Taskfleet run pending/running/done/failed/cancelled and node identity; Git checkout/branch present, absent or uncertain; Pi history readable or not; Pi process running/unknown; browser control available/read-only/uncertain. “Taskfleet running” alone never enables the composer. A running terminal-only agent shows its readable history, terminal ownership and “Read only — opened in terminal” **only if** its cwd is safely discoverable under the current history rules; in the default sibling layout it has a run card but no browser history. A browser-owned RPC agent in a verified, discoverable worktree enables the existing send/steer/abort/question flow. If the run completes, keep its Taskfleet report visible; don't claim the worktree still exists after teardown. **History retention is a separate gap:** today the snapshot attaches Pi history only when its `cwd` exactly matches a currently discovered workspace (`internal/daemon/snapshot_linux.go`). Teardown can make that conversation disappear from the browser even though Pi still has the JSONL. Keeping completed-run conversations findable needs a verified run/node-to-Pi-session binding in Taskfleet's native record and a safe history-read route that does not require the removed workspace; until then show “history unavailable here”, not a false promise that it was deleted or that the browser can reopen it. A stale Taskfleet observation and a lost daemon control handle remain explicitly stale/unknown.
- Distinguish “Stop this conversation” (daemon Pi control) from “Cancel run” (Taskfleet lifecycle), “Merge work” (Taskfleet success/report path) and “Discard retained work” (destructive Taskfleet action). Do not let stopping a Pi child imply run cancellation or deleting a worktree. Before merge/cancel/discard refresh exact run/node/worktree ownership and live writers; on unknown/manual worktrees, offer read-only inspection, not cleanup. If creation got as far as a worktree but not an agent, show the retained run and offer a supported explicit start/recovery action, not another hidden create. If a Pi start succeeds but the response is lost, reconcile its native handle/history before presenting a second start.

Basic run/worktree/agent identity and lifecycle belong here and in manage-agent-worktrees. `expose-native-status` remains responsible for richer profile/model telemetry and tmux/worker bindings; it must not be a dependency for an honest basic run state.

## Launch and control options

| Option | Authority and user isolation | Failure and cleanup | What manage-agent-worktrees would implement |
|---|---|---|---|
| **A. Daemon invokes the existing Taskfleet CLI as its Unix user; Taskfleet starts its usual terminal worker.** Gateway still only routes, daemon requests Taskfleet creation, Taskfleet owns run/worktree and terminal worker, Pi owns history. Per-user execution and Taskfleet home/config must be bound to the daemon's actual UID/home; browser cannot supply a UID, CLI path, arbitrary command/profile executable or another run's ID. | Taskfleet owns cancel/merge/discard, but partial creation and lost replies require read-only run observation and verified ownership. The terminal worker is never browser-controllable. A daemon restart can also kill Taskfleet's supervisor/worker if they were started in its systemd cgroup; whether a pre-existing external tmux server changes this cannot be assumed. | Read-only run projection; worktree/history projection only after safe placement/discovery. This is a discovery slice, **not** the requested interactive worktree-agent journey. |
| **B. Taskfleet reserves a run/worktree without starting its normal terminal Pi; daemon starts a browser-owned Pi RPC child there (recommended, conditional on Taskfleet support).** Requires a deliberate Taskfleet workspace-only/worker-binding contract (new upstream capability), or a supported two-phase create-and-start. Taskfleet alone owns run/worktree and merge/retention; daemon alone owns Pi process, lock and RPC; Pi owns session history. No gateway or root process launches agents. Daemon must prove exact run/node ↔ checkout ↔ user-owned discovered workspace before admitting Pi; a branch string is not proof. No custom executable/profile selected from browser input. | Taskfleet already does not infer success from worker exit: only an explicit report/merge finishes successfully. The missing support is creation without a worker PID handshake and supervision of a workspace-only node with no worker PID. Explicit settlement must still be specified. A daemon crash kills its browser Pi child, loses the handle and may also kill a supervisor it started in the same cgroup; the run, worktree and Pi history files may survive, but browser history still depends on placement. Reconcile before explicit continue/restart. Never merge/discard while a browser Pi may still write, and never equate closing the browser or stopping Pi with merging work. If Taskfleet cannot reserve without starting or cannot safely track this lifecycle, this option is **not yet implementable**. | Taskfleet capability negotiation and creation through daemon, read-only reconciliation, the ordinary daemon Pi controller in verified worktree cwd, browser status/controls and explicit Taskfleet run settlement with exact IDs; synthetic partial-create, disconnect, daemon restart, same-UID writer and separate-UID tests. A concrete Taskfleet API change is a prerequisite, not something to fake with killing a just-spawned terminal worker. |
| **C. Taskfleet launches a worker with a browser-controllable Pi RPC bridge.** Taskfleet retains worker launch/supervision and run/worktree (subject to a supervisor lifetime independent of daemon restarts); an explicit per-user control channel gives the daemon exclusive RPC ownership of that worker. This needs a new supported Taskfleet↔daemon (or harness) handshake, authenticated to the same UID and fenced against terminal and duplicate RPC writers; a tmux PID or history match cannot substitute. The browser never gets a raw socket or CLI. | The bridge must survive browser reconnects, report a lost daemon/channel as control unavailable (not silently reattach), and let Taskfleet preserve/settle the run without double-writing Pi history. Taskfleet alone performs cleanup, after writer settlement. Cross-UID requests remain confined by the mapped daemon socket and native user permissions. | Implement bridge contracts, takeover-free fencing, supervised worker telemetry and recovery as well as the same UI and native reconciliation. More native parity with Taskfleet's ordinary workers, but significantly more coupling and new control protocol surface. |

Any option in which the daemon launches Taskfleet must arrange supervisor and tmux-worker lifetime separately from the daemon service: the current systemd template uses `KillMode=mixed`, and detaching a child process does not move it out of the service cgroup. A user-scope service or another supported lifecycle is a design prerequisite; restarting the daemon must not silently kill or orphan runs. Do not infer external tmux-server ownership from a particular user's session.

“Browser takes over a terminal worker” is **not** a fourth ready option: Pi RPC cannot attach to a terminal TUI; the host's lock does not fence it. Making takeover real would require changing Pi/harness semantics and proving one writer before control. A new browser-owned Pi alongside the terminal worker is another agent in the same checkout, not control of the Taskfleet worker, and would risk concurrent changes.

## Recommendation and decision needed

**Recommend B** for the first interactive browser journey, *subject to a supported Taskfleet reserve-without-terminal-worker and explicit run-settlement contract*. It preserves the existing per-user daemon Pi RPC safety and native conversation UI, and avoids inventing a terminal takeover. It pays for a Taskfleet workspace-only lifecycle extension and independently supervised Taskfleet process lifetime, and gives up a single Taskfleet-supervised Pi process: Taskfleet owns the worktree/run, the daemon owns the browser Pi. We should not represent this as agreed architecture until Jari accepts that division. If Taskfleet cannot support it without becoming a second process owner, return to C with a concrete handshake proposal rather than ship A as though it met the goal.

Questions for Jari:

1. **Do you approve Taskfleet owning run/worktree creation and settlement while the per-user daemon owns a separately launched browser Pi child in the verified worktree (option B), including a new supported Taskfleet workspace-only/explicit-lifecycle mode and supervisor lifetime outside the daemon service cgroup?** Or must the browser's worktree agent be the actual Taskfleet-supervised worker (option C, larger bridge)?
2. **Should the first version allow browser creation only for runs whose worktrees can be safely opened under `~/src`, with outside/manual worktrees shown read-only, pending a supported placement/discovery solution?** Existing Taskfleet CLI help does not promise placement under `~/src`, but workmux exposes `worktree_dir` configuration. Should deployment configure per-repository/global placement for these runs, or should the host safely discover one more level under the native sibling directory? Resolve collisions and existing work either way before enabling create. Do not silently relocate or adopt native work.
3. **For an interactive run awaiting settlement or a non-terminal attention-required run, should merge/salvage be exposed in the browser, and for failed/cancelled retained work should discard be exposed, or should v1 show state and leave finalization to the native Taskfleet CLI?** Either way use Taskfleet for finalization, with exact owner evidence; read-only must not be mislabeled “done”.

Pending answers, `manage-agent-worktrees` can map contracts, prepare synthetic Taskfleet fixtures, and design the status/uncertainty UI, but must not lock a launch/cleanup authority in code. After agreement, record the accepted boundary in an ADR or architecture decision and update affected contracts, docs and issue result. Additional work outside that issue: if B is accepted, an upstream Taskfleet workspace-only/explicit-lifecycle capability, verified idempotency-key recovery where available, and a run/node-to-Pi-session binding to preserve findability after cleanup; if C is accepted, an upstream controllable-worker handshake and fencing protocol. The host's safe post-teardown history projection may require a separate implementation slice if it does not fit manage-agent-worktrees. These are proposed follow-ups, **not filed or scheduled** here.
