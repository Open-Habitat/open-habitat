# Pi browser OAuth capability proof — negative on installed 0.85.1

**Decision:** stop host implementation. The installed provider cannot provide a manual-only browser flow with mandatory redirect/state verification. This is a proof of the *absence of the required capability* in the pinned artifact and a reproducible unsafe baseline, **not** evidence that a proposed patch works, nor approval of the first-use host security architecture. No product code, global installation, real credential, browser profile or live OpenAI endpoint was changed or contacted.

## Reproduce

From the repository root, on a machine with the exact installed package at the pinned paths:

```sh
node issues/prove-pi-browser-auth/proof.mjs
```

Node v22.23.2; installed `pi --version` and `@earendil-works/pi-coding-agent/package.json` both 0.85.1. The script verifies package version and SHA-256 for `dist/core/model-runtime.js` (`32cd50599d9e6e001229090e3d0554b60e4addb8ab7b3165635a574feb660b74`) and `node_modules/@earendil-works/pi-ai/dist/auth/oauth/openai-codex.js` (`41432753ef2ec7ef21c577fdc8f83b731c78be90c10ed8e7e1df7010f84d198f`) under `/home/maintainer/.local/lib/node_modules/@earendil-works/pi-coding-agent/`; it fails closed on a different build/path. `dist/core/auth-storage.js` inspected SHA-256 `0b45029901579032b19273a1427f63b622df8e1aaf9ea185eb932c0d4898998c`. The executable intentionally does not modify the installed sources. It uses a fresh `/tmp/pi-browser-auth-proof-*` HOME and `PI_CODING_AGENT_DIR`, explicit fresh auth paths under synthetic contexts, offline Pi mode, and a global `fetch` replacement that asserts the sole allowed URL is `https://auth.openai.com/oauth/token`, returning a fabricated JWT and credentials without sending a request. A child process is given only synthetic HOME/agent directory and fake auth path. Test homes are removed in `finally`.

Observed transcript (2026-09-27):

```text
PASS baseline: bound-port fallback exchanges bare code with no state (UNSAFE)
PASS baseline: missing state, wrong origin/path, duplicate state accepted; wrong state rejected (UNSAFE)
PASS baseline: operation abort alone does NOT settle prompt; explicit prompt release required (UNSAFE)
PASS ModelRuntime: synthetic native provider writes 0600 in isolated authPath; other synthetic context is empty
PASS ModelRuntime: committed credential can coexist with rejected login; never blindly retry
PASS cross-process: logout does not fence pending child login; no credentials printed
PASS proof completed (negative for manual-only capability; no live provider request)
```

The negative provider cases bind a **test sentinel** to `127.0.0.1:1455` briefly, forcing the unmodified provider's `startLocalOAuthServer` bind failure. The sentinel is *not* a proof that Pi refrains from opening a listener: Pi attempts to bind and falls back to manual entry. Do not run this executable alongside a real login on that port. The pending-abort test releases the prompt explicitly after observing that outer abort does not settle it; otherwise the provider's `finally` cannot run. The script proves a timeout must be enforced by a helper that can terminate/join its process, not that Pi's abort alone is reliable. All credential strings are synthetic; the child stdout/stderr is checked for its synthetic credential marker.

## Source-based contract and gaps

The installed `README.md`, `docs/providers.md`, `docs/sdk.md`, `docs/custom-provider.md`, `dist/core/model-runtime.{js,d.ts}`, `dist/core/auth-storage.js`, pi-ai `dist/models.js` and `dist/providers/openai-codex.js` were inspected. `ModelRuntime.login(providerId, type, interaction)` does expose a Node API, but its interaction has only `signal`, `prompt`, `notify`; there is no manual-only switch. The built-in `openai-codex` provider delegates to `openai-codex.js`, whose browser branch unconditionally calls `startLocalOAuthServer(state)` **before** notifying the auth URL. The fixed redirect is `http://localhost:1455/auth/callback`. A listener bind error produces a no-op server; this is not a supported no-listener mode. `parseAuthorizationInput` accepts a bare code and arbitrary URL origins/paths; the manual branch checks state **only if present** and accepts duplicate state via first-value parsing. Correct-but-stale state is not distinguishable from a current attempt by a host attempt id in this provider; mismatched state is rejected. No TTL, consuming attempt ID, browser session or Unix UID check exists in the native provider. The host must own those bindings and rejection before submitting a value, while Pi must still validate the complete redirect and state. This run cannot prove stale, wrong-session or wrong-UID enforcement because no host binding implementation exists. Two distinct temp *directories* do not simulate two real Unix UIDs.

The provider's listener has state checking for loopback requests but opens TCP on fixed port 1455; the test exercises **manual fallback**, not the listener callback. Provider token exchange/PKCE remain Pi-owned. `ModelRuntime` can run with a disposable `authPath` and isolated model storage (`modelsPath:null`); synthetic provider login stored metadata only in the expected path and file creation mode was `0600`, parent `0700`. These are creation modes, not a defense against pre-existing unsafe permissions or hostile symlinks. `ModelRuntime` serializes one instance's credential operations. The child held a synthetic login while a separate process's parent runtime logged out of the same auth path, then completed: the credential reappeared. This demonstrates why web logout cannot fence an external terminal Pi login. An injected post-file-write synchronization failure made `login` reject despite a persisted credential; report unknown and re-read native status, never auto-retry a code. This injection demonstrates the boundary, not a real filesystem fault. `getAuth` refresh/entitlement and Pi's actual OpenAI subscription/login usability were **not** exercised. Nor was a real SO_PEERCRED, gateway route, CSRF/session/UID isolation or credential-free production logging path exercised.

## Narrow upstream patch proposal (not implemented)

Add a typed, opt-in manual-only browser interaction option in pi-ai's OAuth interaction contract (passed through `ModelRuntime.login`), defaulting to existing CLI behavior. In the Codex browser path, *skip `startLocalOAuthServer` entirely* in manual-only mode and await exactly one prompt tied to the operation signal (abort/timeout must settle without input); never silently fall back to device-code or listener. Validate the pasted input as an absolute URL with exact scheme/host/port/path matching `REDIRECT_URI`, no userinfo/fragment, exactly one nonempty `code` and exactly one nonempty `state` equal to the generated state, and reject duplicates and OAuth `error` results; do not accept raw codes or query fragments in this mode. Exchange via Pi's existing verifier and token endpoint and write via Pi's existing credential store, preserving normal CLI behavior. For a secure no-listener guarantee, test with a port sentinel **and** instrumentation proving `listen` was never invoked; a sentinel alone only proves bind failure. Add deterministic tests for valid URL, bare code, missing/duplicate/wrong state, wrong origin/path, stale prior-attempt URL, cancellation without paste, exchange abort/unknown commit and cleanup; review the patch's public interaction API before distribution. Version/sha pin the reviewed patched package on the deployed host. A host-side validator alone is not an adequate substitute for Pi's state check; neither is a custom Go token exchange.

## Independent security review and stop condition

Proportionate review here is **source-attached, adversarial review by someone independent of the patch author**, once a candidate Pi patch and a minimal synthetic helper exist. Ask them to challenge listener non-creation, state/redirect parsing, abort under pending prompt and exchange/write races, two actual Unix UIDs/peer binding and browser-session isolation. Attach the pinned source/diff and executable transcript, and reproduce tests independently, without live identity. The earlier design review in `issues/design-first-use-onboarding/plan.md` (consult-llm, gpt-6-astra, 2026-09-27) identified abort and cross-process limitations, but did not test a patched provider or host isolation; this proof independently exercises those limits synthetically. A panel or live OAuth test today would not validate a nonexistent patch and would risk overstating assurance. A second review of the *host architecture* is still required with Jari before implementation. Stop until a reviewed and version-pinned manual-only Pi implementation passes the negative tests inverted into positive strict-mode tests and independent cross-UID/session helper tests; do not deploy the unmodified built-in flow, assume consent/entitlement, or claim implementation readiness from this result.
