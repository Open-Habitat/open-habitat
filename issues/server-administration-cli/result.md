# Server administration CLI result

Implemented root-only `admin settings show|update`, `admin users list`, and `admin role update` on the existing private gateway control socket. The gateway authenticates the connecting peer with `SO_PEERCRED`; the CLI separately requires effective root. Browser writes and CLI writes use the gateway's same administration mutex and persistence writer. A grant requires a currently bound GitHub subject; removal works without a current broker binding. `--json` returns schema-versioned data or structured stderr errors, with actionable unbound-target exit 1 and infrastructure failures exit 2. Updates are selective and retry-safe; `--dry-run` validates against current state but cannot reserve a binding or role against concurrent changes.

## Decisions for review

- Reuse `revoke.sock` rather than add a privileged service or socket. Its systemd ownership and kernel peer check already protect the gateway control channel; the root CLI never opens `administration.json` or calls the broker as a substitute writer.
- Expose `admin users list` so the operator can select a numeric subject from an existing binding. `admin settings show` reveals the role set by subject; neither command returns a daemon route, credential or home path. The root operator does not need a browser administrator role.
- Keep mutations as noun-verb selective updates (`settings update --name`, `role update <subject> --administrator true|false`). An empty name clears the setting; a flag-looking name is rejected. Dry-run performs read-only state checks and reports uncertainty about changes between plan and commit.
- The gateway emits bounded control error reasons rather than raw underlying errors or payloads. State I/O, broker unavailability and unbound subjects have distinct CLI diagnostics. A legacy overly long revocation request now closes without a reply, as its existing test expected.
