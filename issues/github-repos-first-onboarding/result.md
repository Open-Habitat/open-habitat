# Browser-first GitHub onboarding: synthetic acceptance evidence

Implementation revision `67682d6db4a4d3aaa92d4c960668728ee77f0965`. The production app shows the shared `GitHubRepoChooser` before Pi when the native Pi status is not usable. The parent binds its transient catalog pages, selection, receipts, pending operations and one-session Pi-step marker to `/auth/session`; the marker is a hash of the CSRF binding, not a repository record. The browser adapter caps responses, validates each v1 schema, and maps errors to Finnish messages without displaying response bodies. A single **Jatka** reads every chosen checkout, writes only for observed absence, and reads again before confirmation. A lost write reply gets one read-only observation; unresolved results stay uncertain and require a separate read-only recheck before another user-initiated attempt. Zero selections move straight to Pi. Pi-usable sessions still proceed directly to the snapshot; workspaces, conversations and history remain Pi gated.

The browser-host test mounts the real gateway and daemon endpoints against disposable synthetic per-identity homes and native `gh`/`git` scripts. `web/tests/github-*.spec.ts` exercises catalog pagination, selected checkout → Pi, zero selection, existing matching origin without another POST, partial conflicting destination, denied write and explicit recheck, lost reply recovered by observation, and cookie replacement while a page is in flight. Existing Pi-onboarding browser tests now pass through the zero-selection step; the test host does **not** prove different kernel UIDs, production systemd activation, live GitHub login, real Pi credentials, or a live test server. No real home, account or provider credential was used.
