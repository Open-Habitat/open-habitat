# Conversation titles — implementation evidence

Pi 0.85.1 has `set_session_name` in RPC (`dist/modes/rpc/rpc-mode.js`) and `ModelRuntime.completeSimple` in `dist/core/model-runtime.js`. It has no automatic title generation in the inspected RPC or session implementation. The daemon reads the latest native `session_info.name` from the session JSONL; when absent it still derives a first-prompt fallback. The controller writes through the owned Pi RPC child, never by editing history. Only browser-owned conversations admit regeneration; terminal-origin names are display-only.

The independent model request uses the mapped person's selected Pi installation and Pi's own configured credentials/model runtime, with no tools or agent session. It ranks available text models by input + output token price, preferring a non-reasoning model on price ties, chooses the cheapest, and declines when none is available. A user's only configured text model may be reasoning-capable; treating that capability as a disqualification would make generation unavailable for ordinary Pi accounts. Cost is a ranking, not a spending guarantee. Input is at most 4096 UTF-8 bytes from the first accepted prompt or bounded first/third excerpts; output is capped at 48 tokens and must be one trimmed, control-free UTF-8 line of at most 160 bytes. The subprocess has a 15-second deadline; the correlated name write has a 4-second deadline. Both are independent of sending and reading. The prompt requests a concise title in the conversation's language, and treats the excerpt as data rather than instructions. A model may fail to comply; invalid output leaves the old name alone.

A first attempt starts after the first accepted turn settles, because pinned Pi buffers fresh sessions until its first assistant message; starting at prompt acknowledgement cannot find a native file to check. For a conversation successfully named by that first automatic attempt, one refinement follows the third accepted turn's settlement; failure to create the first name does not schedule a third-turn replacement. The full native name is checked both before and after the model call; an unreadable or unstable name is unknown, never treated as empty. The controller serializes title requests per owned session, and latches the third-turn refinement even if a fourth message arrives while the first naming call is in flight. Native file scanning and name RPC run outside the controller's global mutex so a model call cannot stall conversation event drains. A later turn does not invalidate a name derived from the first; the native name precondition protects against stale user edits. An external/native/user-chosen name is never replaced by an automatic attempt; explicit regeneration can replace it and reports model failure to the browser without carrying the failure notice into another conversation. Continued browser-owned sessions recover a bounded first prompt for explicit regeneration without restarting the automatic schedule. The only remembered name is a transient precondition in this controller incarnation, not a durable title store. Pi's unconditional `set_session_name` RPC does not provide compare-and-set: a separate extension inside the same Pi process could in principle rename between the last native read and Pi processing the RPC. Browser requests are serialized and terminal-origin sessions cannot be written by this route, but arbitrary native extension mutations are not atomically fenced by Pi's API. This is a capability limit, not evidence of an observed user-name overwrite.

## Remaining decision

The pinned Pi 0.85.1 terminal session selector can rename **the same browser-owned session file** by opening it and appending `session_info`, without taking the daemon's ownership lock (`dist/modes/interactive/interactive-mode.js`, `renameSession`). The daemon's last native-name read and Pi's unconditional `set_session_name` RPC are separate operations. A terminal rename between them could therefore be overwritten. Two independent review passes found this; the setter cannot provide the strict “never overwrite a newer user-chosen name” acceptance guarantee. No such collision was reproduced in live use. The implemented precondition protects names chosen before the last read and all competing browser requests, but it is not a native compare-and-set.

**Recommendation for Jari:** keep the strict guarantee, and add conditional naming to Pi's native API (or a cooperating writer lock honored by both Pi's terminal selector and RPC) before closing this issue. The alternative is to accept the documented narrow race and revise the criterion. That is a product/architecture decision, not a reason to create a host title store. Leave preparation pending and the issue open until the choice is made; the implemented behavior can still be tested safely.
