# Browser conversation recap — implementation result

Committed runtime and visual revision: `0ddbe386a451adbaae7a5d5f8f389e920135ad52`.

A browser-controlled Pi conversation can request a recap from the mapped user's **daemon-owned Pi RPC child**. The daemon only invokes its private `/nah-conversation-recap` command; that Pi extension selects a configured text model, makes a separate tool-free model call, and appends a `conversation-recap` custom entry to the native session JSONL. The browser reads the active native branch through the authenticated gateway and renders a card separate from transcript entries. Terminal-origin sessions can display existing native TUI recaps but cannot generate them through browser control. A newer native message or an active turn marks the card stale; a failed native read retains the last known card but labels its freshness unknown. The card shows generation, a known failure, an uncertain network outcome, creation time, and a suggested next step without treating that suggestion as an agent instruction. The card stays available at the top of the scrolling conversation without pushing the composer below the viewport.

The daemon serializes requests for one controlled Pi session and keeps generating after a tab disconnect. The Pi command rechecks the native branch before persisting and skips a recap already written through the latest message, including after daemon restart; it also writes the TUI extension's `completedTurnCount` so reopening the session in the TUI will not schedule a duplicate for the same completed turns. A lost POST reply prompts a native reread, rather than assuming the model failed. The host stores neither recaps nor their generation state in its own database.

## Model-call and persistence limits

The extension includes at most 64 recent text messages and 64 KiB of prompt input, caps each excerpt at 4 KiB, asks for at most 160 response tokens, and applies a 15-second call deadline. It chooses the cheapest available configured text model by combined input/output token price, preferring non-reasoning on a tie. This ranks cost; it does not impose a currency ceiling, and a user's sole available model may be expensive. The model cannot call tools in this independent request. Recap text is normalized and limited to 320 Unicode code points, next-step text to 160, and model JSON is bounded to 2 KiB. Invalid, empty, timed-out or unauthenticated output leaves native history untouched and reports generation failure. The native entry persists with the Pi session and survives browser reload and daemon restart. The read path rejects changed/unreadable files and traverses only the active parent chain, including the case where its leaf is a root entry; it never falls back to an abandoned recap branch.

The TUI's automatic focus-loss path remains independent. Native TUI entries without a `through` field are projected using the parent entry, so their existing recaps can be displayed. Browser generation is manual only; see the decision below.

## Decisions for review

- **Automatic generation is omitted for this first browser version.** The TUI verifies focus loss, Pi idleness, and absence of tracked live processes before its delayed automatic call. A browser tab losing focus is not proof that the daemon-owned native Pi and its processes are idle; copying that signal would spend model calls during ongoing work. Recommend keeping manual requests until the daemon exposes an authoritative idle/process predicate together with a reliable browser-away signal. This is the precise TUI/browser behavioral gap, not a proposal for another recap store.
- **Terminal sessions stay display-only.** Browser control is held by the daemon's owned Pi child, not by a terminal-origin writer. Enabling browser writes to terminal sessions would require an explicit native ownership/handoff design rather than borrowing their credentials or mutating the JSONL directly.
- **Cost is bounded by input/output size and time, not money.** The cheapest configured text model is chosen for this independent call; a hard spending ceiling would need a product policy and reliable per-model token pricing, neither of which exists in this contract. No separate budget database was added.
