# Native model discovery: evidence and recommendation

Research date: 2026-10-16. The host currently integrates Pi **0.85.1**, not Codex as its conversation engine. “In Pi's catalog,” “has credentials,” “offered by Codex,” and “accepted for this account on this route” are different claims. The first two do not establish the fourth.

## Findings

1. **The failure is real and not a login failure.** The mapped user's `openai-codex/gpt-5.5` turn was rejected as unsupported for this ChatGPT account. Disposable mapped-user Pi prompts rejected `gpt-5.4` and `gpt-5.4-mini` too, while `gpt-6-astra` answered and subsequently answered without a model flag after Pi's native default was saved. These are observations for one account at one time, not universal entitlements. See [incident result](../pi-not-answering-live/result.md). OpenAI's [Codex models documentation](https://developers.openai.com/codex/models.md) independently dates the ChatGPT-sign-in retirement of 5.4/mini to August 31 and 5.5 to October 14, 2026; API-key access is distinct. An OpenAI Codex CLI 0.156.1 refusal of 5.5 is also recorded in the [issue](item.md).
2. **Pi's 0.85.1 list is a catalog, not entitlement.** `pi --list-models openai-codex` on alder lists 5.4, 5.4-mini and 5.5 alongside GPT-6 models. The existing [daemon helper](../../internal/daemon/pi_models_helper.mjs) intentionally loads the user's Pi runtime offline, checks authentication and returns `getAvailable('openai-codex')`, then saves a selected default through `SettingsManager`. This means *credential available*, not *remote request allowed*. [Pi model docs 1.3.0](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/docs/models.md) describe bundled/remote/cached catalogs, `pi update --models`, authenticated picker filtering and `/model` saving the default; none promises account-specific response authorization. In [Pi's provider implementation](https://github.com/earendil-works/pi/blob/main/packages/ai/src/providers/openai-codex.ts), `openai-codex` is a static catalog of model metadata and OAuth, not a Codex-backend entitlement query. Its 1.3 source calls this provider “legacy.” The new `openai` provider can also authenticate via ChatGPT subscription (added in 0.99.0); its distinct route must not be conflated with the currently selected `openai-codex` route. [1.3 changelog](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/CHANGELOG.md), [provider source](https://github.com/earendil-works/pi/blob/main/packages/ai/src/providers/openai.ts).
3. **Pi upgrades refresh metadata, not entitlement.** Between 0.85.1 and 1.3.0 Pi added `pi update --models` and background catalog refresh (0.9x), ChatGPT sign-in under `openai` (0.99.0), GPT-6.1 Sol with a new Codex default (0.99.1), and corrected Codex Sol context metadata in 1.3.0. Refreshing a provider catalog does not remove all models retired for a *particular* ChatGPT subscription; a new default can itself be unavailable to some plans. Sources: [Pi 1.3 changelog](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/CHANGELOG.md), [models guide](https://github.com/earendil-works/pi/blob/v1.3.0/packages/coding-agent/docs/models.md), [OpenAI's plan-dependent model guidance](https://developers.openai.com/codex/models.md).
4. **Codex provides a better account-aware signal, but it belongs to Codex.** Its documented app-server [`model/list`](https://developers.openai.com/codex/app-server.md#list-models-modellist) yields picker-visible entries by default, reasoning effort options and recommended default; docs explicitly say values depend on client and account. Its [model manager](https://github.com/openai/codex/blob/main/codex-rs/models-manager/src/manager.rs) fetches a `/models` catalog with auth-aware filtering, TTL/cache and ETags; its [app-server processor](https://github.com/openai/codex/blob/main/codex-rs/app-server/src/request_processors/catalog_processor.rs) serves `model/list` from that snapshot. It is a supported *Codex app-server interface*, not a documented way to reuse Pi's tokens or a guarantee that the same model works through Pi's provider. Running Codex alongside Pi would create a second login/configuration dependency and potentially another user's credential flow; do not adopt it just to populate Pi's picker. The OpenAI [API-key `/v1/models`](https://developers.openai.com/api/reference/resources/models/methods/list.md) describes availability to an API credential; it is not the ChatGPT Codex subscription endpoint. Avoid calling undocumented ChatGPT backend URLs directly or extracting Pi OAuth tokens for that purpose.
5. **A request is the only demonstrated end-to-end test for the Pi route.** A tiny native prompt with tools, session recording, extensions, skills and context files disabled can confirm that an authenticated mapped user's selected Pi model answers *now*. It consumes request/token or subscription allowance, can hit rate limits and may incur API billing depending on credential; an unsupported model may still count against request limits. [OpenAI API rate limits](https://developers.openai.com/api/docs/guides/rate-limits.md) cover request and token budgets, but do not establish the exact cost or limits of Pi's ChatGPT-subscription route. No source found that authorizes automatic polling of every model or promises a free entitlement-check request. Treat probe cost as nonzero. User-triggered one-model verification at selection, or one bounded recovery probe after an unsupported-model response, is proportionate; never on every page render, login, background refresh, or every catalog entry. Prefer an actual first user turn as proof when possible. Respect 429/retry guidance, and never probe while credentials are unavailable.

## Recommendation

**Keep Pi as the authority for the browser's Pi choices and persisted preferences.** Offer Pi's current, credential-filtered catalog as *candidates*, explicitly not “models you can use.” Preserve the already verified `gpt-6-astra` default on the test account rather than switching automatically to Pi 1.x's 6.1 Sol. Surface unsupported-on-send as a recoverable reason to choose another model and start a new session; no silent message replay. Optionally offer a user-initiated “try this model” operation with strict one-at-a-time rate limits and an explicit usage warning. Its success is a time-specific observation, not durable entitlement; no host-owned entitlement DB/cache or cross-user probe broker. Do not introduce a Codex app-server into the Pi path. If Codex itself later becomes a hosted native agent, use its `model/list` for its own selector.

**Upgrade test Pi to 1.x eventually, but not as a fix for entitlement.** Run a separate bounded compatibility task/release: current helper rejects any manifest version other than `0.85.1`; the daemon selects and starts Pi using version-sensitive APIs and JSON/RPC event semantics; new `openai` subscription login can change provider identity and existing native defaults/sessions remain bound to `openai-codex`; new defaults and catalog entries may be unauthorized; 1.x introduces codemode/MCP, different tool exposure and fullscreen default. Review upgrade changelog and migration behavior, pin through Fleetrepo, exercise mapped-UID native sign-in/default/session/selection, signed-in browser turns and restart recovery on the disposable test server. Do not change global Pi installations or settings as part of this research.
