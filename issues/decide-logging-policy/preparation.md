Source snapshot from this worktree. This is preparation, **not** an adopted policy. All examples are synthetic; no live login, journal inspection or host configuration was used. `proposal.md` is the earlier, more expansive proposal. Its suggested events are not an inventory of what ships.

The public policy should distinguish application diagnostics from HTTP error responses, browser-visible conversation events, root state and ingress-provider logs.

## Trace exercises against current records

- **Failed OAuth shape**: gateway start emits `oauth_callback started` plus `attempt_id`; extra callback query key emits `oauth_callback rejected / shape_extra_key` with the same ID (`auth.go:417,461-466`). No provider or broker call is made. A callback with unmatched state gets a fresh unrelated ID or no line once budget exhausted (`auth.go:438-460`). The gateway log can distinguish a matched malformed callback from a provider denial, but cannot prove that an absent broker record means no broker attempt, nor connect to ingress logs without a safe ingress configuration.
- **Broker provision failure**: on a synthetic unavailable host slot, broker emits `broker_guard / availability_error` (`writer_linux.go:433-442`, `broker_linux.go:103-110`); gateway emits `oauth_callback rejected / broker_denied` with `broker_operation:ensure` and a classified broker reason (`auth.go:505-510`). They have no common ID. Operator can narrow both by time and privately check pending/ledger, but cannot prove these two lines share an exchange, identify the precise host check from a generic `availability_error`, or infer whether a partial mutation completed. An allowlist rejection has no broker guard line at all (`writer_diagnostics_linux_test.go:10-42`).
- **Daemon spawn/start failure**: a synthetic Pi device start error returns HTTP 503 `native_source_unavailable` (`pi_attempt_linux.go:58-63`); the gateway proxy returns a generic `daemon_unavailable` if the mapped socket or round trip fails (`proxy_linux.go:55-59,132-135`). Neither generates a per-operation diagnostic log. The first is a native start failure, the second could be a missing socket or network failure; an operator cannot reconstruct which command failed or join a daemon failure to a browser report from `req_00000000` (`snapshot_linux.go:38-45`). Command arguments/output are not suitable substitutes for a safe classification.
- **Shared setting change**: there is no shared-setting mutation handler in the inspected gateway/daemon/broker paths (`gateway/server.go:24-56` mounts current routes). No claim about auditing that event is possible today. Gateway revocation is the closest existing privileged action: after broker authorization it logs numeric subject and sessions removed, but not which operator invoked the local control listener (`revoke.go:15-43`). Designing an actor field for a *future* setting mutation requires defining which authority knows the acting principal; do not attribute it from a browser header or daemon assertion.

## Test evidence and known limits

Added `internal/gateway/logging_policy_test.go`: synthetic token, cookie, CSRF, authorization header, state, identity, conversation and tool-content markers stay out of captured callback JSONL on a failed handoff. Immediate diagnostic writer errors preserve successful login and shape rejection; the outcome and provider/sink call counts are checked. Existing `auth_diagnostics_test.go:15-153` exercises reason vocabulary, secret markers, independent unmatched ID and a 32-event burst cap; `broker_diagnostics_test.go:33-115` checks classified ensure/authorize events and exact field sets. Added `internal/provision/logging_policy_linux_test.go`: an immediate guard diagnostic sink failure does not change the host guard denial or create a binding; the stage has no candidate/content marker. Existing `writer_diagnostics_linux_test.go:10-42` covers pre-reservation guard classifications.

**Not proven / failure cases to address after policy:** `slog.NewJSONHandler` writes synchronously to its writer (`auth.go:199-206`); a blocked stderr sink can stall a matched login. No test can truthfully assert nonblocking logging today; adding an asynchronous bounded sink and its drop policy depends on the volume/failure choices below. The gateway does not cap *matched* start/callback records or repeated privileged revocations (`auth.go:417,567`, `revoke.go:43`); the unmatched callback burst bound is not a total byte/record cap. The guard callback likewise has no budget (`writer_linux.go:430-457`). Neither cross-component correlation nor future shared-setting actor attribution can be tested as implemented. The revocation record includes numeric subject (`revoke.go:43`), so a universal no-identity diagnostic assertion would fail today; this is an explicit policy choice, not concealed by a passing OAuth-only test. Browser/ingress and service-journal privacy cannot be inferred from captured Go logger tests. No daemon conversation/journal code was changed or tested for redaction in this worktree.

## Choices for Jari (recommended, not decided)

1. **Cross-component correlation.** Option A: continue gateway-only attempt IDs and compare restricted journals by time (no protocol change; ambiguous under concurrency). **Recommend B**: gateway-generated random per-login attempt ID, carried as a bounded optional field only over authenticated gateway→broker and mapped gateway→daemon channels, validated as data not authority; separate short-lived per-request ID for ordinary requests. This improves proof of which stage failed without putting identity or OAuth state in logs, but changes two protocols, requires peer-boundary review and explicit negative tests; no correlation field was added tonight. **Question:** Approve authenticated propagation of a gateway-owned opaque attempt ID to broker and daemon, or keep time-window-only diagnosis?
2. **Actor attribution.** A: anonymous event types only; private ledger remains authority but later shared changes cannot be audited to a person. **Recommend B**: on privileged state changes only, record a verified actor identifier and target scope under restricted operator access, *not* identity in routine login/request lines; derive the actor from the boundary actually authorizing the action, never user input. Numeric subject in current revocation logs must be reviewed against this rule. Cost: privileged records become personal data and need restricted access and deletion; no shared-setting handler exists yet. **Question:** Should approved privileged mutations carry verified actor and target identifiers in restricted records, while routine diagnostics remain pseudonymous?
3. **Access.** A: one shared journal reader across services; easy search but exposes per-UID work timing and broker activity. **Recommend B**: separate root-authorized broker records; gateway records for a small operator group; per-UID daemon records readable only by that user and specifically authorized operators, no cross-user browser feed. More operational friction, but respects Unix boundaries. Fleetrepo owns concrete journal ACLs/ingress configuration. **Question:** Approve these role-separated reader boundaries (including authorized break-glass daemon access), or require a different operator access model?
4. **Retention.** A: indefinite journals for easy historical search; greater exposure. **Recommend B**: propose 7 days for normal gateway/daemon diagnostics and 30 days for privileged mutation/broker diagnostics, with delete-on-expiry and no indefinite central copy; root ledger has its own state lifecycle. These are proposed budgets, not applied settings; longer incident investigation loses old events. **Question:** Are 7-day ordinary and 30-day privileged diagnostic windows acceptable, or what incident-response window is needed?
5. **Volume/failure.** A: log every request and allow synchronous stderr backpressure; most detail but attacker-controlled flood and blocked auth. **Recommend B**: fixed-size records, bounded queues with nonblocking loss on diagnostic-sink failure, rate-limited/aggregated anonymous failures, transitions and exceptional outcomes rather than polling/SSE; surface dropped counts out-of-band when possible. Cost: records may be missing, so absence never proves an operation did not occur; privilege/state decisions must not rely on log delivery. Per-component byte/record caps need operational sizing before Fleetrepo application. **Question:** Approve lossy bounded diagnostic delivery under flood/outage, with separate failure alerting, rather than blocking operations to guarantee logs?

**Additional UX question:** Should a user see a newly generated opaque support reference on failure, backed by a restricted event lookup, or only the existing generic error code? Today's `req_00000000` is not a usable reference (`gateway/auth.go:308-312`). No decision or implementation tonight.
