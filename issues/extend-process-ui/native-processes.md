# Native Pi process evidence (preparation for prototype)

Scope: installed `npm:@aliou/pi-processes@0.10.9` in `~/.pi/agent/settings.json` (line 3), configured by `~/.pi/agent/extensions/processes.json` (version 0.10.9; widget only). Source paths below are relative to `~/.pi/agent/npm/node_modules/@aliou/pi-processes/` unless prefixed otherwise. This is source inspection, **not** a verified browser-to-extension integration or a measurement of v1 usage.

## Ownership, identity and lifetime

* Each loaded core extension creates **one manager** and registers its tool, commands and internal event-bus handlers (`extensions/processes/index.ts:23-91`). Its registry is an in-memory map, not a filesystem inventory (`src/get-manager.ts:7-14`, `src/manager/index.ts:27-47`, `src/manager/process-registry.ts:7-43`). The ID is `proc_` plus two random bytes, checked only against this manager's map (`src/manager/process-registry.ts:10-15`): it is neither globally unique nor stable across Pi instances. Key it by owning Pi instance/session **and** process ID; do not identify it by PID alone. `ProcessInfo` includes name, raw command, cwd, PID, epoch-ms start/end, status, exit code, success, end reason, signal, error and stdout/stderr paths (`src/types.ts:1-44`). There is no session ID in `ProcessInfo`; association comes from the live Pi instance holding that manager, not from the log filename.
* On first start, the extension makes a private temporary `pi-processes-*` directory under Node's `os.tmpdir()` with per-ID raw stdout, raw stderr and tagged combined log files (`src/manager/process-log-store.ts:30-88`). The directory does not exist for a session that never started a process. The raw streams receive byte chunks; combined receives complete lines tagged `1:`/`2:` (`src/manager/process-runtime-controller.ts:340-352`, `src/manager/process-output.ts:31-42`). Thus live combined output can lag an unterminated raw stream line. Per-file 64 MiB cap is truncate-to-zero and restart with a marker; the three files can represent different time windows (`src/manager/limits.ts:7-15`, `src/manager/process-log-store.ts:20-42,268-294`). File append/read errors are swallowed (`src/manager/process-log-store.ts:191-195,210-214,281-293`); empty logs do **not** prove no output. Tail reads cap at 2 MiB and full reads at 16 MiB per stream (`src/manager/process-log-store.ts:116-195,198-214`, `src/manager/index.ts:101-112`). No persistent process manifest is written beside them.
* On normal Pi `session_shutdown`, the extension kills all live process groups and removes the entire temporary log directory (`extensions/processes/hooks/cleanup.ts:26-42`, `src/manager/index.ts:163-169`). Clear and automatic finished-record reaping remove records **and** their log files; the grace period is five minutes when more than 50 finished records accumulate (`src/manager/process-runtime-controller.ts:282-299,460-518`, `src/manager/limits.ts:12-15`). On abrupt Pi death, cleanup may not run: orphan files or independently detached children may remain, but with no reconstructable manager identity/status. Do not show those as live managed inventory. Restarting Pi creates an empty manager; resuming the same Pi session JSONL does not rehydrate it (`src/manager/index.ts:27-47`, `src/manager/process-registry.ts:7-8`). A daemon restart loses its RPC handles and systemd cleans its service children; terminal Pi remains independent (`docs/architecture/conversations.md`, “Ending and continuing”). While a daemon stays up, closing the browser does not stop its controlled Pi. Pi session history may preserve **tool calls/results** and displayed `ad-process:notification` messages (`extensions/processes/tools/index.ts:43-82`, `extensions/processes/notification-sender.ts:29-43`), but these are snapshots, not an authoritative current list, and log files are not embedded in history.

## Native operations and what crosses the current boundary

* Agent tool `process`: start/list/output/stop/write/update/clear (`extensions/processes/tools/index.ts:43-106`); start defaults cwd to Pi context (`extensions/processes/tools/start/index.ts:20-43`). List reports the manager's current records, with optional status filters and watches (`extensions/processes/tools/list/index.ts:21-75`); output returns bounded text and paths, not an unbounded log stream (`extensions/processes/tools/output/index.ts:50-135,191-267`). Notification watches and exit events are delivered through Pi custom messages, not a separate durable notification queue (`extensions/processes/handlers/notifications.ts:16-26,84-108`, `extensions/processes/notification-sender.ts:15-43`). User TUI commands include `/ps`, `/ps:logs`, `/ps:kill`, `/ps:clear`, `/ps:dock`, `/ps:pin`, `/ps:settings` (registered in `extensions/processes/index.ts:75-80`, `extensions/processes-logs/index.ts:15-31`, `extensions/processes-dock/index.ts`). `/ps` and `/ps:logs` **degrade to a plain inventory**, not a logs overlay, outside TUI (`extensions/processes/commands/overview.ts:54-60`, `extensions/processes-logs/commands/logs.ts:51-57`). `/ps:kill` selects a manager-owned process (`extensions/processes/commands/kill.ts:28-75`). The event-bus request/list/get/output/log-files channels, live output broadcasts and logs subscribe/chunk protocol are **inside the same Pi instance**, not daemon HTTP or Pi RPC commands (`extensions/processes/handlers/requests.ts:16-69`, `extensions/processes/hooks/event-bridge.ts:6-32`, `extensions/processes/handlers/subscriptions.ts:17-94`). The subscribe reply supplies a bounded initial combined tail, then tagged lines; subscribers are removed on process end (`extensions/processes/handlers/subscriptions.ts:27-61`). Output events can drop lines under load; raw logs may retain them (`src/manager/process-output.ts:165-223`, `src/types.ts:46-55`). Reading a path alone has no reliable owner/session/status association.
* Pi RPC's `get_commands` lists registered extension commands and `prompt` can invoke one immediately; it does **not** expose extension manager objects or arbitrary `pi.events` channels (`~/.local/lib/node_modules/@earendil-works/pi-coding-agent/docs/rpc.md`, “prompt” and “get_commands”). RPC `ctx.ui.custom()` returns undefined, hence the degraded `/ps` commands (same RPC doc, “Extension UI Protocol”). The daemon starts Pi in RPC mode with native user HOME (`internal/daemon/pi_rpc_linux.go:61-106`) and currently allows a fixed RPC command set; it discards generic command response data except its recap-command presence check (`internal/daemon/pi_rpc_linux.go:173-262`). It projects fire-and-forget extension UI notifications as bounded *display text*, not structured inventory (`internal/daemon/pi_events_linux.go:237-291`). For a terminal-origin Pi it has no RPC attachment (`docs/architecture/conversations.md`, “Identity and control”). A mapped-user daemon can read its own user's files, but cannot call another live Pi's private event bus simply by sharing a UID. **Current code cannot give an authoritative inventory of terminal-owned processes or even a structured list from its own RPC child.** An empty history or `/ps` output after a restart is not evidence of zero processes in other Pi instances.

## Smallest prototype round (recommendation)

Prototype **only for daemon-owned live Pi RPC children**, with availability explicitly scoped to that owner; show terminal-origin conversations as *unavailable*, not empty. Add a tiny host-loaded Pi companion extension to issue `processes:request:list`, `processes:request:combined_output` / `processes:logs:subscribe` through `pi.events` within that **same Pi** (`src/protocol/channels.ts:3-29`, `extensions/processes/handlers/requests.ts:21-56`, `extensions/processes/handlers/subscriptions.ts:23-87`). Determine in an actual RPC prototype a bounded, correlated, non-model, non-history delivery mechanism from companion to daemon; Pi RPC has no arbitrary extension-response command today. One possible experimental bridge is a private command invoked via RPC `prompt` plus a correlated `extension_ui_request` notification, but the daemon's current text truncation/projection and lack of structured reply mean it is **not yet an agreed production protocol** (`internal/daemon/pi_events_linux.go:251-291`). Never send the agent a normal-language prompt or scrape historical tool results to query state. If that bridge is inadequate, arrange a small Pi/extension RPC adapter change rather than a second process registry or log store. Verify extension present via `get_commands`, version/shape at runtime, no interference with an active agent turn, and failure modes with missing extension and Pi exit before designing the UI. Terminal-owned process support needs a separate reachable native interface from the owner; avoid `/proc`-based guesses and temp-directory enumeration.

Host facts for inventory: daemon controller's live Pi session UUID + controller generation/instance, extension manager's `list()` snapshots, and a scoped availability/error state. Display selected name, status, start/end, exit result and **redacted** command/cwd (raw fields may contain credentials or private paths); compute duration client-side. Never send log paths, PID or unredacted command to browser by default. For one selected process, use native combined lines (with stream tags and retention marker), bounded initial tail, then extension output subscription while alive, with resnapshot on a gap/reconnect and a distinct `unavailable` on owner death. Pause follow in the browser without pausing native collection; capture a bounded tail again on resume. Distinguish tail-window omission, file-cap truncation, event dropped-lines and read failure rather than claiming complete logs. Verify subscription handoff under concurrent output and process completion before relying on it: no durable cursor or gap-free replay is promised by this extension. Avoid a daemon-side parallel log store.

**Proposed wire shape, not a `contracts/v1/` edit:** `GET /api/v1/conversations/<id>/processes` → `{schema_version, availability: "available"|"unavailable"|"error", processes: [{id, name, command_preview, status, started_at, ended_at?, exit_code?, success?}]}`; `GET /api/v1/conversations/<id>/processes/<process-id>/output?tail_lines=N` → `{schema_version, owner_generation, process_id, lines:[{stream:"stdout"|"stderr", text}], tail_limited, retention_truncated, complete:false}`. For live following, put bounded `process.output` / `process.changed` events on existing user SSE with owner generation + process ID and recovery by refetching snapshot/tail after cursor expiry. `owner_generation` must fence recycled four-hex-digit process IDs and restarted controllers; do not expose Unix UID, native paths or arbitrary file-read endpoints. `retention_truncated` is tri-state until observed/proven (a tail limit alone cannot establish file-cap truncation). Design proper limits and authentication using the existing gateway/daemon HTTP boundary (`docs/architecture/http-api.md`, “Requests and responsibilities”; `contracts/v1/AGENTS.md`). Controls are a later round, after verifying native ID/lifecycle and RPC command outcome semantics.

L3–L5 remain conditional (`issues/native-agent-host-architecture/ui-design-later.md`, L1–L5).
