## Queue/steering slice (worktree `wt-4rx76419k7`, synthetic)

Verified the pinned `@earendil-works/pi-coding-agent@0.85.1` installed artifact: `dist/modes/rpc/rpc-types.d.ts`, `dist/modes/rpc/rpc-mode.js`, and `dist/core/agent-session.js`. RPC stdin is JSONL with optional `id`: `steer` and `follow_up` take `message` and return correlated `{type:"response",id,command,success:true}` after queueing; `clear_queue` returns `data:{steering:string[],followUp:string[]}` (camel case), not the published `follow_up` spelling. `queue_update` events contain `steering` and `followUp`; they are emitted when enqueued, removed at message start, or cleared. `agent_settled` marks the end of an agent run; steering is delivered after current tool calls and follow-ups when the agent completes. The queue strings can be expanded by Pi's skill/prompt templates, so the confirmed removed texts are Pi's queued texts rather than necessarily the submitted literal string. The controller preserves exactly those returned strings, with no local reconstruction. No change to the published v1 schemas was required: its queue and removed-queue groups already represent this behavior; the private controller endpoint adapts the native spellings.

Implementation scope: bounded correlated native writes; command-ID deduplication, clear response validation, separate queue groups in status and browser, fake-Pi queue emulation, browser test for steering, follow-up, clear and exact restored text. Status derives queue from Pi events rather than assuming a locally sent message was accepted. If an RPC write/ack is ambiguous, there is no automatic retry or invented removal. See `visual-notes.md` for the unreviewed synthetic screenshots.
