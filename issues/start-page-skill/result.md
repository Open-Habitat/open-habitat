# Repository-authored start page

## Outcome

The empty conversation view reads `.agents/start-page.md` in the selected workspace. Its YAML frontmatter supplies the title and optional ordered goals; its Markdown body supplies free text. The whole page is authored by the repository maintainer, not assembled from skill metadata. The shipped `open-habitat-start-page` skill proposes content, writes after approval, and leaves review, commit and push to the person. This repository includes an initial authored page.

A goal inserts its example into the draft, preserving existing text and focusing the composer without sending. Only an explicitly referenced effective native skill becomes a `/skill:name` invocation. A disappeared skill leaves a usable prompt without an invented invocation. A text-only page is supported. Missing, invalid or unreadable pages show only the creation hint.

## Decisions for later review

- Applied Jari's later clarification supplied by the conductor: **the entire view is repository-authored**. Frontmatter holds `title` and optional `goals` (`title`, `when`, `prompt`, optional native `skill` name); the body is sanitized Markdown. The shipped skill documents the format and an example. One maintainer shares the page through ordinary commits. No automatic skill cards or per-skill starting flags remain.
- Removed the separate catalogue: it had no entry point outside this empty state. Removed its presentation metadata/Git provenance reads, new-skill cutoff storage, filters, catalogue UI and schema fields. Pi's native `/` completion remains unchanged. The deleted provenance, filtering and acknowledgement tests distinguished behaviors that no longer exist; the retained pinned SDK test still covers effective skill trust/collision semantics, and the composer browser spec covers native command completion.
- The daemon reads a fixed workspace-relative path as its own UID through the existing held-workspace admission proof and `os.OpenRoot`. Files must be own-UID regular files, at most 32 KiB; opens are nonblocking to avoid FIFO hangs. Symlinks cannot escape even to another workspace in the same home. Invalid UTF-8/YAML, unknown fields, empty required strings, oversized content and syntactically invalid skill references are rejected. The Markdown body is capped at 16 KiB, with at most eight goals and bounded scalar fields. Paths and raw errors never cross the contract.
- Skill delivery uses native Pi **`--skill <file>`**, appended beside the existing shipped extensions for every daemon-owned Pi launch and list-only helper. The skill is embedded in the product binary and materialized in the daemon's private temporary companion directory; an upgrade ships its new bytes, and the next child launch recreates it if tmpfiles removed the directory. No personal settings are rewritten and no registry, network install, or Fleetrepo installation change is required.
- Alternatives: a Pi npm/Git package adds package installation/update state for one text asset; per-user global symlinks/settings or `/etc/skel` need installation reconciliation and either modify personal configuration or miss existing users. Explicit native injection fits the existing child-launch mechanism. It provides the skill to every Open Habitat user, **not to unrelated terminal-only Pi processes launched outside the daemon**. If that broader scope is wanted later, Fleetrepo would install the shipped `internal/daemon/start-page-skill/SKILL.md` as a read-only fleet asset and add its directory to each person's native Pi user-level `skills` resource list (preserving existing settings); that is not needed by this browser feature.
- No automatic generation/writeback during reads. Missing/invalid pages deliberately share the short creation hint; the host does not guess a page from skills. The command-list response carries the page, reusing the existing effective native inventory only to resolve explicitly authored skill references.
