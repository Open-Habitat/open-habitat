# Result: restore daemon sockets after reboot

The broker verifies the committed ledger at startup, then asynchronously starts admissible bindings' inactive sockets via `LinuxHostExecutor.Ready`, which verifies the account and unit, checks the installed JIT gate dependency, starts the socket, and verifies it again. The broker continues to serve while restoration proceeds; it tries later bindings after a definite activation failure. All broker activations (including login `ensure`) share a context-aware serial gate because the installed Fleetrepo policy checks that every sibling listener is fully active. A submitted start has its own 45-second budget even if the caller exchange expires while it runs; the caller still receives no route after cancellation. If that dedicated start times out, its systemd job may still run; the broker fails closed to further activation until operator investigation and restart rather than racing the pending job. `authorize` remains read-only. Revoked bindings are still verified, but not activated under allowlist admission.

The neutral broker service now has a boot install target. **Deployment prerequisite:** Fleetrepo must prepare and verify `/run/open-habitat` ACLs and quota enforcement before enabling/starting both broker units at boot. Its current JIT policy explicitly keeps sockets disabled at boot. Enabling the broker service before Fleetrepo installs this ordering will cause fail-closed startup, not working restoration. The release worker must update the concrete installation and run a real guest reboot proof; the existing VM reboot diagnostic intentionally checks the unprepared/disabled state and does not prove automatic restoration. Fleetrepo's current `release_fresh_next.py` explicitly starts per-user sockets immediately after the broker service; that competing start path must be removed or ordered behind verified broker restoration before the next upgrade. The Fleetrepo policy and preparation scripts currently require disabled socket units and must be revised together with boot ordering. Do not enable per-user daemon sockets directly.

## Decisions for review

- Keep socket activation solely in the root broker and retain a read-only gateway authorization path. This avoids granting gateway a new authority to start units on request.
- Serve during restoration, but serialize all broker starts: the deployed JIT gate refuses sibling sockets that are still activating. A slow or definitely failed start delays the restoration queue for at most the command's bounded timeout; an uncertain submitted job stops further starts until an operator checks unit state. Neither blocks broker authorization for already-active sockets.
- Skip activation for a bound ID removed from the allowlist; keep startup verification of its NSS identity and quota, and preserve its binding for administration. Admission `any` activates all committed bindings.
- Leave UI wording to the web worker; until the concrete boot deployment is in place, signing in again may recover an inactive socket through `ensure`.
