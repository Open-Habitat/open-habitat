## What happened

The guest established A (`guestone`, UID 21032) as a healthy, broker-bound control before activating the gateway's private revocation socket. That order matters: the historical pinned Fleetrepo gate does not recognize `revoke.sock` as a permitted runtime path during a *new* daemon-socket activation. The already-active A daemon route and browser session returned 200 before the fault. A native process ran under A's UID throughout the crash.

For B (`guesttwo`, UID 21033), the guest-only build hook sent **SIGKILL to the real systemd-managed root broker** just after the `account` executor step returned. Systemd recorded `Result=signal`, `ExecMainCode=2`, `ExecMainStatus=9`. NSS then resolved B's new account, while its home and daemon config were absent, the committed ledger still contained only A, and `pending.json` remained at phase `account`. This phase was chosen because it includes irreversible Unix-account creation without a durable binding; an earlier reservation-only kill would not exercise that boundary. No phase matrix or disk-loss durability claim is made.

B's OAuth callback returned 403 (`identity_mapping_denied`), its session and snapshot both returned 401, and no route was issued. The early passing test saw a new systemd service invocation exit with `Result=exit-code` and no running broker, with unchanged pending bytes and bindings. **That observation alone does not prove the pending guard caused the refusal.** The reviewed fixture now emits a fixed diagnostic only at the guest-overlay pending startup guard and requires that marker for the restarted invocation. It fails: the marker is absent. Startup-stage diagnostics show the restarted broker reaching the config/socket check but not the inherited-descriptor or journal checks (`NAH_GUEST_STAGE_config`, without a later `fd` stage). This may be a fixture socket-path/ACL drift; it has not been established as pending-journal refusal. No B home/config/socket or published binding appeared in the earlier run.

The pending journal also denies **A's browser session and routed daemon requests** (401/401). This is intentional global fail-closed behavior, not unaffected browser availability. A's pre-existing native process remained alive; A could still read its own home file as UID 21032, while the partial B account could not read it. Thus the unaffected-sibling observation is native process/DAC continuity, **not** independent browser routing while the broker state is uncertain. The issue must not claim the latter.

## Sensitivity and limits

A local-only mutation of the host proof validator fed an otherwise passing receipt with `restart_refused=false`, `no_session=false`, or `no_executor_after_crash=false`; each was rejected (exit 1), while the unmodified receipt passed (exit 0). This is validator sensitivity, not a second crash experiment. The guest also checks real systemd signal evidence, pending bytes, post-crash filesystem state, and failed restart, rather than trusting a guest-supplied success flag alone.

Only the guest fixture build uses a private, temporary Go source overlay; the committed product source has no crash hook. A comparison build from committed source was compiled and scanned with `GOFLAGS=-tags=nah_guest_fault` to show even an inherited former guest tag cannot include the marker, while the overlay binary contains it. Release packaging has no access to the temporary overlay. No host service, real account, credential, ingress, test server or Fleetrepo file changed; no pending marker was cleared and no recovery attempted. The separate operator-observed post-reboot smoke with bound users remains outstanding.

Independent security review identified two proof gaps: the restart failure could occur before the pending guard, and an inherited Go build tag could include the initial test hook in release packaging. The tagged source has been replaced with a guest-only temporary build overlay. A clean-restart positive control proved unreliable in this historical guest; a direct guest-only pending-guard marker was added instead, but **the marker has not been observed**. The latest failed attempt's sanitized envelope is `/var/tmp/jit-broker-crash-reviewed10.err` (exit 2, `boot_proof_failed`). There is no final post-review green guest run or clean gate for this implementation. The initial failed guest attempts were fixture diagnostics, not evidence of a successful crash: missing revocation activation, missing current config parent, historical gate/revocation-socket incompatibility and emulated first-ensure timeouts were resolved before this passing run.
