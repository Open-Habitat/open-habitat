# Bounded journal restart test; parallel guest experiment not landed

Parent `@prove-jit-guest-isolation` remains **open**. This is a test-only, offline intermediate: no journal repair, process-kill or post-install acknowledgement proof. No reboot scenario was added. No host/Fleetrepo/deployment/ingress/real identity or credential operation was performed.

## What the landed test proves

`internal/provision/writer_linux_test.go` reconstructs a fresh `Writer` against the same private test directory for each pending journal phase (`reserved`, `verify`, `publish`, `account`, `home`, `config`, `socket`, `unit`). Both `authorize` and `ensure` return `state_unavailable`, issue no route, call no executor, and leave the pending journal, binding ledger and high-water head byte-identical. A paired positive control removes *only the synthetic marker inside the disposable test directory* and proves the same restarted writer can ensure successfully. This is **in-process offline simulation of a writer restart**, not an actual root broker crash, disk power-loss/durability test, guest journal recovery, or permission to delete a live journal. The production writer and fail-closed policy were unchanged. Recovery in the sense of automatically completing a partial mutation remains deliberately unimplemented and unproved.

## Parallel first login: explicitly unproved

A separate experimental guest change at `bb2d6535f6548cfbccca36edc91020200dfe20ed` attempted two concurrent synthetic gateway-UID **broker ensures** in the *same* private PID1 guest with empty accounts. These were not OAuth callbacks. The committed guest command `PATH=/home/maintainer/Sources/native-agent-host/.tools/go/bin:$PATH ./scripts/vm-test.sh jit-provision --json` returned exit **2**, `boot_proof_failed`, VM exit 0 after 194 guest seconds, sanitized check `parallel broker route missing`, `pending_phase=None`, `broker_state=active`, elapsed exchange 18.12 s. This cannot prove which ensure failed or that the gate race identified by review actually occurred; no raw guest journal was published. The independent review established from the immutable pinned Fleetrepo gate source that its nonblocking shared ledger lock can reject activation during another ensure's exclusive lock. The failed guest is consistent with, but does **not** prove, that race. The experiment also lacked concurrent browser first callbacks. It was reverted at `97821cf` instead of adding a red opt-in scenario or weakening gate checks. The pre-existing `jit-provision` and `jit-login` fixtures remain unchanged. No claim of parallel-first-login success is made.
