# Result: guest socket and gateway participation routing

Implemented ADR 0038 sections 2 and 7 (the participant's way in), behind the experimental feature `multiplayer` (the owner's daemon refuses every guest route while it is off). No browser UI.

## What exists now

- **Socket unit** `systemd/open-habitat-guest@.socket`: `/run/open-habitat/users/<name>/guest.sock`, `0660 <name>:open-habitat-gateway`, `DirectoryMode=0710`, `FileDescriptorName=guest`, `Service=open-habitat-daemon@%i.service`, the same storage and binding gates as the agent socket. `open-habitat-daemon@.service` requires and orders all three sockets.
- **Broker**: restores the guest socket from the committed binding with the other two (`Ready`, `RouteReady`), verifies its effective properties (`guestUnit`), the socket's owner, group and mode (`socket`), takes no instance over (`available`), and stops it on withdrawal (`listenerUnits`).
- **Packaging and host maintenance**: the policy installs the template; the release verifier pins it exactly (four new negative cases); upgrade starts the three sockets and stops whichever are installed, since a predecessor has no guest template. A predecessor generation saved without the guest unit is still a valid upgrade predecessor (`predecessorOptionalPolicies`), and nothing else may be missing.
- **Activation**: the daemon requires exactly three named descriptors (`daemon`, `agent`, `guest`, any order) and refuses to start otherwise.
- **Transport** (`internal/transport/guest_linux.go`): `ValidateGuestListener` probes the pathname from an abstract address without consuming queued gateway requests; `ServeGuest` accepts only the gateway's UID; `GuestPeer` marks those requests and never satisfies `TrustedPeer` or `AgentPeer`.
- **Daemon guest table** (`internal/daemon/guest_linux.go`): default-deny; only `POST /guest/v1/conversations/<id>/join` today, in one `guestOperations` map that the later lane issues extend. Every refusal past the peer check is `resource_not_found`. `Open-Habitat-Participant` is base64url JSON `{subject, display_name, avatar_url}`, strict (one value, ≤1024 bytes, no unknown or duplicate keys, subject `github:<id>`, a one-line name, a GitHub avatar URL or empty); it is identity only. The header is refused (400) on `daemon.sock` (every route but the transport's own handoff path, which the gateway never sends it to) and on `agent.sock`.
- **Gateway participation index** (`internal/gateway/shares_linux.go`): `participation.json` beside `view-links.json`, 0600, atomic and synced, refused rather than reset when damaged or loosened (sharing is then unavailable, the rest of the app is not). An entry holds the share ID (`s` + 26 base32), the owner's routing identity, the owner's display name, the conversation ID, the participant's subject and the invite state. It follows the owner's member changes: an invitation the daemon answered creates or refreshes the entry, a removal deletes it and cancels its relays; rights changes only update an existing entry.
- **Routes**: `GET /api/v1/shared` lists the session's own shares (owner name and avatar, state, invited_at; never the conversation ID or a Unix name). `POST /api/v1/shared/<share_id>/join` checks the session, CSRF, that the entry's participant is the session's subject and neither person is denied, ties the request to the session and the share under `a.mu`, verifies the owner's `guest.sock` (`udssecure.Guest`), dials it and sends a request the gateway built itself to the fixed guest path. Unknown, foreign, removed and malformed shares and unknown operations all get the same 404.
- **Relays**: `registerRelay` ties a relay to the browser session and to a share; removal, withdrawal and an index fault cancel a share's relays under the lock the relay was admitted under, and a periodic check re-reads the share.
- **Withdrawal and revocation** (`revokeSessionsLocked`) delete the person's shares as owner and as participant; a person admitted again has none, and an owner's later rights change does not recreate one.
- **Picker**: lists the broker's admitted, bound people and also every person holding an unexpired session, so an open-admission server lists everyone who has signed in (Jari: "kaikki kirjautuneet").
- **Contract** `contracts/v1/conversation-shares.schema.json` (list, join reply, participant header) with an example.
- `docs/operations.md` and `internal/AGENTS.md` carry the operator step and the guest listener's rules.

## Decisions for later review

1. **The index stores the owner's routing identity** (UID, username, daemon socket path) as `view-links.json` does, besides the subject the ADR names. Alternative: ask the broker for the owner's binding on every guest request. Chosen because it is how the gateway already routes to another person's daemon for view addresses, and withdrawal deletes the entries; nothing of it reaches the participant.
2. **The owner's display name is kept in the entry** (from the owner's session at invitation, refreshed with each member change) and replaced by the owner's live profile name when they have a session. The conversation title is not in the index yet: the invite card's title needs an invited-only guest route, which belongs to `multiplayer-guest-stream` or `-browser`.
3. **The picker lists people with an unexpired session**, in addition to the broker's list. A session exists only after the broker authorized the person's binding at sign-in, and withdrawal removes it. Someone who signed in long ago and whose sessions all expired is not listed on an open-admission server. Alternative: a new broker operation listing bindings, a broker protocol change.
4. **The gateway forwards only the operations in its own `guestOperations` table** (join for now), as well as the daemon's own table. Defence in depth at the cost of adding each later route in two places.
5. **The listing is not gated on the participant's own experimental switch.** An entry exists only when an owner with the feature invited them, and the browser part will be behind the switch. Gating would cost a daemon request per listing.
6. **A failed index write after the daemon's change answers 503 `shares_unavailable`.** For an invitation the record holds and the owner invites again; for a removal the owner's daemon already refuses. The join records `joined` in the index best-effort only (it is used for the list, never for access).
7. **An owner's re-invitation of a readmitted person who is still `joined` in the record** creates a share in state `joined`: it is the owner's explicit decision. Alternative: require the record to restart at `invited`, a daemon change.
8. **Out-of-order member replies** from two of the owner's tabs (remove, then re-invite within the bridge revocation wait) could leave the record `invited` without an index entry. It closes access, heals on the next invitation, and its fix would add state; dropped by the review triage (rule 1b).

## Installation change needed (not made here)

This release's daemon requires three socket descriptors, so the test installation must install and restore the guest socket in the same round, or the daemon cannot start and the test-release watcher refuses the release. In our test installation's operator the agent socket's handling is the template; the guest socket needs the same, with the daemon socket's identity:

- `six_unit_contract.py`: `socket_contract(unit, 'guest')` with `ListenStream=/run/open-habitat/users/%i/guest.sock`, `SocketUser=%i`, `SocketGroup=open-habitat-gateway`, `SocketMode=0660`, `FileDescriptorName=guest`, `Service=open-habitat-daemon@%i.service`, `RemoveOnStop=yes`, `DirectoryMode` within `0710` (the `kind in ('agent','daemon')` branches must include `guest`); a `GUEST = 'open-habitat-guest@.socket'` with a `guest_payload()` like `agent_payload()` (the daemon unit now names `open-habitat-guest@%i.socket`); `release_units()` and `STORAGE_DEPENDENTS` include it; a `GUEST_GATE` JIT-gate drop-in under `open-habitat-guest@.socket.d/` with the same bytes as `AGENT_GATE`, added to `POLICY`.
- `guest_release.py` `install_units()`: install, verify and roll back the guest unit exactly as the agent unit (first install when the predecessor had none; refuse a rollback that would drop it).
- `jit_acl_prepare.py`: start/stop `open-habitat-guest@<name>.socket` beside the agent socket when the template exists; `release_fresh_next.py`: the socket-name pattern accepts `guest`, and the paired-socket policy migration covers it.
- Directory and ACL: none new. `guest.sock` sits in the same per-user directory `/run/open-habitat/users/<name>/` (root-owned 0710, named search ACLs `user:<uid>:--x`, `user:<gateway-uid>:--x`, `mask::--x`) that the gateway already traverses for `daemon.sock`; the broker's `socket()` check already requires exactly that ACL.
- Tests next to `test_agent_socket_policy.py` and `unit_fixtures.py` for the new unit.

## Review

Critical-rigor `/llm-review`: gpt-6-astra as finder, claude-fable-5-2 as verifier, two model calls. `/assess-findings`: two FIX, one DROP. Fixed with regression tests: an upgrade from a predecessor without the guest unit was refused by the exact predecessor policy comparison and fragment check; an owner's `full_rights`/`take_back` after a withdrawn person was readmitted recreated their share. Dropped (rule 1b): the rare out-of-order reply race in decision 8.
