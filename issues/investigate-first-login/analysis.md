## Failure boundary and provisioning stages

Source at deployed pilot.2 revision (`internal/gateway/auth.go`, `github.go`, `internal/provision/writer_linux.go`; deployment receipt above) establishes the following sequence. A successful `/auth/github/start` stores an in-memory flow with a five-minute TTL, sets a secure Lax flow cookie and redirects to GitHub with `state` and PKCE. The callback **first consumes** its stored state and clears the flow cookie, then checks the exact callback request. For `invalid_request`, the sole callback branch is failure of **both** permitted `exact()` shapes: exactly one nonempty `state` and exactly one nonempty `code`, **or** exactly one nonempty `state` and exactly one nonempty `error`, with no additional query key, parse error, path/fragment mismatch, host mismatch or absent TLS. No provider exchange or broker `ensure` occurs after that branch. The same-origin HTML redirect to the reported URL additionally requires TLS, the configured Host and `Accept` containing `text/html`; thus, *if that URL came from this gateway callback*, Host and TLS passed for the failure response. Given the router's registered GET callback and that redirect, the plausible remaining mismatch is query shape (extra/duplicate/empty parameter or malformed encoding; path/fragment also checked). This **does not identify which predicate failed**, and the callback itself was not observed in a request log. Do not attribute it definitively to Cloudflare or GitHub: the proxy route forwards to a TLS origin, and no captured request proves that an intermediary changed the query. GitHub's usual `code`+`state` success shape would pass; a normal `error`+`state` shape would fail later as `authentication_required`. `callbackFailure` also emits `invalid_request` from other handlers only as a JSON API error, not this same-origin HTML redirect. A forged/stale URL or an unobserved intermediate redirect cannot be excluded solely by the final address.

## Diagnostic gaps and recommended work

1. **First, resolve the actual callback shape without exposing OAuth values.** Add a gateway event for each OAuth start and callback outcome using a cryptographically random, short-lived, server-side attempt ID generated at start (separate from OAuth `state`, session ID and cookies), carried only in the in-memory pending entry and emitted to the operator log. On a callback with no matching pending flow, emit a new independent request ID, not a hash of attacker-supplied state. Record a bounded reason enum such as `shape_extra_key`, `shape_duplicate_key`, `shape_missing_or_empty`, `shape_parse_error`, `host_mismatch`, `tls_missing`, `flow_missing_or_expired`, `browser_mismatch`, `provider_denied`, `exchange_failed`, `broker_denied`, `handoff_failed`, `session_created`; never log URI, query values, code, state, verifier, token, cookie, headers or raw errors. Parse reason classification *before* consuming the pending flow if doing so cannot change the existing fail-closed behavior; do not change the security ordering just for observability. Response-visible opaque support ID can reference the server-side event without making the reason public. The current hard-coded `req_00000000` in JSON errors cannot correlate anything.
2. Add structured, bounded stage events for broker ensure (request admitted, reservation, account/home/config/socket/unit, publish, readiness) and handoff/reauthorize **without** ID, username, UID, path, email, IP or command output. Store durable phase evidence only in root-protected Fleetrepo/operator space, never public logs. A pending marker already guards interrupted provisioning; distinguish `no_request`, `rejected_before_ensure`, `pending`, `binding_committed`, `ready`, `credential_acknowledged` and `session_issued` with the same attempt ID over an authenticated internal boundary. Avoid ambiguous success events before durable publication; lost acknowledgement must remain terminal.
3. Configure narrowly scoped, short-retention logs at the gateway/ingress layer for method, *route template* (not raw path/query), response class and generated request ID. Do not log full HTTP URLs in Cloudflare, tunnel or generic Go access logs: OAuth query strings carry authorization codes and state. Restrict journal access and retention; test failure branches with synthetic credentials and verify that no secrets or identities appear. Do not trust client-supplied correlation headers or forwarded identity/IP as an auth signal. Where Access can offer an audit record, correlate only by time and operator-held random ID if supported; do not export Access identities into this repository.
4. The UI in `web/src/app/App.tsx` checks only presence of `auth_error` and displays a generic warning. Keep generic user-facing errors, but show a safe support ID if issued. Do not treat the supplied query value as authoritative, and do not display server internals or raw provider errors.

**Next fix/retest:** implement the narrow callback reason telemetry and synthetic tests for extra, duplicate, empty and malformed query keys, host/TLS and flow expiry; review the logging fields for secret leakage. Have Jari initiate a **new** login himself after a reviewed deployment, then correlate his reported time/support ID with restricted gateway, ingress and broker stage events, inspecting the root-only ledger and pending state read-only. If the real request shape differs from the contract, decide with Jari whether to reject it intentionally or adjust a narrowly specified shape; do not loosen OAuth validation blindly. After a successful two-login trial, separately verify same binding and native `gh` under that account with Jari's consent. The incident remains open until root cause and retest are observed.

**Review/validation choice:** report-only investigation: manually cross-checked source branch ordering against the read-only live aggregates and Fleetrepo runbooks. No external model review or full CI, because private incident evidence must stay off model prompts and no executable code changed. Markdown/link checks and diff inspection are sufficient for this report; live request reproduction would require Jari actively driving a new login.
