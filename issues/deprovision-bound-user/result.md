## Inspected boundary

At product revision `d5ec12c` (starting HEAD), `internal/provision/writer_linux.go` chooses the first UID absent from `bindings.json`, and the version-1 ledger parser in `state_linux.go` and `writer_linux.go` has only live bindings. `broker_linux.go:Startup` verifies every row as a present account. A pending marker refuses all broker routes. `internal/gateway/revoke.go` calls broker `authorize` before invalidating existing sessions and pre-cutoff OAuth states; it cannot do so while a broker writer holds the exclusive state lock. New OAuth states after cutoff remain permitted. Authenticated requests reauthorize and compare the mapped identity (`internal/gateway/auth.go`), but requests already running cannot be recalled.

The checked-in *private* Fleetrepo `infra/native-agent-host-test/JIT-POLICY.md` describes the pilot.11 four-file v1 state and explains that `broker-high-water.json` is written at seeding only, not updated with later assignments. The checked-in Fleetrepo `jit_policy.py` requires exactly v1 binding keys and verifies bound UIDs against NSS (lines 157–210). These are source inspections, **not a read of the guest's state**. The v1 state cannot express a retired binding, and the current activation gate cannot accept one. The current durable state also cannot prove that an absent UID was never previously allocated and removed if the state was restored from a complete earlier snapshot: the independent receipt remains at its seed value. A proposed migration preflight checks `generation == 1 + len(bindings)` and exact NSS/path inventory, but this alone does not prove no whole-state rollback. The root operator must establish independent history or quarantine unprovable slots, and Fleetrepo's activation policy must change in step with the product's format. Freeze ordering can use a root allowlist removal with an epoch bump *after* successful session revocation, while the binding remains live; deletion must refuse an allowlisted subject and quiesce in-flight requests. Simply dropping a ledger row or running `userdel -r` is unsafe.
