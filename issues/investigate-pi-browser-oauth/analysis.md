# Pi browser OAuth: bounded feasibility analysis

2026-09-29. Scope: Pi **0.85.1** installed package, current host source on this branch, synthetic evidence only. This is not provider acceptance, an implementation design approval, or a live sign-in result. The issue remains open.

## What Pi actually does

The installed `@earendil-works/pi-ai/dist/auth/oauth/openai-codex.js` (dependency of `@earendil-works/pi-coding-agent@0.85.1`) has a fixed client ID and `REDIRECT_URI = "http://localhost:1455/auth/callback"`. Browser login generates a random 32-byte PKCE verifier and S256 challenge plus a random 16-byte hex state; its authorization URL includes that exact redirect, `response_type=code`, `openid profile email offline_access`, and Codex-specific query parameters. Its Node HTTP listener binds port 1455 to `PI_OAUTH_CALLBACK_HOST` or `127.0.0.1`; **that environment setting changes the listener bind address, not the authorization or token-exchange redirect URI**. The listener checks path, state and nonempty code, but has no web-session cookie or mapped-UID binding. It then exchanges the code with the same fixed redirect URI. If the listener cannot bind, Pi resolves its wait as null and offers manual code/redirect-URL entry; manual input accepts a bare code without state and checks state only when supplied. Neither route can turn the advertised OAuth redirect into this host's HTTPS callback. On a remote server the user's browser interprets `localhost` as the user's own machine, not the server.

Device flow is materially different: Pi asks for a device code, polls the device-token endpoint, receives an authorization code *and verifier* from that flow and exchanges them with `https://auth.openai.com/deviceauth/callback`. Pi's OAuth credentials (access, refresh, expiry, account ID extracted from access-token claims) are managed by Pi's native auth runtime in the user's `~/.pi/agent/auth.json`; the host's helper does not return the token. These are observations of the installed code, **not** evidence that OpenAI accepts a different redirect or application registration. See Pi's `docs/providers.md` and `docs/custom-provider.md`: provider extensions can implement a new OAuth flow, but documenting that extension point does not make the built-in Codex client's redirect configurable.

## Existing host boundary and proposed safe shape (not implemented)

`internal/gateway/auth.go` already owns a *different* GitHub OAuth flow: exact HTTPS origin/callback, one-time state, PKCE S256, five-minute flow cookie, Access assertion continuity where configured, verified provider identity, broker `ensure`/`authorize`, then session issuance. Its GitHub identity cannot be reused as an OpenAI identity. `internal/gateway/access.go` enforces configured Access ingress even on OAuth start/callback. `internal/gateway/pi_attempt_linux.go` routes only the broker-revalidated session's mapped socket and hashes the session cookie into a daemon attempt owner, never forwards the bearer cookie. `internal/daemon/pi_attempt_linux.go` checks trusted peer/binding plus attempt owner, and `pi_device_linux.go` runs a pinned Pi SDK child as the daemon's UID with HOME/path validation and bounded lifetime. That adapter **forces device_code**, whitelists its frames, and has no browser callback interface; a new browser flow cannot simply select Pi's existing browser method. See `docs/adr-0003-host-stack.md`, `docs/adr-0004-first-login-user-provisioning.md`, and `docs/interfaces.md` under Pi onboarding. GitHub logout, web logout, and Pi credential removal are distinct.

**Candidate, conditional on provider support:** Keep HTTPS same-origin browser authentication, Access ingress, CSRF on the initiating write and mapping checks in the gateway; keep Pi token exchange and native storage inside the mapped-UID daemon. Gateway would issue a short-lived, unpredictable, single-use state tied in memory to the authenticated web session *and its currently broker-verified immutable UID/binding/epoch*, a same-site browser flow cookie where needed, and one specific pending daemon operation. The mapped daemon, not a browser or gateway token cache, owns the PKCE verifier and the exact provider client/redirect configuration; only an authenticated gateway-to-that-daemon UDS operation could consume the callback's code. On return, require exact configured HTTPS host/path and expected callback parameters/issuer (if available), state and browser binding, active session and fresh broker authorization (same UID/binding/epoch); consume state atomically on both success and error, refuse expiry/replay, mismatched Access assertion, concurrent or cross-session completion. A state-only callback is insufficient: a leaked URL/code or state must not authorize installation to a different session/UID. The gateway should send only a bounded, validated code to the originally mapped daemon after rechecking its socket and identity; it must not exchange/store/access/log credentials or read the user's home. The daemon must verify the operation is owned by that mapped session, bind its verifier to the state/redirect, exchange only with the pinned provider endpoint, and let Pi's native credential runtime write under its own UID. Recheck native status after completion; unknown or lost acknowledgements remain unknown, with no automatic replay or credential transfer. Cancellation/timeout/browser logout must end ownership; handle late callbacks and in-flight exchange explicitly. A native Pi logout/disconnect and provider revocation need separate, honest UI semantics.

This is a **new cross-component OAuth protocol and browser/daemon contract**, not a reuse of the GitHub token handoff or current device attempt. In particular `X-Agent-Host-Session` on the current device attempt is a gateway-supplied owner hint over a trusted peer, not independent authentication against a compromised gateway. Do not treat a guessed UID, provider `email`, unverified JWT payload, callback query, or browser-supplied owner as routing authority. Review cookie SameSite behavior on a top-level provider redirect, session rotation during the flow, process restart, two tabs, binding revocation, race with logout, callback query leakage (referrer/logs), issuer mix-up, and disconnect/refresh handling before implementing. A gateway that now transports an OpenAI code is not supposed to gain native credential authority, but extending it to terminate the exchange or write `auth.json` **would move the authority boundary** and should not be done by convenience. Even code relay is a security-sensitive contract change that requires Jari's architecture choice and a reviewed threat model.

## Alternatives and feasibility

1. **Keep current device code** (baseline, currently implemented). It already delegates provider exchange and Pi auth storage to the UID-owned helper. Less smooth UX; no claim of browser OAuth.
2. **Provider-supported HTTPS redirect and UID-owned exchange** as above. Preferred direction *only if* the existing Codex client can legitimately use a registered HTTPS redirect and Pi supplies a supported adapter/auth-runtime path for that flow, or a separately authorized provider client is available. Pi 0.85.1's built-in browser flow cannot be parameterized to do this: changing only `PI_OAUTH_CALLBACK_HOST`, forwarding a public URL to port 1455, substituting a redirect at the proxy, or pasting a code into the gateway does not change the authorization and exchange redirect URI. Silently patching the bundled OAuth module is not a stable integration. A custom provider extension is an API possibility, **not proof** that this particular Codex grant permits another client/redirect or that the required scopes and native provider credentials match.
3. **Local loopback browser flow on the user's own machine** (or carefully authenticated reverse tunnel to the mapped daemon). Potentially retains Pi's fixed URI but depends on trusted local callback ownership and an authenticated transfer to the correct UID; open loopback listeners, code paste, URL forwarding or unauthenticated tunnels weaken session/UID binding. It is not an ordinary web callback and is not recommended for this product without a separate design decision.

The previous unauthenticated provider probe described in `item.md` / `TODO.md` got anti-bot 403. It proves neither acceptance nor rejection of an HTTPS test-host redirect. No request to an OpenAI endpoint, anti-bot probe, live callback, browser profile, credential, or real identity was used in this analysis. Open questions include whether OpenAI permits this client ID with any non-loopback redirect, whether another approved Codex client registration is available for this host, whether token exchange requires exact registered URI/client, how organization/account selection and refresh/revocation behave, and whether Pi exposes a supported way to install externally obtained Codex credentials without bypassing native validation. Do not infer permission from syntactically generating a URL or from fixture success.

**Decision question for Jari:** Should we retain device sign-in unless a consented, provider-approved HTTPS callback can be proven, and, if proven, accept the gateway as a browser/session/UID-bound *code relay only* with all provider exchange and Pi credential handling under the mapped daemon UID? Record that interface and its trust limits in an ADR before opening an implementation issue. A provider experiment would first need Jari informed, an exact provider-approved redirect/client and authenticated return route, disposable/test-only state, scoped consent from the participating person, no bypass of Access/anti-bot, a verified abort/recovery and credential-removal plan, and a rollback of any temporary host configuration. If those conditions cannot be met, keep device code and report compatibility unknown rather than trying live auth.
