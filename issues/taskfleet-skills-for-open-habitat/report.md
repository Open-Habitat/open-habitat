# Taskfleet skills for Open Habitat — proposal for Jari

Research completed 16 October 2026. **Recommendation, not an architecture decision.** No software, skills, settings or services were installed or changed on any machine.

## Recommendation in brief

- Supply a small, versioned **Open Habitat Pi skill package**, enabled by the operator alongside its declared Taskfleet runtime. Keep Taskfleet's CLI manual upstream-owned; do not copy Jari's whole personal skill collection into users' homes.
- Start with **four browser-oriented skills**: overview, spawn, inspect/wait, and merge/report. Ordinary delegation must work without issuectl, Fleetrepo, `tw`, Telegram or a desktop seat.
- Keep native Taskfleet ownership. Spawn autonomous runs headlessly, await them through Pi's process tool running `taskfleet run wait`, and bring the result back into the parent conversation. The browser's child view is observation, not another worker controller.
- Pin the package to a tested Taskfleet release, initially **0.15.0**, not Alder's installed 0.13.1 instructions. Test both parent and worker discovery. Updating only the browser parent's skills is insufficient.
- Leave research, bug triage, ADR delegation, fan-out and stint orchestration as subsequent opt-in workflows. Especially do not turn issuectl's scheduling model into an Open Habitat requirement.

## Evidence and scope

I read all 14 installed skills in the table below, both locations' inventories, Fleetrepo's ownership guidance and runtime declarations, the corresponding templates at the guest's released Taskfleet commit, ADR 0017, the spinoff implementation result and relevant daemon code. All 14 Claude/Pi pairs are byte-identical: Pi currently receives instructions that still mention Claude's Skill tool. This is a portability defect in the instructions, not evidence that Pi has that tool. [S1–S5]

The task's starting premise needs correcting: Fleetrepo authors **personal context and deployment policy**, but the requested skill family is now authored in **Taskfleet**. Fleetrepo explicitly warns against shadow copies of tool-owned skills. Its updater installs the binary's emitted catalog rather than taking skills from a development checkout. [S2, S3]

Observed local `taskfleet version --json`: **0.13.1**, commit `96ee31cc9e425f7132ef76eb20543ec552aed711`, all 14 skills pinned to that version. The guest deployment evidence records **0.15.0**, producer commit `8464733b0d69cf1342eed64995163fd36c33523d`. I did not log into the guest or repeat a live browser/provider journey; the guest claims below are sourced deployment evidence, not new measurements. [S1, S4]

The released templates are nearly identical after substituting the version: 0.15 adds `run wait --terminal` guidance in run-overview/spinoff, and research now also permits an explicitly configured autonomous Claude profile. Thus merely installing the newest generic catalog does **not** remove the browser/Pi mismatches. [S5]

## Assumption audit

The explicit family contains **no literal dependency on `alder`, `tw`, Fleetrepo, `notify-jari`, or glasspad**. Those are inherited from Jari's global context, related skills and fleet setup. This distinction matters: there is no reason to rewrite every Taskfleet skill as if it hard-coded Alder. The following covers the environment assumptions found in the skills and their surrounding context. [S1–S3]

| Assumption / source | Holds for a mapped user? | Variant or installation consequence |
| --- | --- | --- |
| Human sits in the launching tmux session; tell them the window/session and `tmux attach -t headless` (spawn/research/analysis/decision/fan-out) | **No as the primary UX.** Native tmux still exists behind the browser. | Say “the delegated task appears under this conversation”; retain full run ID for diagnostics, not instructions to attach a seat. |
| No tmux means no workers; `--headless` means no tmux at all | **First part false; second is a misconception.** Headless placement still uses native tmux. | Explicit `--headless` is the ordinary browser spawn placement. Operator supplies Taskfleet/workmux/tmux; agent does not start an unrelated tmux server by hand. [S4, S5] |
| Headless placement alone makes processes independent of the launching daemon | **Not sufficient.** Linux cgroup lifetime also matters. | Use Taskfleet's native Linux user-manager services, with a private runtime directory/bus and persistent user manager. These were tested by the guest runtime work; do not reimplement detachment in the skill or daemon. [S4, S8] |
| A macOS foreground batch exhausts PTYs near five/six; use headless above three (spawn/fan-out/stints) | **Not a Linux capacity rule.** | Remove numerical macOS rationale from default browser guidance. Keep bounded concurrency; v1 needs one child at a time, not fan-out's default ten. |
| `tw` identifies the seat and routes clipboard, browser, `code`, Desktop/files (global context) | **No.** Arbitrary users have no Jari seat/SSH reverse channel. | Use parent text and repository artifacts. Do not install `tw`, refer to Jari's laptop, assume Downloads, or attempt desktop access. |
| Fleetrepo is the user's fleet manager and source of global context (global context) | **No as product contract.** It happens to operate this test host. | Operator declares runtime versions and skill package; neither gateway nor user agent runs Fleetrepo convergence. Generic documentation names the operator, not Fleetrepo. |
| `notify-jari`, Telegram, `.workmux.yaml` emoji identify completion (global context) | **No.** | No notification hook by default. Watched native wait returns to the parent. User-selected external hooks remain optional and must not embed personal destinations. |
| `--notify` is a guaranteed UI wake (spawn family) | **No.** It is an arbitrary supervisor-side shell callback, at-least-once, not browser integration. | Do not fabricate a callback/FIFO/Telegram transport. Use the existing process tool wake contract; warn that a disconnected/restarted parent may need a fresh wait. [S6, S7] |
| `capable`, `implementation`, `lightweight` profiles exist; model argv is supplied by user configuration (overview/spinoff/decision) | **Configuration ownership holds; names do not.** Alder itself defines `capable` but not the other two normal tiers. | Use configured default unless the user explicitly selects an available profile; dry-run before mutating. No model names, Alder launcher paths or silent downgrades. A profile is not test evidence. [S2, S5] |
| Alder's `alder-intake` and document-rethink launchers/profiles can be copied | **No.** They include local absolute paths and personal model choices. | Never ship them. Optional operator seed profiles must execute as the mapped UID and use that user's credentials; repository config must not define executable profiles. [S2, S5] |
| Authentication/default model/PATH in a child equals the interactive parent model/session | **Not guaranteed.** Worker is a new native process. | Verify the mapped user's worker Pi can authenticate and find the declared binaries under a minimal environment. Do not borrow another user's auth, forward browser credentials or promise parent's selected model is inherited. [S4, S5] |
| Autonomous workers cannot ask the user directly; `--interactive` offers hands-on review (family) | **Autonomous model fits; interactive UX does not yet.** | Read-only child views have no composer or settlement controls. Surface safe forks through native awaiting-input/report and the parent; v1 does not advertise interactive child conversation. Do not automatically apply unsafe defaults just because a timer expired. [S6] |
| Browser parent identity and Taskfleet parent-run identity mean the same thing | **No.** | Daemon supplies `TASKFLEET_CREATOR_SESSION=pi:<native-id>` for creator attribution; preserve it when the parent invokes Taskfleet. Never invent/override it. `--parent-run-id/--parent-node-id` are native driver topology, only for actual driver children. Worker launch clears inherited creator attribution, so grandchildren are not automatically the top-level parent's direct children. [S6, S8] |
| Runs may live anywhere under `TASKFLEET_HOME` (generic overview) | **Not for browser visibility.** | Browser reads the mapped user's fixed `~/.taskfleet` root. Do not relocate it in the skill. A custom native home may work in SSH while being absent from the browser. [S7] |
| A run in this Git repository must appear under this parent | **No.** | Browser association also requires exact creator and source-checkout attribution; sibling worktrees sharing a Git common directory are not interchangeable. Create from the parent's real checkout; do not infer association from titles, branches or repository membership. [S6, S7] |
| Browser inventory delivers the worker's result to the parent agent | **No.** | Inventory/transcript are human read views. Parent explicitly waits, then reads native report. Neither visible terminal status nor a disappearing tmux window is merge proof. [S6, S7] |
| `issuectl`, repository schema, DAG, reservations and issue trailers are universal (worktree/stint family) | **No.** Arbitrary workspaces may use GitHub Issues, another tracker or none. | Core spawn accepts free text and has no tracker side effects. Enable issuectl workflows only when binary and repository schema exist. Preserve intake-only, unlaned filing and exact originating-run provenance when applicable; never install a tracker or create a schedule opportunistically. |
| A driver and every child can close the originating issue | **No, even on Alder.** | Retain native driver ownership: children do not race on shared issue lifecycle; bug-analysis informs disposition rather than closing. [S1] |
| Claude Skill tool, `/git-*`, `/complex-rebase`, `/llm-review`, `/assess-findings`, `/wrap-up` are installed (router and cross-skill prose) | **No.** Installed Pi copies do not adapt these references. | Read skill files with Pi's read tool and execute documented CLI commands. Use ordinary Git and deterministic validation; optional reviewers need their own configured tools. Never claim a mandated review ran when missing. [S1, S9] |
| Shell-background waits wake Pi; a browser status chip itself is the wake source | **No.** | Start native wait through the existing process tool with turn notifications. No `&`, `nohup`, sleep/show polling or second job registry. The process implementation owns waiting/wake facts. [S6, S10] |
| Glasspad is available and safe to publish (global context) | **No.** It is not required by these 14 skills. | Commit Markdown and summarize in the parent. Rich publishing is a separately configured user capability and an explicit exposure decision, never an implied report-delivery step. |
| User homes/configuration are interchangeable; operator can install personal settings as root | **No. Unix UID is the boundary.** | Operator may distribute root-owned read-only skill bytes, not shared credentials/state. Any per-user activation must respect ownership and existing settings; no copying Jari's home, auth, trust settings or `TASKFLEET_HOME` into other accounts. [S6, S7] |
| Worker self-merge also pushes Git remotes, deploys, resets accounts or changes global preferences | **No.** | Preserve Taskfleet merge/report as local delivery. Project-authorized remote push/deploy is separate. Missing prerequisites are reported, not globally installed. Stint conventions and reset policies belong to each project. [S1, S6] |
| New worktree sees uncommitted source edits and all project-local skills | **First false; second conditional.** | Commit the brief's prerequisites; respect dirty source checks. Project skills must be committed/trusted, and package discovery must be tested from a newly created worker worktree, not only a parent RPC session. [S1, S9] |

## Proposed browser-native workflow

This is the behavior to write into the variants, not a new daemon authority or API:

1. Read project instructions and validate a bounded task, source branch and clean committed prerequisites. Check supported Taskfleet version and configured Pi worker; missing runtime/auth is an operator/user setup result, not permission to install or share credentials.
2. Preflight the intended native create with `--dry-run`, then create `--kind spinoff --headless`, a self-contained brief and a stable idempotency key. Keep the environment's creator-session attribution. Avoid `--interactive` in v1. Include exact validation, full run identity, merge/report and blocked/failure contracts in the worker brief; do not rely on a sibling skill happening to be loaded in the child.
3. Start `taskfleet run wait <full-run-id> --output json` with Pi's **process** tool, exit notifications set to wake the parent. Use a simple command with literal run IDs: no shell variables, pipes, substitutions or `&&`, because browser wait recognition is deliberately narrow. End the turn or do independent work. The existing browser shows the task under the originating parent turn; no user has to find a tmux window. [S6, S10]
4. On wake, inspect `data.outcome` and `data.runs[]`, not `lifecycle` or a guessed top-level status. Timeout is not completion. Attention/stall/awaiting-input can settle a wait without terminal success. Surface the question in the parent; `--terminal` in 0.15 is useful after attention has been handled, not a way of answering it. [S5]
5. Read `run show <id>` for full report, `landed`, method and retained work. Explain what changed and what remains. Never infer an integrated Git OID from the pre-rebase worker OID, and never promise browser write controls. [S4, S6]
6. Child succeeds by committing and calling native `run merge <exact-id> --report-file ...`; supervisor owns teardown. A blocked required step reports failure and preserves work. Parent can discuss recovery, but a failed/retained branch is not disposable and is not a reason to respawn blindly.

**Reconnect caveat:** native children can outlive the parent service. That does not mean the parent's process wait survives the same restart. After reconnect, inspect the known run and establish a fresh wait when needed; do not create a duplicate child to recover a lost observer. [S4, S6]

## Distribution: three choices, one recommendation

| Choice | Benefit | Cost / boundary |
| --- | --- | --- |
| Product ships and auto-enables a full fork of all Taskfleet skills | Discoverable on first login | Couples every Taskfleet release to product text; brings a tracker and personal workflow into arbitrary accounts; parent-only injection misses workers. Not recommended. |
| **Product maintains a small Pi adapter package; operator declares its activation with a compatible native runtime** | One browser-specific manual, reproducible setup, no new agent controller; operator retains dependency choice | Needs explicit compatibility and parent/worker discovery tests. **Recommended.** |
| Every user installs/adapts the generic catalog themselves | Maximum personal control; no product packaging | First-run delegation remains inconsistent and easy to leave stale. Appropriate opt-out/customization path, not the default hosted experience. |

The recommended package contains four namespaced entries, for example `oh-taskfleet-overview`, `oh-taskfleet-spawn`, `oh-taskfleet-status`, `oh-taskfleet-merge`. Namespacing avoids silently shadowing an existing user's generic Taskfleet skills. Descriptions distinguish the browser workflow; setup diagnostics should detect competing instructions rather than relying on discovery order. Pi keeps the first duplicate name and warns. [S9]

Author only the **Open Habitat delta** here: browser observation, explicit watched wait, mapped-user/runtime constraints and Pi-native invocation. At package build time, take the exact release's generic reference text from that released Taskfleet binary's `skill print` catalog, recording source version/commit/digests. Include the necessary upstream references inside the package so the manual is self-contained and does not depend on a live source checkout or network lookup. Do not maintain fourteen independent command recipes or rewrite upstream version pins by search-and-replace. Taskfleet remains owner of its run semantics; generally useful Pi-portability fixes should go upstream. [S3, S5]

A Pi package is an ordinary package with an explicit `pi.skills` manifest; for v1 it needs **no executable extension**. Operator can place versioned read-only package bytes with the declared runtime and activate them through Pi's existing skill paths or package declaration. Both browser Pi and Taskfleet's native Pi worker must discover the same package. A user-level resource declaration pointing at operator-owned bytes is one viable native mechanism; reconcile only managed settings, preserve foreign entries and report conflicts. Do not create a gateway/provisioner service that edits arbitrary users' homes on every login. Exact packaging/activation mechanics need implementation validation, not an ADR hidden in this report. [S9]

Keep these per-user: credentials, model choice, executable profiles, project trust and personal skills. Operator may offer an opt-in default Pi profile and capacity policy, but not a shared credential or Alder-specific launcher. Keep these per-repository: tracker/schema, quality gate, ADR authority, push/deploy permission and handoff conventions. This split preserves the product's existing Unix-user model. [S2, S6]

## Release coupling and first-version proof

Treat the deployed combination as a tested tuple: **Taskfleet version/commit + adapter package version/digest + Pi/process integration version**. Start with exact 0.15.0 support; widen a compatibility range only after testing it. The browser's “0.15+ readable” condition is not proof that every future CLI command or worker contract is compatible. [S4–S7]

An operator update should stage the matching package and runtime together, check the emitted catalog/version, validate the examples against that binary, and verify effective skill discovery for an existing user and a fresh worker. Select the tested tuple without replacing files being used by active workers. Unsupported or shadowed user-local versions produce a clear setup warning; agents do not silently run upgrade/install or `--force` over personal files. An existing session may need a native reload/new session to refresh its skill catalog; do not promise hot replacement of instructions already in context. [S3, S5, S9]

Minimum implementation scope:

- Four skills above; one ordinary autonomous Pi child, no tracker, no external notification and no interactive-child UX.
- Operator-declared native Taskfleet/workmux/tmux and independent Linux user-manager runtime; mapped user's own working Pi authentication. Reuse deployed runtime work rather than adding another supervisor.
- Read-only child group/transcript/result already implemented by ADR 0017. No new Taskfleet state, session registry, credential broker or browser merge authority.
- Existing parent process wait/notification mechanism; complete worker brief and exact closing path.

Before claiming v1 works, demonstrate:

1. A fresh mapped user and an existing user with unrelated custom Pi settings both discover the package in parent and child; setup neither overwrites personal skills nor reads another UID's data.
2. A real provider-backed parent spawns a headless native child, sees it only under the correct parent/source checkout, waits, wakes, reads the report and confirms landed content. A sibling worktree and a second Unix user cannot obtain that child view.
3. Browser disconnect/parent daemon restart does not kill the native child; reconnect inspects the same run rather than duplicating it. Explicitly test and document re-establishing a lost wait.
4. Failure, attention, timeout, retained work and unknown profile/version are reported honestly; a successful exit alone is never success. Merge retries preserve native transaction semantics.
5. The installed release's bundled examples and adapter command examples parse; no required Claude-only tool or personal CLI remains. Missing web/reviewer/tracker capabilities are not falsely claimed.

Existing synthetic browser and guest-runtime evidence is valuable but does not yet prove item 2's real-provider/distinct-user end-to-end flow. This research does not claim that test. [S4]

## Decision requested from Jari

Approve the **four-skill, operator-enabled Pi adapter package** as the next implementation scope, leaving issuectl/stints/fan-out optional. This gives a browser user reliable delegation without turning the host into Jari's personal workstation. An implementation issue can then settle concrete packaging against the selected guest Pi runtime and run the proof above; architecture authority remains with Jari.
