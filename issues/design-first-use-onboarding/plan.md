# First-use onboarding: Pi subscription login (design proposal)

**Status:** product behavior accepted by Jari on 2026-09-27 in [item.md](item.md); **security architecture proposed, not accepted or implemented**. This is an implementation brief for review, not a claim that the installed host already gates access. No live sign-in, credential file, browser profile, or other person's identity was used. Do not deploy this design as-is. Source baseline: [interfaces](../../docs/interfaces.md), [architecture](../../docs/architecture.md), [v1 plan](../plan-v1-implementation/plan.md), [ADR 0003](../../docs/adr-0003-host-stack.md), `internal/gateway/auth.go`, `internal/daemon/snapshot_linux.go`, `contracts/v1/snapshot.schema.json`.

## Recommendation and native evidence

Make the mapped **user daemon** own a short-lived Pi-native OAuth login operation via a pinned, UID-local Node helper calling Pi's `ModelRuntime.login("openai-codex", "oauth", interaction)`. Return only a Pi-generated authorization URL and redacted progress to the browser; relay the final *provider redirect URL* from a same-origin POST through the gateway to that daemon exactly once. Pi generates/verifies PKCE, state and exchanges the code; Pi alone writes and refreshes `auth.json`. Do not implement another token exchange, copy a Codex credential, reuse the GitHub OAuth token, or give the gateway read access to a home. **First modify/upstream Pi's browser-login seam to support a manual-only mode with no TCP listener and mandatory state in the pasted redirect URL.** The installed version lacks both guarantees. Treat that small Pi-side capability as a prerequisite; do not ship the web login by invoking the unmodified browser flow or by accepting bare codes. The provider's fixed loopback redirect makes a seamless host-HTTPS callback impossible with this native flow; show a clear instruction to copy the URL from the browser's loopback failure page/address bar and paste it into the host wizard. Validate that this is usable on the actual pilot browser before acceptance. If the provider changes redirect behavior so the URL cannot be copied, stop and bring the trust-boundary decision back to Jari, not a homemade OAuth client.

Inspected local installation: `pi --version` and package `@earendil-works/pi-coding-agent/package.json` both **0.85.1**. Installed package paths below are relative to the installed `@earendil-works/pi-coding-agent` npm package root (installed artifact, not this repo). Read `README.md`, `docs/providers.md`, `docs/sdk.md`, `docs/rpc.md`, `docs/extensions.md`, `docs/custom-provider.md` and the referenced auth implementation; docs describe APIs, **not a working web-embedded `/login` endpoint**.

- `docs/providers.md`: `/login` is interactive; OpenAI ChatGPT Plus/Pro is `openai-codex` subscription, distinct from the OpenAI API-key provider. OAuth saved in `~/.pi/agent/auth.json`; `/logout` removes stored auth. `docs/rpc.md`: built-in TUI `/login` and `/logout` are **not RPC commands** (`get_commands` does not include them). Sending `/login` through RPC `prompt` does not authenticate. Extension UI forwarding in RPC applies to extension dialogs, not the built-in TUI command.
- `dist/core/model-runtime.{js,d.ts}` exposes `ModelRuntime.create`, `login(providerId, type, {signal,prompt,notify})`, `checkAuth`, `listCredentials`, `getAuth`, `logout`. `dist/node_modules` is not used; provider source is `node_modules/@earendil-works/pi-ai/dist/auth/oauth/openai-codex.js`, `.../providers/openai-codex.js`, `.../models.js` and `.../auth/resolve.js`. `ModelRuntime.login` serializes same-provider credential mutations, calls provider login and native credential modify, then synchronizes model availability; `CredentialSynchronizationError` means the credential mutation may already be committed. SDK is a **Node process API**, not a Go/web API; a minimal helper run as the daemon's UID is needed. Never echo `login()`'s returned credential.
- Native `openai-codex.js`: `login` first selects `browser` or `device_code`; v1 wizard must select **browser only**. Browser mode generates a random 16-byte hex `state`, PKCE S256 challenge/verifier, uses `https://auth.openai.com/oauth/authorize` with `response_type=code`, `scope=openid profile email offline_access`, and a **fixed** `redirect_uri=http://localhost:1455/auth/callback`. It opens an HTTP listener on port 1455 (`PI_OAUTH_CALLBACK_HOST`, default `127.0.0.1`) and concurrently accepts a manually pasted code/redirect URL. Listener matches `state`, but pasted **bare code is accepted without state**; pasted URL state is compared only if present. It exchanges code + verifier with `https://auth.openai.com/oauth/token`; access JWT is decoded to extract `chatgpt_account_id` (decoding alone is not independent identity verification). Server bind failure falls through to manual entry. Listener is neither a per-UID socket nor protected against another local UID racing to bind the fixed port; a remote browser cannot ordinarily reach the host's loopback listener. Thus do **not** expose or port-forward that callback as the web solution.
- Provider denial or missing code yields an error; **abort is not proven to settle a pending manual prompt in 0.85.1**: the outer abort cancels the listener wait, but the separate `manualAbort` signal is only aborted in `finally`, after `manualPromise` settles. The helper must reject its pending prompt on the operation signal as well as the prompt signal; the Pi patch should fix/verify propagation, and teardown must terminate/join a stuck helper before releasing the attempt slot. Token fetch accepts the operation signal. A rejected code/state or network failure is an error, not a successful login. `readTokenResponse` currently includes provider response text in error strings: helper MUST discard raw exception text and native stderr, reporting only fixed reason codes. No blind automatic retry after unknown exchange/write outcome. On success native credential is `{type:"oauth",access,refresh,expires,accountId}`; `dist/core/auth-storage.js` writes the Pi auth file under the active agent directory with mode 0600 on creation, using a file lock and preserving unrelated providers. Pi's `auth/resolve.js` refreshes under credential lock when less than five minutes remain, persisting the replacement. Never send any of these fields to browser/gateway. Installed Pi can be invoked from a disposable home and synthetic provider to test interaction mechanics, but **this task has not run a login or proven the proposed manual-only patch**.

## Proposed handoff / threat boundary (review required)

1. After GitHub web login, gateway reauthorizes broker mapping on every request (existing `authenticated` path), issues opaque server-side cookie and CSRF as in `auth.go`. Browser starts `POST /api/v1/onboarding/pi/start` with exact `Origin`, `X-Agent-Host-CSRF`, JSON content type; no user, UID, home, callback or provider selector in body. Gateway strips identity headers, routes over the **broker-selected** UDS; daemon checks `SO_PEERCRED` gateway UID and its own UID/home/socket. Gateway forwards only web identity binding, session generation/epoch and an opaque web-session-bound operation key, never a browser-chosen socket. Reauthorize at each hop; remap, web logout and account switch invalidate the web operation. A new login attempt cancels/consumes the previous one for that session; per-UID serialize **daemon-owned** Pi login and settings logout across tabs. Pi's ModelRuntime queue is instance-local; its credential file lock serializes writes, not a terminal Pi process's pending login. A terminal login may finish after web logout and restore native auth: status always derives from current native credentials, never from a permanent host-side revocation flag. Do not promise cross-process cancellation of SSH-initiated login.
2. The mapped daemon starts the helper as its own UID (no `sudo`, no shared Node process, no shell interpolation), with controlled `HOME`, `PI_CODING_AGENT_DIR` resolving to that UID's **native** Pi directory, pinned executable/package version, inherited minimal environment, closed unexpected FDs and no inherited gateway secrets. Use private LF-framed stdin/stdout IPC with bounded strict messages and redacted stderr; the helper only invokes the installed native `ModelRuntime` provider and auth store. The Pi-side manual-only interaction **must never bind localhost:1455**, must require a complete expected-origin redirect URL including exact `state`, must reject bare code, duplicate/missing query keys, unrelated redirect paths and error results; Pi still checks state and exchanges code. State/verifier stay within the helper; the daemon holds only opaque attempt identity, deadline and a pending prompt. Display the Pi-generated authorization URL only to the same authenticated web session; it is not a bearer grant but contains state/PKCE challenge, so `Referrer-Policy: no-referrer`, `Cache-Control: no-store`, no analytics/logging and new-tab navigation (`noopener`). Do not fetch it server-side or let the browser pick its destination.
3. On provider redirect to `localhost:1455`, no host port receives the code. Browser shows a deliberate copy/paste instruction (provider-required redirect URL may appear in the browser address bar; avoid storing it in host URL/history). User pastes the entire redirect URL into a password-like input; `POST /api/v1/onboarding/pi/complete` JSON **body** carries it plus opaque attempt ID (never query, event stream, referer, clipboard telemetry, logs or persistent gateway state). Gateway applies auth + Origin/CSRF + content-length cap, validates shape, sends once via mapped UDS over a private one-hop request body, and never stores/prints it. Daemon atomically claims attempt *before* forwarding input, checks web session binding, expiry and UID, and passes it to the pending Pi prompt. Duplicate, stale, wrong-session, wrong-UID, previous daemon incarnation or mismatched state are terminal; user starts a fresh flow. The code traverses gateway memory transiently, like the preexisting GitHub callback token handoff, but gateway must never exchange or persist it. Same-origin XSS is still a high-impact threat; strict CSP and no third-party scripts on this wizard are required, not a substitute for server binding.
4. Deadline proposal: 5 minutes to complete, one active attempt per UID, random 128-bit opaque attempt ID, bounded queue/global admission. Web logout, session expiry/remap or explicit cancel signal the helper before exchange where possible; await its exit (or terminate it on deadline), wipe transient input, and report `cancelled` only after its outcome is reconciled. A signal alone does not prove abort: if exchange/write may have occurred, return `unknown` and recheck native Pi status. Disconnect of the browser alone does **not** certify cancellation or success. Reconnect calls `GET /api/v1/onboarding/status` and, if an attempt is pending in the same session, may resume the URL/paste UI without returning the code; after uncertain exchange/write outcome recheck Pi status instead of reusing code. Daemon crash loses pending attempts; auth file remains native and is rechecked at next login. Callback/result must not be routed by URL `state` alone. Gateway must not return provider error bodies, codes, tokens, account IDs, filesystem paths or raw stderr.
5. **Gate enforcement is server-side**, not a sidebar conditional. Every repository list/search/clone and workspace/snapshot/history/agent/command API (including direct URLs and stale tabs) requires a fresh mapped-daemon Pi status decision before native source reads. Allow only session, onboarding status/start/complete/cancel and logout while blocked; static shell may render a blank onboarding screen. If daemon/status is unavailable, fail closed with recoverable `503`; never cache a previous `ready` across credential removal, remap, daemon restart or login refresh failure. Existing `snapshot` currently returns `native_github: unknown` and lists workspaces, so this is **not implemented**. Later caching can be justified only with an explicit bounded invalidation proof. External SSH use remains native; browser gating is not a sandbox.

The Pi login proof must run on the **version actually deployed**; upgrade changes to OAuth method, redirect, or auth storage fail the version/contract check and return `native_source_unavailable`. An upstream Pi patch (or pinned small maintained variant accepted explicitly) is a security dependency, not permission to patch provider internals silently in this host. Never implement a copied PKCE/token exchange in Go simply to avoid it.

## First-use and returning-user state machine

State is *derived each request* from broker mapping + daemon/native sources, not a persisted `onboarding_complete` flag. Within the mapped daemon, check `~/src` descriptor and mode/ownership, Pi **stored `openai-codex` OAuth credential type** (not `openai` API key, environment override, `checkAuth` alone or a model-catalog entry), and native `gh` authorization/usable HTTPS Git transport independently. Use Pi `listCredentials` plus a credential-type-safe native check, and a bounded `getAuth("openai-codex")` only when needed for a freshness/refresh proof; redact its returned auth. A successfully refreshable token proves Pi auth is usable at that moment, not the existence of an active paid subscription or the account holder's identity; a synthetic model call is not provider consent proof. Native `gh auth status`/`gh api user --jq .id` must agree with mapped GitHub numeric ID, and credential helper + ordinary Git transport preflight from [interfaces](../../docs/interfaces.md) governs Git writing. Do not imply web GitHub login alone guarantees native Git. Distinguish `connected`, `missing`, `expired_or_refresh_failed`, `unknown` and `partial`; unknown/partial is not ready.

- Provisioning owns initial `~/src` creation as mapped UID with mode/ownership validation and a no-symlink/no-replacement descriptor-relative operation; if missing on an older mapped account, daemon may create only after the same checks, never gateway. If permission/ownership/path is unsafe, show setup failure and retry/support, not an empty workspace list. Preserve safe read-failure handling after later deletion.
- First web login: show a progress path **prepare home → Pi ChatGPT browser sign-in → verify native GitHub → choose GitHub repos → import → normal workspace**. Pi must complete before **fetching or displaying** repository names (even if gh was already connected). Repo list is fetched on entry to selection, from mapped daemon using native `gh`, paginated/limited with safe display labels, selecting zero or more items; no host repo registry. Empty list has a continue action; canceling Pi login leaves user at sign-in, not a read-only repo mode. GitHub repair stays inside wizard and does not replace Pi login. No number-based identity fallback on normal chrome.
- Returning user: if Pi stored OAuth can resolve/refresh and `~/src` is sound, enter regular workspace directly; no repeated wizard based on empty `~/src`. If gh is disconnected or Git transport fails, return to the appropriate integration repair before repo browsing as needed; never silently mark native Git ready from web login. On Pi logout/refresh failure go back to the Pi gate, with retry/re-auth. Do not delete workspaces on logout. Preserve a partially completed import as an existing native directory; show it as failed/incomplete and offer **inspect/resume after native source preflight**, or select another repo, never auto-delete or reclone over it. On lost ACK query operation and filesystem/Git remote before retry with a fresh command ID/precondition. No automatic duplicate clone. Browser disconnect does not cancel clone.
- Bottom-left account shelf: neutral human-friendly identity fallback; Settings shows Pi and native GitHub states separately with a Pi reauthenticate action and explicit Pi local logout (`ModelRuntime.logout("openai-codex")` under mapped UID, then immediate server-side gate), and native GitHub disconnect with fresh web authentication, confirmation and per-UID `gh auth logout` verification per [interfaces](../../docs/interfaces.md). Web logout kills only web session/pending login; it **does not** remove Pi or `gh` credentials. GitHub disconnect does not revoke provider token remotely and must prevent subsequent Git operations even when a web session persists; display exact caveat only in Settings/confirmation. Recheck both integrations on next web session. Account mismatch or external terminal credential change is fail-closed, not fixed by a cached wizard flag.

## Browser/host contract to add (proposal, not current `contracts/v1`)

Before implementation add schemas and deterministic scenarios in `contracts/v1/`, generate Go/TS types, and version consistently with [interfaces](../../docs/interfaces.md). `GET /api/v1/onboarding/status` returns `{schema_version:1,stage:"pi_required"|"github_required"|"repository_selection"|"ready"|"setup_error",pi:{state:"connected"|"missing"|"unavailable",reason_code?},github:{state:"connected"|"disconnected"|"partial"|"unknown"},source_root:{state:"ready"|"unavailable"},attempt?:{id,expires_at,phase}}`. No credential metadata or account IDs. `POST .../pi/start` returns `{attempt:{id,expires_at},authorization_url}`; `POST .../pi/complete` accepts `{attempt_id,redirect_url}` with JSON body only; `POST .../pi/cancel` accepts `{attempt_id}`. All responses no-store; completion response reports `pending|connected|failed|unknown`, never echoes request. Provider URL is transient and visible only to owning session. Stable safe error codes: `onboarding_required` (403 for gated native APIs), `login_attempt_expired`/`login_attempt_consumed` (409), `login_in_progress` (409), `pi_auth_unavailable` (503), `pi_login_failed` (422), `setup_root_unavailable` (503); authentication/Origin/CSRF errors retain existing envelope. Refresh status after completion even on a lost response. API mapping cannot be selected via request fields. Integrate a credential-generation/daemon-epoch precondition for commands begun before a disconnect. Do not add a browser `auth.json` representation.

Repo selection contract extends @connect-github-workspaces: `GET .../onboarding/repositories?cursor=<opaque>` limited page with safe `{owner,name,full_name,visibility,already_present}`; `POST` selected exact refs through existing `workspace.github.clone` commands, one idempotent operation per repo, with native filesystem status and operation query, no duplicate clone implementation. Require Pi gate on the list itself; query cursor bound to UID/web identity, no access to another user's refs. Browser components shared with Storybook; keyboard/focus/accessible progress and failure summaries, no token-in-URL navigation on host. Product copy and screenshots in Finnish for Jari review.

## Bounded implementation slices / dependencies

1. **Pi capability proof (security prerequisite).** Pin deployed Pi version, make/test manual-only browser mode and strict redirect/state validation upstream or in a reviewed Pi variant; use disposable HOME, synthetic provider/exchange, two synthetic UIDs and bound port 1455 sentinel to prove no listener, no bare-code fallback. Demonstrate credential store mode, refresh, pending-prompt cancellation without paste, helper cleanup and partial commit; no real OpenAI calls. A second synthetic native runtime should hold a pending terminal login while Settings logout executes, then finish login; prove the web gate re-derives status instead of claiming logout fenced external writers. Reject this slice if patch is unavailable or changes violate Pi's public API. Record exact provider source revision and test transcript.
2. **Daemon helper + per-UID state.** One short-lived Node helper behind daemon UDS, native ModelRuntime ownership, status/redaction/timeouts/abort and operation serialization; synthetic per-UID temp homes, distinct native auth sentinel files and forced credential-sync failure. Add host tests for wrong peer/socket/UID, concurrent tabs, duplicate/stale attempt and restart, logout/refresh race. No credential-valued logs in request, daemon or helper; compare sentinel against all responses and JSONL.
3. **Gateway gate + contracts.** Route only broker-selected UDS; Origin/CSRF/session rotation and no-store; strict URL/body limits and one-shot relay. Block *all* read/command routes including snapshots/history and direct workspace URLs before Pi status; add generated types/scenarios and cross-user browser + host tests. Ensure no repo names leak pre-gate. This precedes any wizard UI.
4. **Provision + UI wizard.** Descriptor-safe `~/src` ensure as UID; first-run/returning routes, Pi paste UX, failure/resume/cancel states, neutral account shelf. Synthetic browser tests for interrupted browser flow, missing/corrupt auth, unavailable daemon, inaccessible src, session switch, disconnected gh, no side-channel via HTML/URLs/logs. Jari visual/architecture review before live auth.
5. **Repository list/import and Settings.** Build on @connect-github-workspaces search/clone/auth rather than duplicating it; operation reconciliation for interrupted clones, native gh status/transport proof, Settings disconnect separation. Preserve the @build-history-view human visual hold. Capture screenshots and explicit acceptance, then only separately authorized live consent/pilot/deployment per test-host procedure.

Source/contract changes in these slices require `./scripts/ci-local.sh --clean --json`. This design-only diff requires link validation and `issuectl doctor --json`; it does not justify running live sign-in or CI as proof of a native login. Independent, source-attached review (`consult-llm`, `gpt-6-astra`, 2026-09-27) found two correctable design claims: 0.85.1 pending manual-prompt abort can hang, and ModelRuntime's in-process serialization cannot fence an external terminal login after logout. Both are corrected above with explicit helper cleanup and native-state reconciliation. This review did not test a real provider, prove the future Pi patch or verify two-UID isolation. Before architecture acceptance, independently verify the manual-only Pi seam and cross-session/UID callback isolation against a synthetic running implementation. Residual risk: installed provider's loopback redirect remains an awkward browser experience, and `getAuth` proves possession/refresh, not entitlement; neither can be represented as a verified live login by synthetic tests.
