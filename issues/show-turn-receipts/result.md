# Turn and send receipts in the v2 browser

The browser validates the private status extensions (`send_receipt`, `turn_settled`, `pending_question`) and a bounded, command-ID-matched receipt lookup. A 404, transport failure or missing receipt remains uncertain; no request path replays a send. The most recent send has a local message/receipt row with four distinct outcomes. `accepted` means Pi RPC acceptance, not turn completion. The settled row uses the host observation time only if `state=settled` and its `native_key` is present in the loaded native history; `unknown`, missing history or stale views cannot claim settlement. A question and its choices are rendered as text, including `unknown` kinds, with no answer/cancel control. Ordinary send cannot answer `extension_ui_response`.

**Deviation I4:** The designer's hardcoded 13.53 and implied message-level confirmation are replaced by the server's observation timestamp and command-ID receipt. Ambiguous sends retain a visible copy action, not a retry. The native history does not carry the send command ID, so the latest tab-local receipt is displayed as its own adjacent message row instead of claiming a precise correspondence to an arbitrary identical native user entry. This avoids falsely attaching a lost send to a prior message with the same text.
