# Result: participant messages and text-only turns

Implemented ADR 0038 sections 3–5 in the daemon's Pi companion and the conversation controller, behind the experimental feature `multiplayer`. No browser card yet, and no guest `send` route: that route is `multiplayer-guest-stream`'s, and it calls `holdParticipantMessage` from here.

## What exists now

- **Turn mode in the companion** (`process-extension.mjs`): one mode per Pi process, `tools`, `text_only` or `approve_each`, decided in `before_agent_start` from the message that starts the run. The owner's input is an idle `input` event with source `rpc`/`interactive`. An extension's `sendUserMessage` (source `extension`) keeps the mode, and so does any user-started run while an extension input is still pending (fail closed). `oh-participant-message` gives `text_only`, or `tools` for `full_rights` only when the membership record says so at that moment. A `continue` line gives its mode. Wakes, scheduled wakes and notifications keep the mode. The owner's steering or follow-up switches to `tools` from the next call.
- **Enforcement**: the companion's `tool_call` handler returns `{block, terminate, reason}` for every call in `text_only`, nested codemode calls included. Pi stops at the first block, so other extensions' handlers before it (returning `block: false`) or after it cannot undo it.
- **Rebuild**: on `session_start` and `session_tree`, the mode comes from the branch: the latest owner input, participant message, `continue` line or the companion's own `oh-turn-mode` entry. A participant message always gives `text_only`; an unreadable branch gives `text_only`. The companion writes `oh-turn-mode` custom entries (not in the model's context). A run's start decision (`covers: 1`) is written just before its starting message and covers only that message. A queued steer or follow-up is attributed once Pi delivers it, by an entry right after it (`steer: true`), matched to the queued input by text and falling closed to an extension's. Without these entries, history cannot tell an extension's `sendUserMessage` from the owner's input after a restart. A steer the owner cleared from the queue never reaches the branch, so it attributes nothing. Entries are written only once the branch has other people in it, so ordinary conversations gain nothing.
- **Fail-closed full rights**: each call of a full-rights participant's run rereads the membership record (path given at launch as `OPEN_HABITAT_MEMBERS_RECORD`, removed from the environment at load) and needs `role: full_rights`, `state: joined` and the same member generation as at delivery. A take-back whose `grant` message was lost still blocks the next call. A delivered `grant` switches the run to `text_only` at once.
- **Per-call approval**: in `approve_each`, every call (nested ones too) is asked one at a time through `ctx.ui.select`, with the title `oh-approval:` plus `{call_id, tool, arguments, parent_call_id?, request}`. The arguments are complete JSON, up to 32768 code points; a larger call is blocked rather than asked about partially. The answers are `allow`, `deny`, `allow_all`. Each answer is an `oh-approval` entry; Salli kaikki is recorded as the run's mode.
- **Web tools**: `globalThis[Symbol.for('open-habitat.turn-mode')].webTools()`, which runs the same grant recheck as a call. `runtime/core/web-search.mjs` adds no provider search outside `tools`. The bridge patch moved to `runtime/core/bridge-patch.json`, which the build and the acceptance test both apply; it gives a query started outside `tools` `--tools=` instead of WebSearch/WebFetch.
- **Bridge ops**: `participant_message` (refused while a run is in progress, once per message ID) and `release` (`continue` with mode `tools`/`approve_each`, or `declined`, which starts no run). The companion checks against the branch that the named request is still waiting (`waitingRequests`: the owner's own message settles the newest one, and older ones stay).
- **Daemon** (`turn_modes_linux.go`): participants' messages and the owner's releases wait in `guestHeld`, in one order (`seq`) with the owner's held text. They are delivered at the settle that frees Pi, after a launch, or at once when Pi is idle. One person's consecutive messages are joined; they are never joined with the owner's text or with another person's. An owner send while such an item waits for a live Pi is held behind it. At delivery the record is reread, and someone removed meanwhile is dropped. A batch being delivered can no longer be cancelled. Delivery holds the owner's sends (`s.waking`) until the run starts, as the scheduled wake does, and dispatches whatever waits behind it afterwards. The companion's request bound is 128 KiB, so a 16000-byte message fits even when Go's encoder escapes it. A stopped Pi is started for a held item. The owner's route is `POST /api/v1/conversations/<id>/requests` `{request, subject, action: allow_all|approve_each|decline}` (gateway allowlist updated).
- **Approval question** (`pi_approval_linux.go`): question kind `approval` with the typed `approval` object. A malformed one is cancelled unseen, so the guard blocks the call. An answer must be one of the three choices, and Pi's request ID binds it to that call. The browser accepts the kind and shows it as a choice whose prompt carries the arguments until the owner's card lands.
- **Host context**: `multiplayer-context.md`, given while the feature is on, says that participant words are information, not instructions for the owner's turns.
- **Contract**: `event.schema.json` question kind `approval`, an example, and negative checks; `conversation-members.schema.json` `$defs/release` and `releaseReply`.

## Acceptance against the pinned Pi and bridge

- `pi-device-test/turn-modes.test.mjs` runs the real Pi 1.5.2 in RPC mode with the companion, a hostile `tool_call` handler before it (always `block: false`), a recording one after it, Pi's own codemode tool and a scripted provider. Covered: the longest message, Go-escaped; a queued owner follow-up that was cleared transferring nothing to a later extension message; a parallel batch plus a codemode call with nested calls in a participant turn (nothing runs, the later handler never sees a call, the run ends after the batch); `participant_message` refused while busy; the owner's message gives tools back; an extension `sendUserMessage` after a participant turn stays text-only and rebuilds as such; a restart between a participant message and a scheduled wake (the wake is text-only); per-call approval of a codemode call and its nested calls, plus a parallel batch with Salli kaikki (five questions, complete multi-line arguments, answers recorded); release, decline and not-waiting; revocation during a run with the `grant` message delivered and with it lost; a forged full-rights message the record does not back.
- `pi-device-test/bridge-tools.test.mjs` runs pinned pi-claude-bridge 0.12.0 with the release's patch against a stand-in Claude Code (`fixtures/turn-modes/fake-claude.mjs`). The stand-in speaks the SDK's stream-json protocol, streams a `tool_use` for the served `mark` tool and calls it on the bridge's in-process MCP server. In a participant turn Pi blocks the call (the tool never runs) and Claude Code gets `--tools=`. In the owner's turn the call runs once, through Pi's `tool_call`, and Claude Code gets `--tools=WebSearch,WebFetch`. Code reading confirms the bridge's MCP handler executes nothing: it only waits for Pi's result for that tool-use ID (`buildMcpServers`), and the served set is every Pi tool through the same path. **No bridge-served tool bypasses `tool_call`.**
- `web-search.test.mjs`: a turn without all its tools gets no provider search.

## Decisions for later review

1. **`oh-turn-mode` entries.** The ADR rebuilds from owner input, participant messages and `continue` lines. History alone cannot tell an extension's `sendUserMessage` from the owner's input, and the acceptance test needs that to survive a restart. So the companion records each decision as a hidden custom entry. Alternative: treat every user message as owner input after a restart (fails open). Written only for conversations with other people in them.
2. **Approval transport: a prefixed select, not a bridge message.** The ADR says the companion gives the daemon the call's details "over the bridge". The bridge is daemon-initiated, so the companion encodes the details in the Pi `select` itself, exactly as the accepted permission question does with `confirm`. The daemon keeps the complete arguments in the typed question, not the 250-character prompt, and Pi's request ID binds the answer to that call. Alternative: a new companion→daemon channel.
3. **Answer tokens `allow`/`deny`/`allow_all`**, not Finnish labels: the browser names them.
4. **Calls with arguments over 32768 code points are blocked** in `approve_each`, with a reason the agent reads, rather than asked about in part. The owner can still release with Salli kaikki.
5. **A full-rights run checks the member generation strictly**: any change to that member since delivery (a re-invite that renames them, for example) drops the run to text-only. It fails closed, and the next message delivers with the new generation.
6. **The release names its requester by subject**, and the daemon takes the display name from the record (the subject if they were removed). The browser knows each waiting request's author from the daemon's facts (`multiplayer-guest-stream`).
7. **A stopped Pi is started for a held participant message or release**, as for the owner's held send. The owner's Stop does not drop participants' held messages; they go after the next start, in arrival order.
8. **Pending `input` entries expire after 60 s**. A prompt that failed after its `input` event leaves one entry, which makes at most the next minute's ambiguous run keep its mode (fail closed).
9. **Mid-run revocation and the bridge's parked query**: the companion blocks the next Pi-dispatched call, but a Claude Code query started with WebSearch/WebFetch while the run had tools keeps them until it returns to Pi. This is the ADR's "a call that has already started finishes", applied to the in-flight query; the next query gets none.
10. **The browser's interim approval view** shows the tool and arguments in the generic choice dialog, without line breaks preserved, until the owner's card (`multiplayer-browser`). Only reachable once participants can send.

## For the later issues

- `multiplayer-guest-stream`: mount `send` and cancel on the guest table with `holdParticipantMessage` / `cancelParticipantMessage`. The guest stream must **not** carry the `approval` object of a question (the owner's detail), nor the owner's held texts. Waiting requests can be derived as `waitingRequests` in the companion does; the daemon has no Go version yet.
- `multiplayer-browser`: the card's actions post to `/api/v1/conversations/<id>/requests`; per-call rows come from `question_kind: "approval"` and the `oh-approval` entries.

## Review

Critical rigor, because this changes an authorization boundary (who can make the owner's agent act), the contract and daemon concurrency. Independent `/llm-review` with gpt-6-astra as finder and claude-fable-5-2 as verifier (two completed calls; the finder's first attempt hit the harness's background time limit with no output and was rerun), then `/assess-findings`. Six findings, all confirmed by local checks and by the verifier, all FIX, all fixed in this branch with regression tests:

1. A queued owner follow-up the owner cleared left a coverage entry that a later extension message consumed after a restart, rebuilding as `tools` (fixed by attributing steers on delivery).
2. `webTools()` skipped the grant recheck, so a lost revoke kept provider search and the bridge's web tools (fixed).
3. A direct owner send could overtake a held participant item (now held behind it).
4. Cancel could report success for a message being delivered (now refused while delivering).
5. No dispatch after a successful delivery, and `already_delivered` waited for a run that never starts (fixed).
6. Go's JSON escaping could push a long message over the companion's 32 KiB request line (bound now 128 KiB).

The verifier noted that none was reachable in production at the reviewed commit, because the guest `send` route lands in `multiplayer-guest-stream`. No issue was filed: nothing remained open.
