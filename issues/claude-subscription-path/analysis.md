# Claude subscription path — research for decision (15 October 2026)

**Suositus Jarille:** Älä rakenna Claude-tilausta käyttävää Pi-laajennusta tai tarjoa Claude Code -kirjautumista selaintuotteessa vielä. Anthropic kieltää nimenomaisesti kolmannen osapuolen tuotteita tarjoamasta claude.ai-kirjautumista ja tilauksen käyttörajoja ilman ennakkohyväksyntää; kielto koskee myös Claude Agent SDK:ta. Valitsisin arkkitehtuuriksi erilliset, käyttäjän Unix-tunnuksella ajettavat natiivit agentit (Pi, Claude Code ja Codex), mutta Claude-tilauspolku vaatii ensin Anthropicin kirjallisen hyväksynnän; ilman sitä Claude voidaan toteuttaa vain kaupallisin API-tunnuksin. Myös nykyisen Pi/Codex-kirjautumisen käyttö hostatussa tuotteessa vaatii tarkistuksen OpenAI:lta: Codexin oma dokumentaatio sanoo, ettei app-server-kirjautuminen ole ollut sallittua kaupallisille tai hostatuille palveluille. Tämä on päätösehdotus, ei lupa toteuttaa kumpaakaan tilauspolkua.

This is a technical/product reading, not a legal opinion. Recheck the live documents and obtain provider authorization before launch.

## Candidate paths and actual components

* **Installed Pi package is not a Claude provider.** `~/.pi/agent/settings.json` lists `npm:pi-claude-code-ui@1.0.78`. Its installed `package.json` describes “Claude Code-style grouped tool rows for pi”; `pi.extensions` registers `extensions/index.ts` and `spinner.ts`, whose source implements Pi TUI rendering/tool display. Its dependencies are Shiki and diff, not the Agent SDK or Claude API. It cannot give Pi access to a Claude subscription. This is local source inspection, not a claim that no other Pi extension exists. [Package upstream](https://github.com/FammasMaz/pi-cc-tools).
* **Possible Pi + Agent SDK bridge:** Anthropic [says](https://code.claude.com/docs/en/agent-sdk/overview) the Python/TypeScript Agent SDK launches the Claude Code binary, reuses its tools, permissions, sessions and hooks; it is not a direct Claude model provider for Pi. A Pi extension could invoke it and bridge events, but then Pi and Claude Code would both have conversation histories; Pi would be a transport/UI shell around another agent, and the subscription login prohibition still applies. Direct API integration into Pi would use an Anthropic API key, not subscription capacity. We did not enumerate the entire third-party Pi extension ecosystem, and do not claim none exists.
* **Native Claude Code adapter:** [CLI reference](https://code.claude.com/docs/en/cli-reference) documents `claude -p`, `--input-format stream-json`, `--output-format stream-json`, `--include-partial-messages`, `--resume <id>` and permission-prompt handling. [Headless guide](https://code.claude.com/docs/en/headless) describes JSON streaming, SIGINT/Agent SDK `interrupt()`, and SIGTERM shutdown: SIGTERM may leave a turn without a result; distinguish it from turn interruption. [Sessions guide](https://code.claude.com/docs/en/sessions) identifies native `~/.claude/projects/<project>/<session-id>.jsonl` transcripts and warns simultaneous resumes can interleave. [Authentication guide](https://code.claude.com/docs/en/authentication) describes browser login with remote-server copy/paste fallback and `claude setup-token` for scripts. Prefer an interactive per-user login over making the host collect/copy long-lived tokens. Native read-only transcript discovery and single-writer checks need a separate prototype; JSONL layout and permissions are native facts, not a stable host schema. Claude SDK streaming input offers a stronger control surface than one-shot CLI but shares the SDK commercial/subscription restriction. A permanent headless CLI session's live steer semantics require an experiment; do not promise Pi-style steering from these flags alone.
* **Native Codex adapter:** [Codex app-server](https://learn.chatgpt.com/docs/app-server) explicitly targets deep third-party clients with stdio JSONL RPC; `thread/start`, `thread/resume`, `thread/turns/list`, `thread/items/list`, `turn/start`, `turn/steer` and `turn/interrupt` give stronger live control than `codex exec`. It reads native persisted threads (recent versions use paginated history) and emits turn/item events. `account/login/start` offers browser or device-code login technically, but the same document disallows **app-server authentication** for commercial or hosted services. [Codex auth](https://learn.chatgpt.com/docs/auth) describes `~/.codex/auth.json` / OS store, `CODEX_HOME`, per-user CLI device sign-in and automatic token refresh. The host should not handle those tokens. App-server transport is not authority to use the subscription in this deployment. API-key billing is a separate route; verify provider terms and hosted-client approval for the exact design.

## Fit with this repository

The [Unix-native ADR](../../docs/decisions/adr-0001-unix-native-agent-host.md) already namespaces IDs (`pi:<id>`) and makes histories native. [ADR 0010](../../docs/decisions/adr-0010-taskfleet-worktree-agents.md) keeps Taskfleet responsible for worktree lifecycle and the per-user daemon responsible for browser-owned Pi. Extend that ownership rule *per harness*, not by running Claude inside Pi: the gateway maps the user and never reads their credentials; each daemon owns its own user's child/connection, workspace checks, one-writer lock and event translation. Existing [conversation/recovery design](../../docs/architecture/conversations.md) can retain its uncertainty semantics. Do not mix terminal and browser writes to a native session. Taskfleet binding must still prove run/node/checkout identity.

The contract is **not already harness-neutral**: [`common.schema.json`](../../contracts/v1/common.schema.json) hardcodes `^pi:[0-9a-fA-F-]{36}$` for `agentId`; [`command.schema.json`](../../contracts/v1/command.schema.json) has Pi-level steer/follow-up/queue/question semantics; [`history.schema.json`](../../contracts/v1/history.schema.json) has Pi-specific entry types; [`pi-status`](../../contracts/v1/pi-status.schema.json), [`pi-attempt`](../../contracts/v1/pi-attempt.schema.json) and model routes name Pi. A second harness needs new namespaced IDs (`claude:<native-id>`, `codex:<native-id>` after verifying formats), harness identity/capabilities in snapshot and onboarding, optional/unsupported commands represented honestly, native history/event normalization, and harness-specific auth/status and model choices. Reuse workspace discovery, gateway identity, HTTP/SSE envelope, pagination/uncertainty concepts and browser presentation where possible; do not manufacture Pi-style queue/recap/question controls or duplicate Claude/Codex transcripts in a host database. Prototype history parsing, continuation ownership, permissions and credentials under separate Unix users before modifying v1 contracts.

## Recommendation and decision boundary

Recommend **native harness adapters**, not a Pi extension wrapping Claude. They keep terminal and browser on the same credentials, processes, settings and native session IDs and avoid two competing histories. Principal cost: separate controllers/history adapters and capability-aware UI, plus native transcript/version drift. The Pi extension is superficially smaller at the UI boundary but gives the wrong history owner and, for subscription use, an explicit SDK policy blocker. Running native Claude Code with subscription removes that technical duplication but **does not resolve** whether this hosted product can offer that subscription; seek written Anthropic approval naming the CLI/SDK use and the multi-user remote browser product. Until then no hosted Claude subscription launch. The commercial API-key path is the non-subscription fallback; a native Claude Code controller can still preserve native history if commercial terms and permissions fit.

Likewise distinguish OpenAI's documented local ChatGPT subscription support from hosted-product rights: ask OpenAI about Sign in with ChatGPT/partner access and specifically whether current Pi OAuth in this hosted product is allowed; do not extend it to Codex app-server login by analogy. Record the architecture proposal in [ADR 0016](../../docs/decisions/adr-0016-native-harnesses-and-subscription-authorization.md), proposed only. No implementation or provider approval was obtained in this research.
