# Manual title regeneration — result

The pilot.22 gateway's `daemon_exchange_failed` observation is a transport failure, not a confirmed provider failure. There is no matching daemon-side evidence from that request; its exact cause cannot be reconstructed from the frozen guest, which was not touched. The synthetic lab reproduced the existing failure presentation with the real conversation controller and fake Pi (which has no model runtime), **not** the gateway transport failure or real-provider behavior.

The model helper now tries one other available text model if the cheapest configured model fails or returns an invalid title. Both calls together remain under the daemon's existing 15-second subprocess deadline, with 48 output tokens per attempt and no tools. A failed attempt never writes a native name. The daemon distinguishes fixed failure reasons (`model_unavailable`, `model_timeout`, `model_invalid_response`, `native_name_unavailable`, `native_name_changed`, `controller_unavailable`, `name_write_failed`) in its JSONL diagnostic and the manual failure response, without including provider errors, prompt content or the session ID. The gateway logs `conversation_title` rather than the generic `daemon_request` on a verified regeneration route, making a lost exchange recognizable. The browser keeps its generic Finnish error and prior title; a subsequent request can retry. A successful request still goes through the owned Pi RPC `set_session_name`, invalidates the browser snapshot and persists only in Pi history.

## Decisions for review

- Preserve a generic browser-facing failure notice; the fixed reason is for host diagnosis, not a user-facing provider error. No raw SDK exception or excerpt is logged or sent to the browser.
- Limit fallback to one alternate model. The available-model snapshot cannot guarantee that the cheapest answers, but a long list of sequential attempts could consume unbounded provider calls; the existing overall 15-second limit still applies.
- Do not infer that pilot.22's transport failure was caused by model selection. The deployment and visual approval remain later steps; no changes were made on the frozen guest.
