# Result

Repository icon suggestions now receive the current repository's validated image content, rather than a local path that the tool-free helper cannot open. Raster images reach vision-capable models as image blocks; small SVGs reach them as source text. Discovery also recognizes conventional app icons and bounded local README logo references. The same discovery supplies the picker and sidebar, so a suggested logo has a working preview.

## Diagnosis

`workspaceIconSuggestions.ts` sends workspace ID, wish and earlier rounds, not repository files. `conversation_linux.go` owns the controller's suggester seam, but the request is assembled in `workspace_icon_suggest_linux.go`. That handler previously sent only `facts.logo`, derived from four filenames in eight fixed directories. There was no recursive search. `workspace_icon_candidate_linux.go` already provided the bounded, owner-checked image reader used by previews/selections, but its bytes were not sent for the repository's own logo. Uploaded SVGs likewise became only a generic label in `iconWishAttachments`.

The helper calls the model directly, without an agent session or tools, from the person's home. It cannot open a supplied repository path. This was a content-delivery defect, not a missing read permission to grant the model. No tools, renderer, network fetching or new authority were added.

## Decisions for later review

- **What counts:** retain conventional `logo.svg`, `favicon.svg`, `logo.png`, `favicon.png`; add `icon.svg`, `icon.png`, `apple-touch-icon.png`, `logo.webp`, `icon.webp`, `logo.jpg`, `logo.jpeg`. Search the root, `public`, `static`, `assets`, `design-system`, `docs`, `web/public`, `web/static`, `.agents`, `web/assets`, `public/assets`, `assets/icons`, and `public/icons`, in that order. This includes `.agents/icon.svg`. The alternative was an unrestricted recursive image crawl; fixed locations avoid dependency/vendor screenshots and unbounded repository work. It is not a claim to recognize every app framework's naming scheme or ICO files.
- **README fallback:** inspect the first nonempty supported README's first 2 KiB, only when conventional locations yield nothing usable. Inline Markdown images and quoted HTML img attributes count when their alt text or path contains a logo/icon/favicon word. Up to eight local candidates, in document order, are checked; arbitrary screenshots, remote URLs, reference-style Markdown, query/fragment paths and later README sections are not crawled. A README reference can name a deeper local file; no directory walk is performed. This is deliberately a hint parser, not a Markdown renderer.
- **Usability and bounds:** retain PNG/JPEG/WebP/SVG, 256 KiB per image and existing path validation. Automatic discovery now checks bounded content before accepting a file, so an LFS pointer cannot hide a valid later favicon. Reads remain pinned beneath the workspace, without symlinks or mount traversal. Model-content reads additionally retain the existing candidate reader's ownership checks; unreadable/foreign-owned candidates do not become model data. Those ownership policies were not widened.
- **SVG representation:** supply at most 4 KiB of complete SVG source, subject also to the remaining 64 KiB model text budget. Larger SVGs stay selectable but get an explicit source-omission notice, not a partial or fabricated description. No SVG rasterizer, execution or external-resource fetching was added. Alternative: a rendering dependency and its security surface; unnecessary for selecting an already available icon.
- **Model capability:** repository raster imagery is optional enrichment. A text-only model receives an honest availability-only notice and can still select the supplied path; explicitly uploaded raster images remain required input. The prompt distinguishes an available icon, omitted visual content and no usable discovered icon. A bounded search cannot prove that no icon exists anywhere in the repository, so the helper must not claim exhaustive absence.
- **Other workspaces:** empty-wish requests reject references to other workspaces even if the model returns them. Explicit wishes retain the earlier supported named-workspace/file selection behavior. The catalogue contains selectors, not other workspaces' image bytes. Existing saved browser rounds remain saved; requesting another round uses the new facts.
